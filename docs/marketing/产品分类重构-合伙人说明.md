# 产品分类重构方案（合伙人审阅版）

> 状态：🔵 **方案已定稿，未开发**（2026-10-28）
> 一句话：**把「展示我们有 41 个工具」改成「按税法分类 + 按用户身份引导」两套逻辑** —— 让专业客户觉得专业，让不懂税的人被引导到正确的那个税。
> 本文是给**非技术读者**看的业务说明。技术细节见两份文档：`docs/development/阶段22-分类体系与双视角导航-未开工.md`（为什么这么定）与 `docs/development/阶段22-分类总表-思维导图与工具映射-未开工.md`（完整分类树与工具映射）。
> 商业背景见 `marketing/合伙人版商业企划.md`；本文只讲产品结构这一件事。

---

## §1 现状：三个可以验算的事实

| # | 事实 | 数据 |
|---|---|---|
| 1 | 产品现有 41 个计算入口（20 个速算 + 21 个完整测算），已全部真机冒烟通过 | 产品是**跑得通的** |
| 2 | 但现行的 5 组分类**混了四种维度**：「工资与到手」是场景、「税优与养老」是政策、「企业与经营」是主体、「一次性收入」是频次 | 分类没有统一口径 |
| 3 | 中国现行 **18 个税种**，产品能提供计算器的只有 **4 个**（增值税、企业所得税、个人所得税代扣、社保类）；**14 个税种没有任何计算器** | 覆盖面的真实状况 |

**结论**：产品的计算能力是对的，但**入口的组织方式是按「我们有什么」排的，不是按「客户在找什么」排的**。两类客户都受影响：

| 客户 | 他的状态 | 现在的体验 |
|---|---|---|
| 财务 / 代账 / 小微企业主 | **知道自己要算什么税** | 想找「房产税」，得先判断它是「企业经营」还是「一次性收入」 |
| 普通个人 | **不知道自己要算什么税** | 只知道「我把房子租出去了」，但工具列表里写的是「财产租赁所得」 |

## §2 方案核心：一层分流，两套逻辑

### 2.1 第一层不变（已上线，本次不动）

用户进来先回答一个问题：**这笔税是给你自己算的，还是替公司/客户算的？**

这已经在线上跑着了（v2.0.0），不是本次新增，所以**没有额外的学习成本与存储迁移**。

### 2.2 分流之后，两侧各用自己的一套逻辑

| | **选「企业」的人** | **选「我自己」的人** |
|---|---|---|
| 他是什么状态 | 知道自己要算什么税 | 不知道，只知道发生了什么事 |
| 给他的东西 | **专业目录**：按税种找 | **引导**：告诉你要算哪些税 |
| 一级分类 | 按征税对象五类（税法口径） | 按职业角色 8 类 |
| 二级 | 具体税种（18 个 + 费） | 具体事件（24 个） |
| 举个例子 | 点「财产与行为税 → 房产税」 | 点「我把房子租出去了」→ 系统告诉他要算 4 个税 |

**为什么不是一套**：专业人士要的是效率和确定性（直接到税种），普通人要的是翻译（把生活事件翻译成税）。一套结构服务不了两种心智。

### 2.3 一条方法论：先分类，后对应

不是整理现有 41 个工具，而是**先把「一个中国纳税人可能遇到什么税」这件事列干净**，再把工具挂上去。

- 挂得上的 → 保留（可能要拆：现在有两个工具把不同税种揉在一起）
- 挂不上的 → 那就是**缺口**，进新工具排期
- **不再预设「41 个入口必须一个不少」** —— 这是本次最大的观念变化，见 §6 待拍板第 1 条

## §3 分类结构（概览）

```
用户进来
│
├─「企业」──── 按专业税种（目录，自助查找）
│   ├─ 流转税          增值税 ✅ / 附加税费 ⚠️ / 消费税 ❌ / 关税 ❌
│   ├─ 所得税          企业所得税 ✅ / 个税代扣 ✅（缺汇总申报 ❌）
│   ├─ 财产与行为税    印花税 ⚠️ / 房产税 ❌ / 土地使用税 ❌ / 契税 ❌ / 车船税 ❌ / 购置税 ❌
│   ├─ 特定目的与资源环境税  土增税 ❌ / 耕地占用税 ❌ / 资源税 ❌ / 环保税 ❌（默认折叠）
│   └─ 费与用工        社保 ✅ / 残保金 ✅ / 工会经费 ⚠️ / 文化事业费 ❌ / 用工成本 ✅
│
└─「我自己」── 按身份引导（我也是谁 → 遇到什么事）
    ├─ 第 1 层  税务身份：居民 / 非居民（只影响算法，不问普通用户）
    ├─ 第 2 层  职业角色 8 类：上班族 / 自由职业 / 个体经营者 / 股东高管 / 退休年金 / 灵活就业 / 外籍 / 待业学生
    └─ 第 3 层  事件 24 个：发了工资 / 发了年终奖 / 离职了 / 卖房了 / 买房了 / 把房租出去了 / 开小店了 / 中奖了 …
```

**关键数字**（从完整分类树数出来的）：现有 41 个入口，**30 个主挂在「我自己」分支、11 个主挂在「企业」分支**，另有 **10 个工具两侧都要用**（例如工资个税：员工自己算，HR 也在算）。这就是为什么不能简单把工具劈成两堆。

## §4 这件事的商业价值

### 价值一：企业侧的专业度，是我们进入代账 / 财税顾问渠道的门票

- 现行 5 组里混着「场景」「政策」这些非税种维度，专业客户一眼会看出这是**给个人用户设计的**
- 改成按征税对象五类 + 18 税种后，导航口径与 CPA 教材、电子税务局的分类一致
- 现有 **21 个 SEO 落地页**可以按税种与新目录一一对应，SEO 结构与站内结构从此统一（现在是两套）
- 「特定目的与资源环境税」默认折叠但保留完整 → 对专业客户是「这家伙懂」，对个人是「不打扰」

### 价值二：个人侧的引导，解决的是「来了但没算完」

- 个人用户不是不想算，是**不知道自己要算什么**
- 按「事件」组织（卖房了 / 开小店了 / 中奖了）后，用户不需要先知道「财产转让所得」这个词
- 这是 TurboTax、个税 App 的共同做法：先问「发生了什么」，再落到具体表单

### 价值三：缺口就是增长空间，且都是大额场景

按新分类清点出来的空白，恰恰是**金额大、搜索量大、也最容易被转发确认**的场景：

| 场景 | 涉及金额 | 有没有工具 |
|---|---|---|
| 买 300 万的房 | 契税 3~9 万 + 印花 | ❌ |
| 卖自己的房 | 个税 + 增值税 + 附加 | ⚠️ 现在只算个税，其余要用户手填 |
| 把房子租出去 | 增值税 + 房产税 4% + 财产租赁个税 + 附加 | ❌ |
| 买 20 万的车 | 车辆购置税 2 万 | ❌ |
| 有车 | 车船税，每年几百 | ❌ |

买房、买车、租房这几件事的共同点：**用户会主动搜，也会把结果发给配偶或中介核对**——这是天然的传播动线。

### 价值四：风险可控

| | 说明 |
|---|---|
| **不动计税内核** | 41 个计算引擎一行不改，不存在「改完算错钱」的风险 |
| **不动用户数据** | 不新增必须填写的字段，无需数据迁移 |
| **不改现有价格与商业模式** | 纯产品结构与导购层 |
| 影响范围 | 只有「工具列表怎么排、怎么找」这一层 |

## §5 为什么现在做

| 理由 | 说明 |
|---|---|
| **现在改成本最低** | 产品已具备 41 个跑通的计算器与 21 个 SEO 落地页，但**尚未开始推广**。此时重构是纯粹的工期问题；一旦开始获客，改结构就要同时改文案、改落地页、改已形成习惯的用户 |
| **分类是 SEO 的地基** | 21 个落地页的导航结构与站内分类现在是两套口径；统一后收录结构才可能互相导流 |
| **结构化工作做一次，长期受益** | 税种字典一旦建立，新工具只需要挂到已有位置，不必每次重新讨论「放哪一组」 |

## §6 路线图与成本

按「先做看不见的地基，再做看得见的变化」排序。每一步都可以单独上线、单独验收。

| 里程碑 | 交付物 | 工作量 | 对用户可见 | 验收口径 |
|---|---|---|---|---|
| **M1 税种字典** | 18 税种 + 5 税类 + 申报周期 + 适用主体的结构化数据 | 小（纯数据） | ❌ | 数据自洽断言全绿 |
| **M2 个人三层字典** | 8 角色 + 24 事件的结构化数据 | 小（纯数据） | ❌ | 同上 |
| **M3 工具映射 + 前台双逻辑** | 现有 41 个工具按新分类重排；企业侧目录 / 个人侧引导 | 中 | ✅ | 41 个入口数得出、全量可达 |
| **M4 补新工具** | 契税 / 车辆购置税 / 个人出租组合 / 卖房补齐（按 §8 第 3 条定顺序） | 大（每个都要活参数税率 + 测试） | ✅ | 每个新工具独立出页、独立冒烟 |

**M1–M3 是本次提议的范围；M4 建议作为下一阶段单独立项。**

## §7 三条风险和取舍（提前说明，不要事后惊讶）

| # | 风险 | 处置 |
|---|---|---|
| 1 | **「41 个工具」这个对外数字会变**：拆开混装工具后入口数会增加（例如「附加税+印花税」拆成两个） | 对外材料改用「覆盖 N 个税种」而不是「41 个计算器」，口径更稳也不怕增长 |
| 2 | 现有部分自动化测试会失效 | 一次性改测试，属于工程量不是风险 |
| 3 | 拆分工具会暂时增加前台入口密度 | 用「默认折叠」控制（低频税类折叠），已在分类设计中预留 |

**明确不做**（避免范围蔓延）：报税代办、代理记账、凭证/票据管理、登录后的跨设备档案同步。这些依赖后端与资质，与本次结构调整无关。
