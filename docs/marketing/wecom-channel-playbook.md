# 企业微信按入口分码 · 打标签 · 欢迎语操作手册

> 最后更新：2026-09-16（v1.37.3）
> 本文件只回答一个问题：**怎么让顾问知道眼前这个客户是从「留资弹窗 / 分享图 / 落地页」哪一个来的**。
> 站点侧的一半（按入口取不同的码）已在 v1.37.3 落地；本文件是**企微后台那一半**的操作清单。
> 配套：执行清单见 [gtm-execution-plan.md](gtm-execution-plan.md)，线索跟进见其「线索跟进 SOP」一节。

---

## 结论先行

1. **一个入口一个码**是唯一零依赖、可立刻验证的做法：企微后台建 3 个客服账号 → 站点按入口渲染对应链接。
2. **不要手工在客服链接后拼 `?from=share`**。企微《获取客服账号链接》文档规定：返回的客服链接**不能修改，
   也不能把参数复制到其他链接上使用**，否则「用户进入会话事件」的参数校验不通过、无法回调。
   —— 页面照样打得开，但回调里拿不到来源。这是"看起来能用、实际没数据"的假成功，比不做更糟。
   （证据等级：**官方文档**，企业微信开发者中心《获取客服账号链接》
   <https://developer.work.weixin.qq.com/document/path/94665>，2024-03-04 版；同一文档亦写明
   "不同客服账号对应不同的客服链接"，这是一账号一码的依据）
3. 分了码却配**同一批接待人 + 同一句欢迎语**，等于没分。欢迎语与接待人也要跟着分。

## 站点侧已具备的能力（v1.37.3）

配置在 `index.html` 底部的 `window.LEAD_CONFIG`：

| 字段 | 触发的入口 | 说明 |
|---|---|---|
| `wecomQrUrl` | 兜底 | 所有未单独配置的入口都用它；留空则弹窗降级为仅留言通道 |
| `wecomQrByChannel.modal` | 站内留资弹窗（结果页 / 个人中心） | 未配 → 回落兜底码 |
| `wecomQrByChannel.share` | 分享图带来的访客 | 分享图上的码仍是"回流站点"的码（它的任务是拉新访问），
访客进站后归因记为 `share`，**其留资弹窗改用这个专属码** —— 分享图来源就是这样被区分出来的 |
| `wecomQrByChannel.landing` | 站外落地页 / SEO 页（`source` 含 `seo_` / `landing`） | 未配 → 回落兜底码 |

- 入口归类逻辑见 `lead-modal.js` 的 `channelOfSource()`：复用后端已认可的 `source` 字符串，**不新增归因字段**，
  所以管理台线索表的 `source` 与企微侧的入口码是同一套来源口径，两边对得上。
- 未配置或配了空白串的入口一律回落兜底码：**少配一个入口不会让通道消失**，只会少一条来源数据。

## 企微后台三步

> 路径以你后台实际界面为准（企微后台版本差异较大）；下面是"要做什么"，不是"点第几级菜单"。

### 第 1 步：为每个入口建一个客服账号（一账号一链接）

在「微信客服」里新建客服账号，每个入口一个，命名统一前缀便于排序与统计：

| 入口 | 建议账号名 | 链接填到 |
|---|---|---|
| 留资弹窗 | 顾问-入口-留资弹窗 | `wecomQrByChannel.modal` |
| 分享图带来的访客 | 顾问-入口-分享图 | `wecomQrByChannel.share` |
| 站外落地页 / SEO 页 | 顾问-入口-落地页 | `wecomQrByChannel.landing` |

先把链接填进 `index.html` 再验证（第 4 节的清单）。**当前若只建了一个码，三个入口都走兜底码，功能完全正常，
只是分不出来源** —— 可以先上线，再补码。

### 第 2 步：欢迎语与接待人员（跟着账号分）

每个客服账号单独配接待人员与欢迎语（首次进入会话自动发送）。三份欢迎语要**有差异**，
否则分码只分到了统计，没分到体验。可直接抄改：

- **留资弹窗**："您好，这里是 EuriskoTax 顾问。您刚在测算页留了信息 —— 直接把想核对的问题发过来就行，
  我会结合您的测算类型给您答复（不采集收入金额）。"
- **分享图**："您好，您是通过朋友分享的测算结果找到我们的。想核对哪一项？把情况发我，
  我按您所在城市的口径帮您看一下。"
- **落地页**："您好，您是从我们的个税文章过来的。文章里没讲到的情形可以直接问我，
  比如年终奖计税方式怎么选、专项附加扣除漏填怎么补。"

共同约束（合规）：不承诺"一定能退税 / 一定少缴"，统一用"核对 / 测算 / 参考"。

### 第 3 步：打标签

- 若你用的是**「客户联系」的渠道活码**：创建时直接开启「自动打标签」，客户扫码加好友时自动带上标签 ——
  这是最省事的路径。（证据等级：**二手来源**，多篇运营教程一致描述；**请你在后台确认后把结论回写本文件**）
- 若你用的是**微信客服**（本项目当前的 `kfid` 链接即微信客服）：微信客服偏"会话"而非"好友关系"，
  标签能力弱于客户联系，能否自动打标签**以你后台「客户」页实际可见为准**。
  替代做法（不需要额外能力）：**不同账号由不同接待人承接**（人即标签），
  或在上面的欢迎语里问一句、由顾问手工补标签。
  （证据等级：**未核实**，属于待确认项 —— 不编造没验证过的后台功能）

## 验证清单（建完必须做，约 5 分钟）

1. 三个码各用**个人微信**扫一次 → 是否进入三个不同客服账号的会话？
2. 后台「客户」列表：新客户是否带上对应标签 / 落在对应接待人名下？
3. 欢迎语是否按账号分别触发（不是同一句）？
4. 站点侧：桌面端打开留资弹窗 → 用 devtools 看 `#lead-wecom-link` 的 `href`，应为该入口的专属链接。
5. 分享图路径：生成一张分享图 → 扫它上面的码进站（URL 带 `?source=share`）→ 打开留资弹窗 →
   二维码应变成 `share` 专属码。
6. 兜底：把某个入口的码清空 → 该入口应回落到兜底码，**通道仍然可用**（不出现空白或裂图）。

## 常见错误

| 错误 | 后果 |
|---|---|
| 手工给链接拼 `?from=xxx` | 页面照开，回调拿不到来源（见结论 2） |
| 只建一个码却指望分出来源 | 企微侧无从判断，数据始终是"总数" |
| 分了码但接待人与欢迎语相同 | 统计分开、体验没分开，客户感知不到差异 |
| 三个入口同时改成新码、旧码立刻停用 | 已发出去的分享图/文章里的旧码失效，且无法回溯；旧码至少留一个迭代周期 |

## 更高级的可选路径（冷启动阶段不必做）

用《获取客服账号链接》接口（`add_contact_way`）为**同一个**客服账号生成带不同 `scene` 的链接：

- `scene`：≤32 字节，取值 `[0-9a-zA-Z_-]`，用于区分渠道；
- 链接上可再拼 `scene_param`（需 urlencode，encode 前原始长度 ≤128 字节），「用户进入会话事件」会原样带回。

适合渠道很多、不想建一堆客服账号的场景；代价是要有服务端调接口（`access_token` + 应用权限配置）。
本项目有 Node 后端，将来要做是可以做的，但在"先跑通承接"的阶段属于过度设计。
