## 0. 一页纸结论

| # | 判断 | 理由（一句话） |
|---|---|---|
| 1 | **手机端是主战场，桌面端是价值端** | 流量在手机（个体户 / 汇算人群主用手机），钱在桌面（小微企业主 / 财务 HR 要报表） |
| 2 | **手机端不只「算得快」，必须「算得完」** | ★★★ 客群中的个体户主用手机、且填的字段最多；算不完 → `calc_done` 掉 → 北极星直接掉 |
| 3 | **桌面端 = 信息密度 + 可信度 + 可交付** | 三者并列缺一不可；「可交付」是因为财务 HR 要拿结果给老板看，「可信度」是铁律「合规即卖点」的视觉表达 |
| 4 | **桌面不是「放大的手机」，手机不是「缩小的桌面」** | 桌面的价值是**密度/证据/交付物**；手机的价值是**引导**与**传播**。互相移植等于两边都做坏 |
| 5 | **明确否决：桌面左输入/右结果主从双栏** | 过不了「关键词 / 线索 / 收款」筛子，且要覆盖 4 个流程页，收益可被局部对照替代 |
| 6 | **自适应 ≠ 三个断点，是「设备矩阵 × 非宽度变量」** | 真正的坑在安全区、键盘、`100vh`、系统字号、折叠屏、触屏 hover —— 这些断点管不了 |
| 7 | **商业化引导必须是「有用的下一步」，不是广告位** | 产品铁律「不做广告」不只是道德偏好，它决定了引导卡的形态；且必须按计算类型动态决定（守 `BLOCKED_TYPES`） |
| 8 | **IA 结构已对，不再改结构；继续投 `nextTools` 互链** | 搜索 + 身份卡 + 场景组三层已覆盖 20 工具；规模再涨时让**搜索优先于浏览**，而不是加层级 |
| 9 | **光做浏览器不够：微信 + PWA standalone 必须单独适配** | 传播与留资全程在微信里（`download` 被拦 → 导出失效）；装机用户无浏览器返回键 → 向导必须接管 History。这两处在真实主流环境下是**功能是否可用**，不是观感 |
| 10 | **补齐「对账」覆盖：推导能力已有，但只覆盖了 1 个页面** | 阶段12 已实现 `buildFormulaSteps`（含 9 例单测），却只挂在综合所得前向页；其余 3 个完整测算与 20 个速算器都没有。这是**复用**，不是新建 |
| 11 | **完整测算要铺到每个税种 —— 但前提是先把通用求解器抽出来** | 它是核心功能不可简化；现状 4 个全是个税，且反向求解已手写 6 套。**继续复制会导致第 5 个就技术破产**，必须先抽内核（详见 §5.5） |
| 12 | **商业模式是两阶段接力，「 UI 铁律」也有阶段** | 前期引流→私域，后期工具自收费。前期的正确做法（免费算全部税种、登录永不阻塞）若不标注阶段，会**锁死后期变现**（详见 §1.5） |

**一条贯穿全文的纪律**：任何增加「算完之前」摩擦的东西都是负资产。
登录、注册、邀请码、多余字段、教程弹窗——全部排在 `calc_done` 之后。

## 1. 先看清我们在做什么：UI 的四层任务

商业链路是**两个阶段的接力，不是一条单链**（2026-09-17 澄清，原文写成单阶段是错的）：

```
前期：免费个税工具（获客）→ 高意图流量 → 线索 → 引入私域 → 服务成交（主营收）
后期：工具本身做出付费价值 → 功能订阅/增值 → 持续盈利（摆脱人力边际成本）
```

> **两个阶段要求的 UI 是不同甚至相反的**，详见 §1.5。本方案的 UI 原则默认处于**前期**；
> 前期的正确做法若被写成「永久铁律」，会直接锁死后期的变现路径。

把这条链路翻译成 UI 的任务，有**严格优先级**：

| 优先级 | UI 任务 | 对应指标 | 做不到会怎样 |
|---|---|---|---|
| 1 | 让用户**算完** | `calc_done` | 后面全部归零 |
| 2 | 让用户**看懂并信任结果** | 分享率 / 复访 | 财务工具没有信任就等于没有产品 |
| 3 | 让高价值人群**留下线索** | `lead_submit` | 有流量不变现 |
| 4 | 让低价值人群**带走分享图** | 分享回流 | 失去最便宜的分发渠道 |

北极星是 `lead_submit / calc_done` —— **分子分母都是 UI 直接决定的**。
这解释了很多设计取舍为什么「看起来反直觉」：

- 为什么不把登录前置？—— 它砍的是分母。
- 为什么结果页引导卡要长得像「帮助」而不是「广告」？—— 它同时影响分子和信任。
- 为什么打工人（谈薪）**不给服务引导**？—— 会拉高分子的假象、拉低分子的质量，还伤品牌。
  （已固化为 `BLOCKED_TYPES: ['reverse']`，是硬约束不是偏好）

> **推论**：本项目的 UI 优化目标不是「功能密度」，而是**每一步转化损耗最小**。
> 一个页面加一个功能，如果它让 `calc_done` 下降 1%，通常是不划算的。

## 1.5 两阶段商业模型：**「引流」阶段的正确做法，会锁死「收费」阶段的后路**

> ⚠️ **本章为新增**（2026-09-17）。澄清了商业模式是「**前期小程序引流进私域 → 后期工具自身收费**」之后，
> 回溯发现前稿有 **3 处会把后期锁死的设计**，且其中一处是**技术形态的事实错判**。

### ① 先纠事实：这个项目**不是微信小程序**

| 核实项 | 结果 |
|---|---|
| `app.json` / `project.config.json` | ❌ **不存在** |
| 全库 `appid` / `mp.weixin` / `miniprogram` | ❌ **0 命中** |
| 微信 JS-SDK | ❌ 未接入 |
| `manifest.json`（`display: standalone` + service worker） | ✅ 存在，是 **H5 + PWA** |

**所以当前代码库没有任何小程序。** 它是**纯网页 + PWA**，在微信里只能作为「网页」被打开。请明确「小程序」具体指哪一种：

- **(a)** 口语化指「在微信里打开的 H5」 → 形态无需改，但能力受限（见 ②）
- **(b)** 引流入口在别处（公众号 / 别的小程序），本 H5 只是承接端 → 需要对齐跳转与留资衔接
- **(c) 确实要做原生小程序** → ⚠️ **不建议**，会把后期变现的路堵死，见 ② 与下面结论

#### ✅ 结论：选 **(b) 变体——SEO 独立站为本体 + 微信为渠道 + 站外收款闭环**

三条理由（其中两条建立在「已经建成的事实」上，不是推演）：

1. **自有 SEO 流量已经建成，且不归任何平台管** —— `seo/` 已有 **21 个落地页** + `sitemap.xml` + `robots.txt`。
   主动搜索「年终奖怎么计税」进来的人，**意图强度远高于小程序泛流量**。这是唯一不受平台管控的获客渠道。
2. **变现闭环已按「天然绕开应用商店」的方式建成** —— `ProCode` 的设计原话是
   「**线下收款后**由运营批量生成并交付」。支付行为发生在站外，站/小程序内只有「兑换」，
   **因此不受 iOS 虚拟支付禁令约束**（不展示购买按钮也能合规交付权益）。这是目前唯一正确的解法，**不该推翻**。
3. **做原生小程序是负收益** —— 要重做一套、受两条红线夹击，而你要的「引流 + 收费」现状**两者都已具备**。

> 若确实需要微信流量：正确做法是**让这个 H5 在微信内被分享传播**（现在就能做），
> 而不是重做原生小程序。**务必守住：私域靠「工具值得留住」，不靠放二维码。**

### ② 微信生态有两条红线，**正好卡住这个模型的两端**

| 阶段 | 红线 | 后果 |
|---|---|---|
| **前期「引流进私域」** | 平台明确严打「站外导流 / 私域留资」——任何「加微信 / 进群 / 扫码 / 打电话 / 留联系方式」式的引导 | 设计方案若内含「放二维码、诱导加好友」，有被限流/封禁的风险 |
| **后期「靠功能收费」** | **iOS 虚拟支付限制**：iOS 端小程序**不得展示任何购买/支付功能、页面、按钮**，连价格标签都不能有；也不得引导至外部网页完成支付（《微信小程序平台运营规范》5.13 / 14.6）。即便现已「破冰」，iOS 仍要抽 **15% 苹果税 + 5% 微信技术服务费** | 「卖高级测算功能」在 iOS 端基本不成立 |

**由此得到一个反直觉但关键的结论：**

> **当前 H5 + PWA 形态，恰恰是「后期靠功能收费」的正确载体。**
> 把它改造成原生小程序，等于主动给自己的变现套上枷锁。

正确分工是：**微信是「渠道」，H5/PWA 是「本体」**。
在微信内承担获客与轻量计算，**不要在微信内试图完成付费闭环**；
付费引导到 PWA 正式版（「在浏览器打开」/ 扫码），那里不受此约束。

### ③ 最尖锐的一条：现有的「产品铁律」是前期正确的，但会锁死后路

前稿写了两条铁律，它们是**获客期的最优解**，但没有标注「仅适用于前期」：

| 现有铁律 | 前期的确正确 | 但它会挡住什么 |
|---|---|---|
| **「免费版算全部税种」**（§2.2 产品铁律 1） | 免费换流量，正确 | 后期**没有东西可卖** —— 这是最直接的死锁 |
| **「登录入口始终可见，但永不阻塞」**（§2.2②） | 登录砍分母，正确 | 无法识别用户 → 无法做付费门禁与跨端订阅 |

**处理原则（重要）**：**不改这两条，但给它们加阶段标注与翻转点**——
把它们定义为「**前期常真**」，而不是「永久铁律」。
翻转时 UI 的形态变化要能承受，见下面的阶段翻表。

### ④ 阶段翻表：哪些 UI 原则会随阶段反转

| UI 决策 | 前期（引流→私域） | 后期（工具自收费） |
|---|---|---|
| 登录 | **永不阻塞**（保持） | 仍然不阻塞计算，但**在付费触点**才要求登录 |
| 免费范围 | 全部税种免费（保持） | 划出付费边界，**收的不是「算」，是「算之外」** |
| 结果页主 CTA | **留资 / 咨询**（拉 `lead_submit`） | 留资 CTA 会让想用工具的人反感，需让位于产品 CTA |
| 客群价值排序 | 老板 > 财务 > 打工人 | **打工人反转成订阅主力**（见 ⑤） |

### ⑤ 客群价值排序会随阶段翻转 —— §3.2 现在的表是「前期表」

前稿把**打工人定为 ★☆☆ 且「只出分享图、不出服务引导」**。
这在「卖人工服务」下是对的（单价低、付不起顾问费）。

但**一旦后期是「工具自收费」**，排序会变：

| 客群 | 前期（服务成交） | 后期（订阅收费） |
|---|---|---|
| 打工人 / 汇算纳税人 | ★☆☆ 转化不成服务 | **★★☆~★★★ 反转**：量大、每年必回来（汇算/谈薪）、单价低但**续费率**才是命门 |
| 个体户 / 小微企业主 | ★★★ 高客单 | ★★★ 仍高，但**总量有限** |

> **给 §3.2 的修正**：不应把客群价值写成静态常量，要标成「**随商业阶段变化**」。
> 否则后期会按一张过期地图做产品决策。

### ⑥ 「卖什么」已不是假设——三档权益体系已经落地

上一点曾被写成「建议」。核实后发现**早已实现**：付费全部落在「算之外」，且已跑通三条腿。

| 付费点 | 门禁现状 | 位置 |
|---|---|---|
| **云端历史多端同步** | 基础版仅存本机；专业版跨设备 | `history-sync.js`（已有 PRO gate） |
| **多方案对比数量** | 免费 `MAX_FREE` / 专业版 `MAX_PRO` | `scenario-store.js limitFor(isPro)` |
| **精装版计算报告** | 见 ⑦ | `final-report.js` + `app.js` |

另有内容分层（`contentService` 的 all / free / pro）与 **14 天专业版体验**（`authService`），
说明「免费 → 体验 → 付费」链路已铺好。这也解释了为什么 §5.5「每个税种都要完整测算」如此重要：
**它是付费值的厚度本身**，没有它，上面三条腿都是空壳。

### ⑦ 计算报告收费：**已经实现了，而且实现方式比建议的更优**

```
免费版 / 未登录 → 导出普通 PDF（既有能力，无倒退）
专业版         → 精装版报告：封面 + 政策要点 + 税负结构图表
```
依据：`final-report.js:310`（`if (!isProUser())` 回落到原有导出）与 `app.js:935` 注释
「免费版保留现导出——无倒退」。

**这个设计最漂亮之处：它不是「免费用户导不出」，而是「免费能导，专业版导得更好」。**
三条铁律因此全部守住：不算不了、**不伤 `calc_done`**（计算过程零门禁）、**不伤 `lead_submit`**（是升级不是拦截）。

> ⚠️ **关键建议：绝不要改成「免费用户完全不能导出」。**
> 「能导出但更精美」是**升级感**；「导出要钱」是**勒索感**。
> 后者会砸掉 SEO 口碑与分享率——而 SEO 正是 §1.5① 认定的主力渠道。这是自杀式改动。

**但要形成闭环还差三件事：**

| 缺口 | 问题 | 怎么补 |
|---|---|---|
| **1. 付费预期没建立** | 用户点导出前不知道有精装版 → 没预期就没转化 | 导出口**事前**预告「专业版含封面 / 政策要点 / 图表」 |
| **2. 与 `lead_submit` 抢 CTA** | 报告收费口做强了会吃掉留资（北极星） | **让报告成为私域的钩子，而不是付费墙** —— 见下 |
| **3. 缺复购入口与到期提醒** | 现在是一次性兑换码，撑不起「持续盈利」 | 续期机制已有（`duration_days` 可叠加），缺的是**到期前提醒 + 再次购买入口** |

#### ⭐ 缺口 2 是整个商业模型的枢纽：把前后两阶段串起来

不该让「留资」和「付费」互相抢，而应让它们是**同一个动作**：

```
SEO / 微信引流 → 算完 → 想要精装报告 → 留资进私域 → 运营发 ProCode
              → 用户真正体验到 pro 价值 → 次年 / 多成员 / 多端同步时续费
```

**一张口同时完成「引流 + 私域 + 付费教育」三件事。**
既拉了 `lead_submit`，又让用户免费体验到付费价值、完成持续盈利所需的教育——
这正是「前期引流 → 后期自收费」两阶段之间**缺失的那座桥**。

### ⑧ 留资链路的合规做法

不能用「扫二维码加微信」这类站外导流。应走**平台愿意看见的路径**：

- 微信侧走官方能力（客服入口 / 已认证主体的官方组件），而不是放个人号二维码
- H5 侧：`lead-modal.js` 已有一致性强校验基础（`lead/` 三个模块已具备），保持「明示同意 + 可拒绝 + 说明用途」
- ⚠️ 若确要接入手机号快速验证类能力：它**按次收费**（快速验证 ¥0.03/次），且**在流程中断点强索取属违规**，不能做成不填就不给算
- 「加入企微」的正确姿势：**把它当作「交付/咨询」的一个自然出口**，而不是弹窗

### ⑨ Phase 3.5① 的交互形态与合规护栏

> 顺序不能反：**先让合规把形态收紧，再谈转化。** 下面四条硬约束决定了它长什么样，不是事后装饰。

| 约束 | 来源 | 对形态的影响 |
|---|---|---|
| **计算过程零打扰** | Phase 1 的 gate | 钩子**只能出现在算完之后**，绝不进填参流程 |
| **站内零购买语义** | §1.5② 微信 / iOS 红线 | 控件与文案不得出现「购买 / 支付 / 价格 / ¥ / 订阅」 |
| **不是弹窗，是出口** | 上面 ⑧ | 嵌进用户**本来就要做**的「导出」动作里 |
| **必须复用现有 consent** | 个保法 | 只能走 `lead-modal.js`，另起一套即绕过硬约束 |

#### 形态：导出时给「两个版本」，而不是给一道障碍

```
点「导出」→
┌─────────────────────────────────┐
│ 选择导出版本                      │
│                                 │
│ ○ 标准版 —— 你正在看的完整结果     │
│   PDF，免费，现在即可导出          │
│                                 │
│ ○ 精装版 —— 封面 + 政策要点        │
│   + 税负结构图表，可直接交付        │
│   属专业版权益                     │
│                                 │
│ [ 导出标准版 ]                    │
└─────────────────────────────────┘
```

选精装版后：**已 pro → 直接生成**（即现状 `final-report.js:310` 逻辑，零改动）；
**非 pro → 进「如何获得权益」页** ← 钩子在这一步，**且只在这一步**。

#### 「如何获得权益」页的文案边界（合规关键）

| ❌ 禁用 | ✅ 说法 |
|---|---|
| 购买 / 支付 / 价格 / ¥ / 订阅 / 付费 / 立即 / 限时 / 错过 | 「精装版报告属专业版权益。留下联系方式，我们把权益码发给你。」<br/>＋「已有权益码？在此兑换」（入口已存在） |

**为什么「零购买语义」同时满足合规与商业目的：**

- **平台视角**：站内不发生支付行为，收款在站外/私域完成 → 不触发虚拟支付条款，iOS 也无需拦按钮。
- **用户视角**：从「被收费」变成「被赠送」——不只是措辞差异，**这正是 Phase 3.5 能保住 `lead_submit` 的根本原因**。

#### 四条护栏（须做成验收项，缺一不可）

1. **绝不采集金额** —— 复用 `lead-modal.js`（已承诺「不采集任何收入金额」，`consent` 必勾选 + 后端留痕）。
   ⚠️ **严禁**为「让报告更精准」让用户在钩子表单里补填收入明细：
   那会把一张非敏感表单变成**采集个保法敏感个人信息**，性质完全不同。
2. **`BLOCKED_TYPES` 必须覆盖钩子** —— 谈薪（`reverse`）页永不出现；且要接进 `verify:local` 门禁断言，
   沿用 `lead-touchpoints.js` 现成的 `ALLOWED_TYPES` / `BLOCKED_TYPES` **双保险**，不另起第二套。
3. **频率克制 + 可关闭** —— 用户选「标准版」后不反复出现。
4. **无紧迫感文案** —— 不用限时 / 立即 / 错过。

## 2. 竞品拆解：取什么，弃什么

既有竞品表（阶段15 方案 §4）是**能力维度**，这里补**UI 与交互维度**。

### 2.1 逐家拆解

| 产品 | 做对了什么（✅ 取） | 做错了什么（❌ 弃） | 我们怎么用 |
|---|---|---|---|
| **个人所得税 App**（官方） | 首页**场景宫格**：用户按「我要办什么事」进入，不是按税种；权威感来自克制 | 重流程、强制登录、结果藏在多层申报流程里，算个税像在填表 | ✅ 首页按**场景**组织（不是按税种）；❌ 绝不强制登录前置 |
| **TurboTax 类**（国外报税） | **一次只问一个问题** + 明确进度 + 随时可返回 + 每问一句「为什么问这个」 | 流程过长且**不能跳**，用户被困在向导里；进度条给人压迫感 | ✅ 引导式分步 + 可返回 + 实时预览；❌ 不做强制顺序，允许跳到目标字段 |
| **代账 SaaS**（云账房 / 柠檬云 / 慧算账） | 桌面**工作区感**：左树 + 右工作区，数据密度高 | 层级深、术语会计化，面向**会计**不面向**老板/个人**；新用户上手成本极高 | ✅ 桌面要「工作区感」；❌ 不要左侧深树（我们层级浅，用顶部 Tab） |
| **免费计算器小站** | **一屏算完、零门槛、无需注册** —— 这是它们能拿到搜索流量的全部原因 | **算完即走**：无留存、无信任沉淀、无法变现 | ✅ 保留「零门槛一屏算完」；❌ 用**结果页**接住，解决算完即走 |
| **记账 / 金融 App**（支付宝 / 微信 / 随手记） | 底部 Tab 稳定心智；**FAB 承载唯一主行动**；金额是绝对视觉主角 | 功能堆叠到 Tab 承载不了，最终变成「第二个首页」 | ✅ 底部 **3** Tab + FAB 助手（**已是现状**）；❌ Tab 只做导航，不做内容聚合 |
| **Notion / 飞书 / Linear** | 浅层级用**顶部 Tab**，不浪费左侧栏；键盘优先；空状态有明确出路 | 桌面形态搬到手机就是灾难（它们也确实弱） | ✅ 桌面用顶部 Tab；❌ 不把桌面 IA 平移到手机 |
| **Stripe 类**（表单体验） | 金额输入带前后缀、就地校验、错误不弹窗、成功有明确反馈 | 面向开发者，信息密度对普通纳税人过高 | ✅ 金额输入的交互细节；❌ 不抄它的密度 |

### 2.2 最关键的三条

**① 单端惯例可抄，双端策略无可抄对象。**
没有任何竞品做过「桌面办公 + 手机速算」的任务分流——**因为它们的双端本就是两个产品**。
我们是唯一「一套产品跨两端」的。所以：只采用已被验证的**单端**惯例，双端策略上不创新（0 用户，无数据做 A/B）。

**② 竞品的共同糟粕是把「登录」放在「算」之前。**
官方 App 强登录是因为它要真申报；代账 SaaS 强登录是因为它要卖席位。
**我们两样都不是**——计算在浏览器本地、免费版算全部税种（产品铁律 1）。
强登录对我们是纯损耗。**登录入口始终可见，但永不阻塞。**

**③ 「算完即走」不是小站的疏忽，是它们的商业模式决定的——而我们必须解决它。**
接住用户的不是弹窗，是**结果本身的价值**：让结果页值得停留（可核对、可保存、可分享、可打印）。
引导只是「下一步」的自然延伸，不是中断。

### 2.3 我们自己要解决的问题（基于已核实的现状）

| 问题 | 证据 / 现状 | 方向 |
|---|---|---|
| **手机端「算得完」还没被保证** | 定稿 §3.2 实测：任务页固定层 **约 22%**（目标 ≤18%）。个体户/汇算客群恰恰是在手机上填字段最多的人 | §5.3 降输入成本（不止压缩固定层） |
| **20 个工具的入口效率拐点** | `tool-registry.js` 已有 5 个场景组 + 5 张身份卡，但仍依赖浏览；规模再涨，分组浏览的效率会低于搜索 | §5.1 搜索优先于浏览 |
| **桌面端「可交付」偏弱** | 工具页已加宽 1024（S5 已做，信息密度有改善）；但导出/打印仍是零散能力，未成体系 | §4.2 桌面三要素之三 |

> **已经做对的（不要重复建设）**：
> 「我是谁」身份入口 + 5 场景组 + `nextTools` 互链 + `pitfalls` 易错口径 —— 这在同类产品里是超前做法，
> 本方案不再提「场景化改造」，那是已经解决的问题。

## 3. 客群 → 任务 → 端：三维分流

> 早期判断「手机 = 速算，桌面 = 完整测算」**已被否决**（见定稿 §1）。
> 原因：商业价值最高的两类（个体户、小微企业主）偏偏主用手机/桌面各一，
> 按设备能力分流会把最值钱的客群推到他们不用的端。

### 3.1 分流不是按设备，是按任务

三个维度共同决定形态：

| 维度 | 取值 | 决定什么 |
|---|---|---|
| **任务长度** | 30 秒 / 5 分钟 / 30 分钟 | 用引导式还是表单式 |
| **是否需要交付物** | 看一眼 / 要报表 / 要批量 | 用不用桌面能力 |
| **是否复用历史数据** | 一次性 / 反复调 / 多人份 | 要不要账号（注意：要账号 ≠ 阻塞计算） |

### 3.2 客群 × 任务 × 端 映射

> ⚠️ **本表是「前期」地图**（商业阶段 = 服务成交）。**它不是永久排名** ——
> 一旦进入后期的「工具自收费」阶段，**打工人会从 ★☆☆ 反转成订阅主力**（量大、每年必回访）。
> 用这张表去做后期的产品决策会做错，**翻转见 §1.5⑤**。

| 客群 | 商业价值 | 典型任务 | 主端 | UI 形态 | 商业化动作 |
|---|---|---|---|---|---|
| **个体户 / 个独 / 合伙（经营所得）** | ★★★ | 经营所得汇算、扣除项核对 | **手机** | 引导式分步 + 结果页情境卡 | 强引导 + 留资（代账/申报，可年费） |
| **小微企业主** | ★★★ | 用工成本、预算、多方案对照 | **桌面**（手机补位） | 对照式工作区 + 报表导出 | 顾问 + 预算表页 |
| **财务 / HR** | ★★★（第二曲线） | 批量测算、发薪方案、导出 | **桌面** | 批量 + 表格化 | B 端 API（阶段16） |
| **年度汇算纳税人** | ★★☆ | 专项附加扣除是否填全、退/补 | **手机** | 引导式 + 结果页核对 | 汇算代办/咨询，单次 |
| **打工人（谈薪 / 月薪）** | ★☆☆ | 到手倒推税前、年终奖怎么发 | **手机** | 极速单屏 | **只出分享图，不出服务引导** |

### 3.3 由此得出的两端定义

**手机端 = 引导式速算 + 必须「算得完」 + 结果传播**

> ⚠️ **这是本方案最重要的一条修正**。手机端不只要求「算得快」，**必须能算完重任务**。
> 理由：★★★ 客群中的个体户、以及 ★★☆ 的汇算人群**主用手机，且恰恰是填字段最多的人**。
> 若手机上重任务算不完 → `calc_done` 掉 → 北极星 `lead_submit / calc_done` 直接掉。
> 「手机 = 只能速算」是错的，那是把最值钱的客群推到他们不用的端。

- 承接绝大多数流量（个体户 + 汇算 + 打工人，三类都在手机）
- 核心指标：`calc_done`、**重任务的完成率**、分享率
- 形态：一次一个问题、进度可见、结果先给结论
- **但更关键的是降输入成本**：预填默认值 / 上年结转 / 可跳过步骤 / 草稿自动保存 / 断点续算

**桌面端 = 信息密度 + 可信度 + 可交付**

这三个词是并列关系，缺一不可：

| 要素 | 含义 | 为什么桌面才成立 |
|---|---|---|
| **信息密度** | 单位屏呈现更多有效信息，多列网格、并排对照 | 手机给不了横向空间，硬塞只会变成长条堆叠 |
| **可信度** | 政策依据、税率来源、失效提示、免责声明可见 | 财务/HR 要拿结果给老板看，需要能追溯 |
| **可交付** | 导出（CSV/PDF）、打印、多方案留存 | 交付物本质是「给别人看」；桌面做**完整交付**（文件 / 打印），手机做**轻量交付**（长图 / 复制，见 §8.6）——两者是同一能力的两种落点，不是互斥 |

- 承接绝大多数线索价值（小微企业主 + 财务 HR，客单价高）
- 核心指标：`lead_submit`、导出/打印次数、停留时长

> **一句话**：手机端负责「让更多人在手机上算完」，桌面端负责「让值钱的人拿得出东西、信得过」。

**⚠️ 已明确否决的做法：桌面双栏（左表单 / 右实时结果）**
完整否决理由与替代方案见 §5.3（此处不重复展开，避免同一条理由散落四处）。

## 4. 双端：做不做桌面？做，但先说清桌面为谁而做

### 4.1 结论：做

三条理由，**缺一条都不值**：

1. **客群里有天然桌面人群** —— 小微企业主、财务 HR 在办公室用电脑，这不是偏好是工作场景。
2. **交付物只在桌面成立** —— 打印、导出、多方案并排对照，手机做不了也不该做。
3. **B 端 API 是第二增长曲线**（阶段16 前置）—— 桌面端是它的产品预演与需求验证场。

### 4.2 桌面端的三要素：信息密度 · 可信度 · 可交付

最容易犯的错：把桌面端做成「更气派的导航 + 更大的卡片」。
**那是把预算花在没人买单的地方。**

| 要素 | 具体做什么 | 对应客群 |
|---|---|---|
| **信息密度** | 20 个工具多列网格（S5 已做：工具页 768 → 1024）；多方案并排（年终奖单独/并入/最优）；结果表不折叠 | 小微企业主、财务 HR |
| **可信度** | 政策依据与税率来源可见；优惠到期由注册表 `statusOf` 自动显示「已过期/延续中」；易错口径前置；免责声明统一 | 财务 HR（要给老板看）、所有人 |
| **可交付** | 导出（CSV / PDF）、打印、多人份留存 | 小微企业主、财务 HR、汇算人群 |

**为什么可信度值得单列**：产品铁律里写着「合规即卖点」，而**可信度是合规的视觉表达**。
财务人员拿一份没有政策依据的结果去跟老板汇报，这个结果就没有价值——这不是信任偏好，是使用场景决定的。

**不做**：桌面左侧深层级树状导航。
那是代账 SaaS 的形态，服务对象是会计；我们的桌面用户是**老板和财务负责人**，层级浅、要结论。
（我们正好 3 个平级模块 → 顶部 Tab 足够，引左侧栏是浪费。）

### 4.3 两端形态的硬边界

| 维度 | 手机端 | 桌面端 |
|---|---|---|
| 导航 | 底部 3 Tab：首页/工具/我的（`< 768px`） | 顶部 Tab 行（≥ 768px）—— **已落地 S2** |
| 主行动 | FAB 悬浮球（助手） | 助手为推开式侧栏（≥1280px）—— **已落地 S6** |
| 输入 | 引导式分步，一次一问 | 完整表单，同屏可见 |
| 结果 | 结论优先 + 明细折叠 | 输入与结果**同屏** |
| 容器 | 单列，全宽 | `--c-default` 1024px 限宽（**已落地 S5**） |
| 输出 | 分享图（传播） | 导出 / 打印（交付） |

> 两端**状态同源**：`syncNav()` 一份状态驱动两端 DOM（已落地 S2，5 条断言钉住）。
> 新增导航项时只改一处，不允许两端各写一套。

## 5. 信息架构

### 5.1 现状 IA（已核实，不要重复建设）

```
底部 / 顶部 Tab（3 个，双端同一份状态 syncNav() 驱动）
  首页 · 工具 · 我的
+
FAB 悬浮助手（情境位，不占导航位）
```

**首页** ── 三层递减的组织方式（`tool-registry.js` 已实现）：

| 层 | 内容 | 解决什么 |
|---|---|---|
| **搜索入口** | 直接搜「年终奖」「增值税」「社保」 | 工具数 ≥20 时，**搜索比浏览快** |
| **我是谁（5 张身份卡）** | 上班族 / 自由职业·兼职 / 个体户·小店 / 企业财务·HR / 高管·股东·临近退休 | 用户不一定知道年终奖归哪类，但**一定知道自己是不是上班族** |
| **最近使用 / 最近计算** | 基于本地历史 | 复访者直接续上次动线 |

**工具页** ── 5 个场景组 + 完整测算（排在最后，不与其他组混排）：

| 组 | 覆盖 |
|---|---|
| 工资与到手 | 月薪个税、谈薪倒算、年终奖、专项附加扣除、年度汇算 |
| 一次性收入与特殊所得 | 劳务报酬、股权激励、离职补偿、提前退休、外籍津补贴 |
| 税优与养老 | 个人养老金、税优健康险、企业年金 |
| 社保与用工 | 社保公积金、企业用工成本、残保金与工会经费 |
| 企业与经营 | 增值税、企业所得税、附加税与印花税、个体户经营所得 |
| **完整测算**（末位） | ⚠️ 见 §5.5。现状只有个税 3 类 + 反向；**目标态是按税种铺开** |

> **「完整测算」排末位是刻意的**：混排会让同一组里出现两个「算工资」的入口，用户更懵。
> 它也不是「另一种工具」，而是**同一种任务里填得更全的那一种**——这是用户心智能理解的差异，
> 而早期「深度测算」是按实现形态起的名字，用户心里没有「深度」这回事。
>
> ⚠️ **但现状把它列成 4 项是错的**：「综合所得 / 经营所得 / 分类所得 / 反向倒算」里，
> 前三个是**「算什么」（所得类别）**，第四个是**「怎么算」（求解方向）**——
> 两个正交维度被压在同一层。修正见 §5.5。

**每个工具自带三段**（已有结构，本方案确认并强化）：
`结果` → `易错口径（pitfalls）` → `下一步（nextTools 互链 / 保存 / 导出 PDF）`

> **`nextTools` 互链是被低估的资产**：它把一次测算接成一条动线（月薪 → 年终奖 → 汇算），
> 直接提升 `calc_done` 的**人均次数**，也让高意图用户在多个场景里被触达。
> 本方案的取向：**继续投入互链质量，而不是改 IA 结构**（结构已经对了）。

### 5.2 本方案对 IA 的唯一主张：规模再涨时，搜索要优先于浏览

20 个工具靠 5 张身份卡 + 5 个分组还能承载；
当阶段15/16 继续补税种（每一个新税种 = 一批关键词 + 一个工具），**分组浏览的效率会掉到搜索之下**。

| 阈值 | 主张 |
|---|---|
| ≤ 25 个工具 | 现状（身份卡 + 分组）够用，不动 |
| > 25 个 | **搜索框前置为首页第一屏**（现状已是第一层，但视觉权重还不够）；身份卡降为「不知道搜什么时的引导」 |

不做：**任何形式的左侧树状分类**。那是在用树的复杂度解决搜索能解决的问题。

### 5.3 桌面端：顶部 Tab + 宽容器（不做主从双栏）

```
顶栏（登录 / 主题 / 安装 / 用户菜单 / plan pill 插槽）
  ────────────────────────────────────────
  Tab 行：首页 · 工具 · 我的        （3 个平级模块）
  ────────────────────────────────────────
  内容区  ← --c-default 1024px 限宽，多列网格
```

**为什么不用「左输入 / 右结果」主从双栏**（之前提过，已被否决，本方案不复活）：

| 否决理由 | 说明 |
|---|---|
| 过不了商业筛子 | 不带关键词、不带线索、不解锁收款——这是资源筛子的三个口子，一个都不占 |
| 改动面太大 | 完整测算要按税种铺开（目标 9 个税种），页面只会更多，风险与收益更不对等 |
| 收益可被替代 | 「看结果」的需求由结果页承担；「同屏对照」只对多方案场景成立，可以按需做局部对照，不必改全局版式 |

从栏：助手 **push 侧栏**（推开而非覆盖，≥1280px，已落 S6）——桌面决策场景需要「边看边问」。

### 5.4 两端共享

- 同一份导航状态（`syncNav()`）
- 同一套设计令牌（`tokens.css`）
- 同一套内容：桌面**不提供手机没有的功能**——只提供手机**做不好**的呈现方式

> 这条是防漂移的锚：一旦桌面开始长手机没有的功能，就等于养第二套产品。

## 5.5 完整测算：目标是「每个税种一套」，但**不能按现在的写法加**

> ⚠️ **本章前几稿完全缺失**。前几稿把 4 个完整测算当作常数使用，既没识别出它是**目标态的一小部分**，
> 也没识别出**当前写法在结构上无法支撑扩展到每税种**。
>
> 已核实（2026-09-17）：
> - `tax-registry.js`：**27 个政策条目 / 7 个 category**（`iit`/`vat`/`cit`/`surtax`/`stamp`/`social`/`fee`），去重后约 **9 个独立税种/费种**
> - `tool-registry.js` 的 `DEEP`：**4 项，全部为个人所得税**（综合所得 / 经营所得 / 分类所得 / 反向倒算）
> - `tax-calculator.js`：**2600+ 行，反向求解写了 6 套**（综合所得 3 套 + 经营所得 3 套），且单函数内仍有复制块

### ① 产品本意 vs 现状的完整差距

| | 现状 | 目标态 |
|---|---|---|
| 覆盖 | 只有个税（3 类 + 反向） | **9 个税种/费种各自一套** |
| 企业税种（增值税、企业所得税、附加税、印花税、残保金、工会经费） | **完全没有完整测算**，只有速算器 | 各自有完整测算 |

这不是边缘差距：**企业对应用户集中在 ★★★ 客群**（小微企业主、财务 HR）。
现在的完整测算只服务了三类个人，等于把最值钱客群的完整需求挡在门外。

### ② 口径修正：reverse 是「模式」，不是「所得类别」

`reverse`（反向倒算）**不应与前 3 项并列**。它是求解方向，可以作用于任何税种
——事实也正是如此：经营所得的反向早已实现（`calculateBusinessFromTargetRate/FromMonthlyNet/FromTargetTax`），
只因为它被单列为"第 4 项"，反而**掩盖了「每种所得都能反向」**，用户会以为只有综合所得能倒算。

**正确结构是二维的**：

| | 正向（已知收入 → 求税） | 反向（已知到手/税额/税负率 → 求收入） |
|---|---|---|
| 综合所得 | ✅ | ✅ 已有 |
| 经营所得 | ✅ | ✅ 已有（但被埋没了） |
| 分类所得 | ✅ | — |
| **增值税 / 企业所得税 / …** | **目标态** | **目标态** |

所以 UI 上：**求解模式应是页面内的切换，不是顶层的一个独立入口。**

### ③ 致命问题：组合爆炸已经发生

现有 `tax-calculator.js` 里，反向求解是**逐 taxon 手写的**：

```
calculateFromTargetRate / FromMonthlyNet / FromTargetTax      ← 综合所得
calculateBusinessFromTargetRate / FromMonthlyNet / FromTargetTax ← 经营所得
```

两套逐行同构，差异只有税率表与一个"减半优惠"。
更严重的是 `calculateBusinessFromTargetTax` 单个函数内部，`actualTax`/`halvingTax`/`halvingThreshold`
就有 **4 处近乎相同的复制块**。

**外推**：9 个税种 × (正向 1 + 反向 3) ≈ **27 套手写**，文件奔着一万行去。
**结论：按现在的写法加第 5 个完整测算 = 技术破产。**
所以「先提炼通用内核」不是工程洁癖，是**能不能继续加税种的前提**。

### ④ 幸运之处：地基已经存在，但没被接上

`tax-registry.js` 已经提供了完整测算需要的元数据，只是**现在的 `performTaxCalculation` 完全没用它**
（`collectTaxInputData` 直接读 DOM，`computeDeductions` 硬编码十几项扣除）：

| 已有能力 | 正好解决什么 |
|---|---|
| `listByCategory(category)` | **「按税种组织完整测算」的现成入口** |
| `basisOf(id)` 政策文号 + 可选 url | §8.6 要求的「政策依据页内展开」+ §4.2「可信度」 |
| `statusOf(id, now)` + `expiresOn` | 自动判定「已过期/延续中」，一并解决 pitfalls 里硬编码政策的双轨问题 |
| `resolveParams(id)` | 声明式取参数，不必传值 |

**这条路也不是未经验证**：20 个速算器已经在用 `tool-registry` 的 `fields` → `fieldHtml`/`visibleFields`
**自动生成表单**。所以正确路线是：**把速算器已验证的「声明式」做法升级到完整测算**，
而不是继续复制 `index.html` 里的静态页面。

### ⑤ 设计：测算描述符（calc spec）+ 通用内核

所有税种的正向测算本质是同一张图：

```
收入汇总 → 逐项扣除（各有口径/上限） → 应纳税所得额 → 查税率表 → 税额
                                                    ↓
                                            优惠/减免（有顺序、有门槛、有期限）
                                                    ↓
                                                实际应纳
```

反向求解只是在**单调关系上做二分**。真正可变的三要素都可声明：**税率表 / 扣除项清单 / 优惠链**。

```js
{
  id: 'vat',
  policyIds: ['vat', 'vat-small-scale'],   // → basisOf + statusOf 自动带出
  income:     [{ key, label, when, default }],
  deductions: [{ key, label, cap, when }],
  taxTable:   '*resolveParams(vat).rules', // 累进 / 比例均可
  reliefs:    [{ kind: 'halve', threshold, when }],
  solvable:   ['tax', 'net', 'income']     // 声明后自动获得反向，不再手写
}
```

内核对每个税种**自动成立**，不必再写：

| 能力 | 说明 |
|---|---|
| `runForward(spec, input)` | 正向：明细 + 税额 |
| `solve(spec, target, mode)` | 取代现有 6 套（未来 27 套）手写二分 |
| `buildSteps(spec, result)` | 泛化 `buildFormulaSteps`，推导链自动有 |
| `basisOf` + `statusOf` | 合规追溯 + 到期提示，自动有 |

> **额外收益**：这一层打通后，**§7.2「20 个速算器缺推导链」会被顺带解决** ——
> 速算器也能走同一内核，无需再单独给 `*-quick.js` 补 `steps`。这比逐个补更快、也更不容易漂。

### ⑥ IA：浏览层与能力层分离

`tool-registry.js` 第 30 行「分组按人/场景而不是按税种 —— 用户不按税种思考」这条**不用推翻**，要分清两层：

| 层 | 组织方式 | 是否需要改 |
|---|---|---|
| **浏览入口** | 仍按身份 / 场景 | 不用改（已验证） |
| **能力层** | 按税种组织 | 新增 |

具体形态：「完整测算」组从 4 项改为按 `listByCategory` 铺开
（个税含综合/经营/分类、增值税、企业所得税、附加税+印花税、社保公积金、残保金+工会经费），
但**入口仍由身份卡过滤露出** —— 个体户看到的是**与他相关的那几个税种**，
而不是甩给他 9 个税种名词。**用户依然不需要学税种名称。**

### ⑦ 落地路径：必须三步走，不可跳步

| 步 | 做什么 | 为什么是这个顺序 |
|---|---|---|
| **1. 提炼通用求解器**（不加任何功能） | 把现有 6 套模式复制收敛成一个 `solve()`，4 个流程行为**完全不变** | **能否加第 5 个的前提**。跳过这步直接补税种 = 把技术债翻倍 |
| **2. 打样一个企业税种** | 用描述符驱动重做第一个**非 IIT** 完整测算 | 验证描述符够不够用。描述符未稳就批量 = 大规模返工 |
| **3. 批量接入** | 其余税种按商业价值排序逐个接入 | — |

**第 2 步选企业所得税或增值税**，三者同时成立：对应 ★★★ 客群、主用桌面、且是 Phase 3 的关键内容供给。

### ⑧ 一处被忽略的强耦合（会改变 §10 排序）

Phase 3「桌面可交付（导出/打印体系化）」的价值**高度依赖企业税种有没有完整测算**。
若只有个税，导出去的仍是**个人个税测算表**——对小微企业主吸引力有限。

> **所以「企业税种完整测算」必须排在 Phase 3 之前**，而不是之后。

这条同时影响北极星的两侧：不仅拉 `calc_done`，更直接拉动 **`lead_submit`**（★★★ 客群的高价值线索），
并为阶段16 的 B 端 API 提供真实的需求验证场。

## 6. 版式与排版

### 6.1 栅格与容器（已落地，本文确认方向）

| Token | 值 | 用途 |
|---|---|---|
| `--c-narrow` | 720px | 速算器 / 表单（行长 65–75 字符最优） |
| `--c-default` | 1024px | 首页 / 列表 / 网格 |
| `--c-prose` | 760px | SEO 正文阅读 |

**网格列数跟「容器还剩多少宽度」走，不跟视口走**（已落地 S5：`auto-fill minmax(260px, 1fr)`）。
原因：视口变宽和侧栏推开是**同一结果的两种原因**，按视口写死会漏掉后者。

### 6.2 中文排版特化

这是通用设计系统不会告诉你、但对中文产品致命的三条：

| 项 | 规则 | 为什么 |
|---|---|---|
| **行高** | 正文 **1.7**（英文惯例 1.5 不够） | 方块字没有上下延伸部，行距不足会糊成一片 |
| **段间距 > 行间距** | 段落间 ≥ 1.5 倍行距 | 中文没有首行缩进习惯，靠间距分组 |
| **数字等宽** | 金额 / 税率一律 `--font-numeric` | 不等宽数字在结果表里**纵向对不齐**（已落地） |

**字号下限 11px**（已落 `--fs-micro`）——更小的字号在中文小屏上不可辨认。
`text-[10px]` 只允许用于非文字装饰。

### 6.3 留白节奏

4px 基准栅格（已落 `--sp-1` ~ `--sp-8`）。两条纪律：

- **卡片内边距与卡片间距不是一回事** —— 内边距决定「这张卡的气质」，间距决定「这两张卡是不是一伙的」。
  卡间距 ≥ 卡内边距，否则视觉上会粘连。
- **区块间距 > 卡间距** —— 用间距做分组，比加分割线更干净。

### 6.4 结果页的视觉层级（本方案认为最该改的一处）

现有结构已经是三段式（`结果` → `易错口径 pitfalls` → `下一步 nextTools`），方向正确，本方案确认并强化其**层级**：

```
① 金额（Hero，最大）
② 结论：应退 / 应补（带文字，不只靠颜色）
③ 一句话理由（为什么会这样）
─────────────────────────
④ 推导链「这个数怎么算出来的」  ← 默认折叠，复用既有 #formula-steps-panel
⑤ 易错口径 pitfalls   ← 已有，**不折叠**（信任来源 + 传播素材）
⑥ 明细（默认折叠）
─────────────────────────
⑦ 下一步：nextTools 互链 / 保存 / 导出 PDF   ← 已有，这是提升人均 calc_done 的动线
⑧ 免责声明
```

> **④ 与 ⑤ 的分工要说清**（前稿两处说法冲突）：
> `pitfalls` 是**口径提示**（哪些坑容易算错），推导链是**数值逐级落地**（这一步到底减了多少）。
> 二者都服务于「可信度」，但回答不同问题，不可互相替代。

> **⑧ 免责声明是合规缺口，不是排版细节**（2026-09-17 核实）：
> 导出报告（`quick-report.js` / `export-utils.js`）与分享图（`share-card.js`）**都有**免责文案
> （「结果为测算参考，实际纳税请以税务机关核算为准」），
> 但 20 个速算器的**屏幕上没有**（`toolbox-ui.js` 全文无「免责」二字）。
> 也就是说：**可带走的东西有免责，看得最久的那一屏反而没有** —— 这是风险，不是疏漏级别的小事。

**手机端硬要求：①② 必须在第一屏可见**（不滚动就能看到「要补多少」）。
问题在于桌面端习以为常的多列布局搬到手机会堆成长条——不是加内容，是布局降级没做。

| 人群 | 只看 | 需要 |
|---|---|---|
| 大多数人（打工人、汇算） | ①② | 一个能截图发出去的结论 |
| 要核对的人（个体户、财务） | ①②③④⑤⑥ | 明细、易错口径、可导出、可打印 |

所以：**明细折叠，但展开后必须完整且可导出** —— 两类人都不牺牲。
而 `pitfalls`（易错口径）**不折叠** —— 它既是信任来源，也是传播素材（「99% 的人算错这一步」）。

**无障碍硬约束**：退 / 补**禁止只靠红绿区分**，必须同时有「应退 / 应补」文字（约 8% 男性红绿色觉障碍）。

## 7. 交互体验设计

### 7.1 输入：一次只问一个（手机端核心形态）

> ⚠️ **先调和一处原文矛盾**：§2.1 主张免费计算器小站「✅ 保留零门槛一屏算完」，
> 本节又主张「一次只问一个」——**两者对同一批工具给了相反形态**。
> 调和规则：**按任务长度分流，而不是统一形态**。
>
> | 工具 | 形态 | 理由 |
> |---|---|---|
> | 20 个单页速算器（字段 ≤5） | **一屏算完** | 拆成 5 步会让 30 秒的任务变成 2 分钟，直接砍 `calc_done` |
> | 4 个完整测算（字段多、有分支） | **引导式分步** | 一屏放不下，且用户心态本来就是「认真填一次」 |
>
> 所以「一次一问」适用于**重任务**，不适用于速算器 —— 这也是 Phase 1 的适用范围边界。

```
进度 ●●○○○  ← 可见但不用数字压迫
┌────────────────────────┐
│ 今年你的年终奖是多少？      │  ← 一句话，人话
│ [        ¥ 50,000 ]    │  ← 金额输入：数字键盘 + 货币前缀 + 就地校验
│ 不确定可以先填个大概       │  ← 消除「填错」的焦虑
└────────────────────────┘
   ┌────────────────────┐
   │ 预览：约 ¥ 43,250  │  ← 实时预览条，改一个数立刻变
   └────────────────────┘
        [ 上一步 ]  [ 下一步 ]
```

取 TurboTax 的精华，弃它的糟粕：

| ✅ 取 | ❌ 弃 |
|---|---|
| 一次一个问题、进度可见、随时可返回 | 强制顺序不能跳（我们要允许跳到目标字段） |
| 每问配一句「为什么问这个」 | 进度条用百分比制造压迫感（用点位，不用「已完成 40%」） |
| 实时预览结果 | 填完才给反馈 |

输入框细节（抄 Stripe）：
- 数字键盘（`inputmode="decimal"`）、货币前缀、千分位
- **就地校验**，错误显示在字段旁，**不用 `alert` / 不用错误弹窗**
- 输入框字号强制 16px（防 iOS 聚焦缩放，已落）
- 触摸区 ≥ 44px（已落）

#### ⚠️ 补一类校验：不只管「格式」，还要管「量级」

财务数据的**错误成本是不对称的** —— 少填一个零或多填一个零，结果差十倍，而**用户自己发现不了**
（他看到「应补 ¥48,000」，只会觉得税真高，不会想到是自己月薪填成了 15 万）。

现有校验只覆盖「格式」（必填 / 是否数字 / 是否超 min-max），缺**合理性怀疑**：

| 例子 | 判断 |
|---|---|
| 月薪填 100 万 | 可能是笔误，也可能是高管 —— **不能阻断** |
| 专项附加扣除 > 月收入 | 几乎必错 —— 应提示 |
| 任职月数 > 12 | 一定是错 —— 应提示 |

**处理纪律：一律软提示（黄字旁注），绝不阻断提交。**
理由：税务场景个体差异是真实存在的，任何「不让提交」的强校验都可能把真实输入挡在外面。
我们要做的是**让用户确认一次**，而不是替他决定对错。

### 7.2 结果：先给结论，再给理由

- 结论是一句话，不是一个表格
- 「为什么会这样」配一句人话解释（这是建立信任的关键，也是竞品普遍缺的）
- 明细折叠可展开
- **结果页是留存的唯一机会** —— 保存 / 分享 / 打印三个出口必须显眼

#### ⚠️ 更正一处判断：推导链**已经存在**，真缺口是「只覆盖了 4 个流程，没覆盖 20 个速算器」

> **本节前稿曾断言「结果区无推导实现」，该结论已核实为错误。**
> 阶段12 就已做过「计算过程透明化」：`utils.js` 的 `buildFormulaSteps(results)` 是纯函数，
> 逐步输出 `label / note / value / totalLabel / totalValue / footnote`，
> `tax-calculator.js` 在 `updateTaxResultsUI` 末尾调用 `updateFormulaSteps` 渲染 `#formula-steps-panel`，
> 并有 `tests/formula-steps.test.js`（9 例，**断言各步数值与结果区逐位一致**）。
> 前稿之所以漏判，是因为只检索了中文关键词，而这套实现是英文命名（`formula-steps`） —— 检索词不对导致误报。

**真实缺口（v1.39.0 时的状态）**：这套能力当时的覆盖面比想象的还窄 ——
`#formula-steps-panel` 在 `index.html` 里**只存在一处**（综合所得前向页），
`updateFormulaSteps` 也**只被 `updateTaxResultsUI` 调用一处**（`tax-calculator.js:653`）。

| 场景 | v1.39.0 时现状 | **v1.40.0 现状** |
|---|---|---|
| **综合所得·正向**（综合所得前向页） | ✅ 唯一有推导链的一处 | ✅ |
| 经营所得 / 分类所得 / 反向倒算 | ❌ 没有 —— 同为「完整测算」，体验不一致 | ✅ **已补齐**（台账 C，`utils.js` 三个新纯函数 + 三页面板接线） |
| **20 个速算器（`*-quick.js`）** | ❌ 没有 —— `rows` 是并列指标，不是逐级推导 | 🟡 **打样 1 个**（月薪个税），其余 19 个待批量铺；`steps` 为 **可选字段**，未补的速算器不受影响 |

> 注意第二行：**同为「完整测算」，只有 1/4 有推导链** ——
> 这在用户看来是「有的地方有、有的地方没有」的随机体验，比「都没有」更伤信任。
> 该「完整测算内部不一致」问题已在 v1.40.0 消除；剩余缺口收敛为**速算器覆盖率**。

**结论因此反转**：这不是「从零建一个新东西」，而是**把已验证、可测的实现平移复用**。
成本远低于新做，收益覆盖全部测算场景。

现有 `pitfalls` 回答的是「哪些坑容易算错」——它提升的是**「我信你是专业的」**。
推导链回答的是**「这个数怎么一步步算来的」**——这才是**「我能核对」**。

**做法**（v1.40.0 已按此落地）：给速算器 `compute` 的返回补一个**可选的** `steps`
（沿用 `buildFormulaSteps` 的结构；实现位置是 `tool-registry.js` 的 `compute`，而非 `*-quick.js` 库文件本身），
`renderResult` 复用同一套 `<details>` 面板组件 —— **只复用一套实现**，不写第二套。
本轮已抽出 `renderFormulaStepsHtml`（纯字符串）+ `showFormulaStepsPanel`（通用挂载）供四处共用。

```
月薪 15,000
 − 五险一金 1,500
 − 基本减除 5,000
 − 专项附加 1,000
 = 应纳税所得额  7,500      ← 这一步是争议高发点，必须可见
 × 适用税率 3%（速算扣除 0）
 = 应纳税额 225
```

| 人群 | 需要 | 现有够不够 |
|---|---|---|
| 打工人 | 「我这个月到手多少」 | 够 |
| **个体户 ★★★ / 财务 HR** | 「我能不能核对每一级扣除」 | **不够** |

> **为什么这值得单独做**：我们要求 user 相信一个影响真金白银的数字。
> 财务习惯是「对账」，不是「信一个黑盒」。推导链把结果从「答案」变成「可复核的过程」——
> 它是桌面三要素中「可信度」最实的一块，权重高于任何视觉包装。

位置上放在结论之后、`pitfalls` 之前；**默认折叠但保留深链锚点**（分享出去能直接定位到某一步）。

### 7.3 商业化引导：看起来必须是「帮助」

这是本方案与纯体验方案最大的分歧点，也是**最容易被做坏的一处**。

产品铁律 3 是「不做广告」。它不只是道德偏好，它**直接约束引导卡的形态**：

| ❌ 广告位形态 | ✅ 有用的下一步 |
|---|---|
| 「需要专业服务？联系我们」 | 「你的专项附加扣除可能没填全，可补约 ¥1,200」 |
| 悬浮 banner / 弹窗 | 结果页内嵌**情境卡**，与结果同源 |
| 所有场景同一张卡 | 按 `type` 分流（已落 `BLOCKED_TYPES`） |

三条纪律：
1. **引导必须携带信息价值** —— 用户即使不点，也学到了东西
2. **谈薪人群（reverse）永不出服务引导** —— 要他们的传播，不要他们的线索（硬约束）
3. **引导卡必须可关且记住** —— 反复弹同一个东西 = 广告

### 7.4 反馈与错误

| 场景 | 规则 |
|---|---|
| 写操作 | 乐观 UI + 失败可撤销（Toast 带「撤销」） |
| 错误 | 就地显示，说清「哪里错了 + 怎么改」，不用 alert |
| 空状态 | **必须有出路**（一个主行动按钮），不能只写「暂无数据」 |
| 加载 | < 300ms 不显示 loading（闪一下比没有更糟）；> 1s 显示骨架屏 |
| 网络失败 | 区分「离线可继续算」（计算在本地）与「需要联网」（同步/保存） |

> 计算在浏览器本地（产品铁律 2）意味着：**断网也能算完**。
> 这个能力要在 UI 上被感知到（离线时的提示应是「仍可计算」，不是「网络错误」）。

### 7.5 性能即体验

已有 `HomePerf` / `ProfilePerf` / `AssistantPerf` 埋点。
**渲染耗时是交互体验的一部分**，不是工程细节——超过 100ms 的交互反馈用户就能感知到延迟。

## 8. 自适应：不是「三个断点」，是「设备矩阵 × 非宽度变量」

> 这是本方案相对常规响应式方案最大的差异点。
> 大部分项目理解的「自适应」= 加几个 `@media (min-width:)`。
> **真正的坑几乎全在断点管不到的地方。**

### 8.1 断点：两条解耦（已落地 S2）

| 维度 | 断点 | 变化 |
|---|---|---|
| **导航形态** | 768px | 底部 Tab ⇄ 顶部 Tab 行 |
| **内容形态** | 1024px | 单列 ⇄ 多列 / 宽容器 |

**为什么要解耦**：平板竖屏（768–1024）应该拿到桌面导航（因为屏幕够高够宽放 Tab 行），
但内容仍是单列（因为宽度不够放多列）。用一个断点会两头不讨好。

### 8.2 设备矩阵（「不同型号设备」的真实清单）

| 设备 | 典型宽度 | 关键适配点 | 常见坑 |
|---|---|---|---|
| **小屏手机** | 360–375px（iPhone SE / 安卓主流） | 字号下限、触摸区 44px、按钮不换行 | 两个按钮并排会把文字挤成两行 |
| **大屏手机** | 390–430px（Pro / Max） | 内容不被无限拉宽，Hero 可放大 | 全宽卡片在大屏上显得空 |
| **折叠屏（折叠态）** | ~375px | 同小屏手机 | — |
| **折叠屏（展开态）** | 768–880px | ⚠️ **会命中 768 断点的桌面导航** | 它其实是手机：触摸操作、竖持、宽度仍不足双列。**不能只靠宽度猜设备** |
| **平板竖屏** | 768–834px | 桌面导航 + 单列内容 | 直接套桌面双栏会挤 |
| **平板横屏** | 1024–1194px | 双栏内容 | 与笔记本同宽，但**是触摸屏**（无 hover） |
| **笔记本** | 1280–1440px | 标准桌面形态 | 助手侧栏推开（≥1280，已落 S6） |
| **大屏 / 2K** | ≥1920px | **必须限宽**（`--c-default`），内容不拉满 | 拉满后行长超过 100 字符，阅读效率反而下降 |
| **触屏笔记本** | 1280+ 但可触摸 | hover 样式要降级 | `@media (hover: hover)` 包裹 hover 效果，否则触屏上 hover 态**粘住不消失** |

### 8.3 非宽度变量（断点管不到，但会真出事）

| 变量 | 处理 | 不做会怎样 |
|---|---|---|
| **安全区**（刘海 / Home Indicator） | `env(safe-area-inset-bottom)` 叠加到底栏高度（已落） | 底栏被 Home Indicator 压住 |
| **`100vh` 陷阱** | 用 `dvh`（移动端地址栏收起/展开会改变 `vh`） | 首屏高度在滚动后跳动，底部内容被裁 |
| **软键盘弹出** | 用 `visualViewport` 监听（Android 压缩视口，iOS 不压） | Android 上输入框被键盘盖住 |
| **横屏手机**（高度 < 500px） | 固定层收缩 / 隐藏非关键层 | 顶栏+底栏占掉 60% 高度，内容区只剩两行 |
| **系统字号放大**（Android 字号 / iOS 动态字） | 用 `rem`，**禁止 px 锁定容器高度** | 字号放大后文字溢出按钮 |
| **深色模式** | `.dark` 令牌镜像（已落）；打印时 `beforeprint` 摘类（已落 S8） | 打印出「白纸上的白字」 |
| **减少动效** | `prefers-reduced-motion`（已落） | 前庭障碍用户不适 |
| **高对比度 / 强制颜色** | `forced-colors` 下保留边框与焦点 | Windows 高对比度模式下组件边界消失 |

### 8.4 原则：不要用宽度猜设备

媒体查询**只能测宽度**。当宽度不能唯一决定形态时（折叠屏展开态、平板横屏），
正确做法是**逐步增强地降级**，而不是猜：

1. 默认按宽度给形态（覆盖 95% 情况）
2. 用 `@media (hover: hover) and (pointer: fine)` 判断**是不是鼠标** —— 这比猜设备可靠
3. 只有在真正需要时（如折叠屏分栏）才用 `viewport-segments` 或 JS 探测
   —— **默认不猜，猜错比不适配更糟**

### 8.5 方向：容器查询 > 媒体查询

已落地的 `auto-fill minmax(260px, 1fr)` 就是容器思维。
下一步：组件级 `@container`——**组件应该响应自己的容器，而不是响应视口**。

理由：同一个卡片在「全宽首页」和「助手侧栏内」应该给不同布局，
但它们两个的**视口宽度完全一样**。媒体查询在这里无能为力。

### 8.6 运行时环境：设备矩阵没覆盖的那一半

> ⚠️ **本章是前几稿完全没有的一维。**
> §8.2 谈的都是「屏幕」，但用户不是在浏览器标签页里使用我们的产品 ——
> 他们是在**具体的容器**里用：**微信内置浏览器**、**PWA 独立窗口**。
> 这两者都会改变 UI 的可用假设。
> **已核实（2026-09-17）：全仓库无 `display-mode` 查询、无微信 UA 检测 —— 适配现状为零。**

#### ① 微信内置浏览器 —— 传播主场，但我们从没为它做过设计

**为什么它不是边缘场景**：商业链路是
`分享图 → 微信里扫码/点开 → 站内使用 → 再次分享 或 企微留资`。
获客（马车 C）与留资（企微活码）**全程发生在微信容器内**。
在 Safari 上做得再好，也不覆盖 majority 的真实触达环境。

| 约束 | 后果 | 应对 |
|---|---|---|
| Android X5 内核底部工具栏 | 视口被挤掉约 44–50px，**相当于凭空多一层底栏**，只叠 `--bottom-inset` 不够 | 微信环境下再叠一层 inset；固定底栏需抬高 |
| **`download` 属性被拦截** | **导出 PDF / CSV 大概率失败** | 见下方「移动导出替代」 |
| 字体栈回退 | `-apple-system` 在安卓微信落到系统默认中文字体，**行高与排版会变** | 中文字体必须显式指定字号 + 行高令牌，不能依赖系统字体度量 |
| 外链只能在同窗跳转 | 政策依据外链 → 用户离开即流失 | 政策依据做**页内展开**，不外跳（与桌面「可信度」同向，同一套组件复用） |

**移动导出的替代方案**（这条会改变 Phase 3 的排期判断）：

既然微信里文件下载可能被拦，那么「可交付」在移动端**不能只做成文件下载**。三条可用出路：

1. **结果长图** —— 复用现有分享图生成器（`export/capture.js`），含结论 + 推导链 + 政策依据，长按即可保存
2. **复制为纯文本** —— 对 HR 场景极实用，可直接粘进 Excel / 微信对话
3. **「在浏览器打开」提示** —— 仅在**检测到导出确实失败时**提示，不常驻

> **纪律：不常驻任何环境提示。**
> 常驻的「请在浏览器中打开」是在把自己的能力缺陷转嫁给用户，且它挂在每一屏上、对所有人都没用。
> 正确做法是**失败时才说**，并同时给出长图/复制两条能立刻用上的出路。

#### ② PWA 独立窗口（standalone）—— 最有价值的那一批用户在的形态

装机用户（`beforeinstallprompt` / `appinstalled` 已实现）是留存与复访最高的一批，
但他们**失去了浏览器提供给我们的兜底**：

| 失去什么 | 我们必须自己补什么 |
|---|---|
| 地址栏与刷新 | **不允许出现死胡同**：任何页面都要能回到起点，否则用户只能杀进程 |
| **系统返回键 / 手势** | History 必须与**视觉层级**一致。否则「返回」会跳错页，甚至在向导中途直接退出应用 —— 这对 Phase 1 的分步向导是**直接的前置依赖** |
| 外链跳出容器 | 与微信同理：政策依据外链会跳出应用，再次指向「页内展开」 |

必须做的两条：

1. `@media (display-mode: standalone)`：至少提供**应用内返回 / 首页出口**，并补贴安全区
2. 向导的 History 策略：用 `history.pushState` 使「上一步」与系统返回语义一致，
   **绝不允许系统返回 = 退出应用**（用户会理解成「这软件崩了」）

#### 为什么这一章值得单独列为优先级

| 环境 | 影响的价值链 |
|---|---|
| 微信 | 获客（分享回流）+ 留资（企微）—— 直接作用于**马车的两个发动机** |
| PWA standalone | 最重度用户的**留存与完成率** —— 直接作用于 `calc_done` |

二者都不是「观感优化」，而是**在某些真实主流环境下功能是否可用**的问题。

## 10. 落地路线

> 排序原则：**按「北极星敏感度 × 实施成本」排，不按技术依赖排。**
> 每张都要能回答商业筛子的三个问题：**带关键词吗？带线索吗？解锁收款吗？** 都不能 → 排队或砍。

### Phase 0 — 地基（✅ 已完成，S0–S8）

设计令牌 / z 层级表 / 断点解耦 / 屏幕预算 / 悬浮球避让 / 容器加宽 / 助手推开 / 落地页接入令牌 / 打印样式。
详见 [`dual-end-ui-plan.md`](dual-end-ui-plan.md)。

### Phase 1 — 手机端「算得完」（最高优先）

> **这是本方案唯一的最高优先项**。目标不是让手机端「更快」，是让**重任务能在手机上算完**。
> 个体户（★★★）与汇算（★★☆）是填字段最多的人，且在手机上。他们在手机上算不完 → 北极星直接掉。

| 项 | 内容 |
|---|---|
| **做什么** | ① **降输入成本**：合理默认值 + 上年结转预填 / 可跳过非必填步骤 / 草稿自动保存 + 断点续算<br/>② 引导式分步：一次一个问题 + 进度点位 + 实时预览条 + **可跳可返回**<br/>③ 压缩固定层：步骤条并入顶栏，22% → ≤18% |
| **为什么优先** | 直接作用于 `calc_done`（分母），且作用在**高商业价值客群**上；三者叠加才真正解决「算不完」 |
| **为什么能过筛子** | 护卫北极星的分母，不是体验打磨 —— 这是它与被砍的双栏项的本质区别 |
