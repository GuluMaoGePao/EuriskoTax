## 1. 一页纸定稿

| # | 定论 | 约束强度 |
|---|---|---|
| 1 | 手机端是**主战场**，桌面端是**价值端** | 决定所有取舍的第一刀 |
| 2 | 手机端不止「算得快」，**必须「算得完」** | ★★★ 客群主用手机且字段最多 |
| 3 | 桌面端 = **信息密度 + 可信度 + 可交付**，三者并列 | 缺一就等于没做桌面端 |
| 4 | 桌面**不是放大的手机**，手机**不是缩小的桌面** | 两侧不许互相移植形态 |
| 5 | IA **骨架**不再改动；新增税种走**增量接入**，不重排现有分组 | 结构已自洽；真正的缺口在 deep 侧覆盖（§4.2 仅 1/6），不在入口编排 |
| 6 | 商业化引导必须是**「有用的下一步」**，不是广告位 | 由产品铁律「不做广告」决定 |
| 7 | 谈薪人群（`reverse`）**永不出服务引导** | 硬约束 `BLOCKED_TYPES`，不是偏好 |
| 8 | 任何增加「算完之前」摩擦的东西都是负资产 | 登录 / 注册 / 教程弹窗一律排在 `calc_done` 之后 |
| 9 | 微信容器 + PWA standalone 是**功能可用性**问题，不是观感 | 见 §11 |
| 10 | 缺乏视觉回归 → 所有改动必须**拆小步、每步可独立回滚** | 见 §12.4 |

**北极星**：`lead_submit / calc_done` —— 分子分母都直接由 UI 决定。改版唯一验收标准是**它不降**。

## 2. 商业模式（UI 的服务对象）

### 2.1 一句话

> **免费工具获取高商业意图流量 → 把能付得起服务费的人转成线索 → 由我们的财税服务能力交付成交。**

工具本身不赚钱，它是入口。**所有 UI 决策要服从这条链路**，而不是服从「产品看起来更专业」。

### 2.2 三层收入与 UI 的对应

| 层 | 内容 | 当前手段 | UI 承接点 |
|---|---|---|---|
| **第一层（主营收）** | 代账 / 申报 / 汇算代办 / 咨询 | 留资 → 企业微信活码 → 顾问 1v1 | 结果页**情境卡**（§9.3） |
| **第二层（现金流）** | C 端专业版 9.9–19.9 元/年 | `ProCode` 兑换码（线下收款 → 后台发码 → 自助兑换） | 入口已收敛到 `#topbar-plan-badge` 与 `#profile-nav-upgrade`，**不许再增加入口** |
| **第三层（第二曲线）** | B 端 API | 待 ICP 备案 + 阶段15B | 桌面端是它的产品预演 |

**客单价对比是决定性的**：一单服务 ≈ 千元量级，一个订阅 ≈ 15 元/年 —— **1 个成交客户 ≈ 几百个订阅用户**。
因此 UI 的首要目标是把 ★★★ 客群的服务线索做出来，而不是把订阅付费墙做重。

### 2.3 两阶段模型（会影响 UI，必须知道）

| | 前期（引流 → 私域） | 后期（工具自收费） |
|---|---|---|
| 计算 | 全部税种免费（保持） | 划付费边界，**收的不是「算」，是「算之外」** |
| 登录 | **永不阻塞计算** | 仍不阻塞计算，但**付费触点**才要求登录 |
| 结果页主 CTA | **留资 / 咨询** | 让位于产品 CTA |
| 客群价值排序 | 老板 > 财务 > 打工人 | **打工人反转为订阅主力** |

> ⚠️ 本方案的 UI 原则默认处于**前期**。前期的正确做法不要写成「永久铁律」，否则会锁死后期的变现路。

### 2.4 产品铁律（UI 不许越过）

1. **计税能力永不锁定** —— 免费版算全部税种，锁定的是云端增值。
2. **计算永远在前端** —— 隐私即卖点，断网也要能算完。
3. **不做广告** —— 信任就是产品本身。
4. **不做申报，只做测算** —— 所有页面统一免责声明。
5. **合规即卖点** —— 禁用「避税 / 节税 / 税筹」，统一「申报核对 / 汇算清缴代办」。

> ✅ **本缺口已于 v1.41.1 补齐**（同一版还修掉了 §12.3 那颗已经爆了的雷 —— Phase 2 结果页样式从未生效）。
> 现状：五处结果区（速算器壳 + 4 个完整测算）统一挂 `result-disclaimer` 段落，
> 文案「测算结果依据您填写的数据与现行政策估算，仅供参考，不构成税务建议；正式申报请以税务机关核定为准。」
> 由 `tests/ui-result-compliance.test.js` 钉住 —— 删一个是零成本且无人发现的，所以必须钉。

## 3. 目标群体（客群 → 任务 → 端）

### 3.1 客群分层的两张表

**前期表（当前生效）**：

| 客群 | 商业价值 | 典型任务 | 主端 | UI 形态 | 商业化动作 |
|---|---|---|---|---|---|
| 个体户 / 个独 / 合伙 | ★★★ | 经营所得汇算、扣除项核对 | **手机** | 引导式分步 + 结果页情境卡 | **强引导 + 留资** |
| 小微企业主 | ★★★ | 用工成本、预算、多方案对照 | **桌面**（手机补位） | 对照式工作区 + 报表导出 | 顾问 + 预算表 |
| 财务 / HR | ★★★（第二曲线） | 批量测算、发薪方案、导出 | **桌面** | 批量 + 表格化 | B 端 API（阶段16） |
| 年度汇算纳税人 | ★★☆ | 扣除是否填全、退/补 | **手机** | 引导式 + 结果页核对 | 汇算代办 / 咨询 |
| 打工人（谈薪 / 月薪） | ★☆☆ | 到手倒推税前、年终奖怎么发 | **手机** | 极速单屏 | **只出分享图，不出服务引导** |

**后期会翻转**：进入工具自收费后，打工人在量大、每年必回访的前提下**反转为订阅主力**。
拿这张前期表去做后期的产品决策会做错。

### 3.2 由客群推出的两端定义

| | 手机端 | 桌面端 |
|---|---|---|
| 一句话 | 让更多人在手机上**算完** | 让值钱的人**拿得出东西、信得过** |
| 核心指标 | `calc_done`、重任务完成率、分享率 | `lead_submit`、导出/打印次数、停留时长 |
| 形态 | 一次一问、进度可见、结果先给结论 | 完整表单同屏、多列网格、结果不折叠 |
| 交付 | 分享图 / 长图 / 复制文本（轻量） | CSV / PDF / 打印（完整） |

> **「手机 = 只能速算」是错的判断** —— 那等于把最值钱的客群推到他们不用的端。

## 4. 核心功能清单

### 4.1 核心功能只有一句：**全税种完整测算**

> ⚠️ **本节 2026-09-17 重写。** 上一版把「26 项能力 + 24 个入口」并列算作核心功能，**这是错的**：
> 入口数量不等于能力覆盖，而且它会掩盖本站最大的未交付缺口。以下以 `tax-registry.js` 实测为准。

**两层，位次不许颠倒**：

| 层 | 定义 | 形态 | 在 `tool-registry.js` 里的标识 | 服务对象 |
|---|---|---|---|---|
| **① 核心（卖点）** | 每个税种/费种的**完整测算**：按期逐项填全 → 出完整明细、预算表、可保存、可导出 PDF | 多步向导（2–4 步），结果七段齐全 | `status: 'deep'` + 有 `pageId` | 有真实报税/申报需求的人 → **留资与付费主力** |
| **② 引流（获客）** | 单表单快速估算：2–9 个字段，一屏出数 | 单页速算壳 `quick-calculator-page` | `status: 'native'` + 有 `seoPath` | 搜索流量 → SEO 自然增长 |

> 一句话：**速算器负责被找到，完整测算负责被付费。**
> 任何把两者并列讨论的表述都会在排期上出错 —— 缺完整测算 = 缺核心卖点，缺速算器只是缺流量入口。

| `iit` | 个人所得税 | 15 | ✅ **10 个**（全在它内部；17D 起含劳务报酬预扣预缴、年终奖择优、股权激励、离职补偿、提前退休内退、外籍津补贴免税） | 14 | 14 |
| `vat` | 增值税 | 2 | ✅ **1 个**（17C-1，spec 驱动） | 1 | 1 |
| `cit` | 企业所得税 | 2 | ✅ **1 个**（17C-2，spec 驱动） | 1 | 1 |
| `surtax`+`stamp` | 附加税与印花税 | 3 | ✅ **1 个**（17C-4，spec 驱动） | 1 | 1 |

### 4.3 三个最容易误判的点（写进计划前必须知道）

**①「我们有 N 个完整测算」≠「我们覆盖了 N 个税种」。**
`business`（经营所得）是个税九类所得里的**第 5 类**，`classification`（分类所得）是**第 6–9 类**（利息股息红利 / 财产租赁 / 财产转让 / 偶然所得）—— 都不是独立税种。
所以个税那 12 个 deep（17D-8 后）是 **1 个税种的 12 个切面**，不是 12 个税种 —— 场景数涨了，`category` 覆盖数没变。

**② `reverse`（反向倒算）不是税种，是求解方向。**
它与「算什么」（所得类别）正交。把两者并列在同一层菜单是历史包袱 —— 目标态里「反向」应成为每个税种的一个模式，而不是平级的第五项。详见 §12.7。

**③「阶段15 多税种已完成」这句话有歧义，是本轮混乱的根源。**
阶段15 确实 **✅ 已全部关闭**（`development-plan.md:338`，v1.18.0 → v1.35.0，交付 20 个 SEO 落地页 + 20 个 quick 模块 + 对拍测试）。
但它交付的是 **② 引流层**：

| 「多税种覆盖」的两种含义 | 状态 |
|---|---|
| SEO 关键词覆盖（每税种一个落地页） | ✅ **已完成**（20 页 + 1 目录） |
| App 内完整测算覆盖（每税种一套多步向导） | ❌ **只完成 1/6**，另外 5 类完全没有 |

> 📌 **这是当前最大的未交付缺口。** 2026-09-17 全仓扫描（`TODO` / 待开发 / 后续 / stage / plan）：
> **代码库中不存在任何 TODO 或规划文档承诺过补齐它** —— 它此前从未被发现、也从未被排期。
> 不要把「阶段15 已完成」读成「核心功能已完成」。

### 4.5 能力清单（UI 要知道它有什么可用）

## 7. 设计基线（已落地，改动须知）

### 7.1 令牌层

唯一真源 `src/css/tokens.css`。已接入：`toolbox.css`、`seo/landing.css`（21 页）。

> ⚠️ **Tailwind 仍有 hex 副本**：`tailwind.config.js` 与令牌**同值镜像**，改色必须两侧同步。
> 未全量变量化的真实阻力是**缺视觉回归**，不是技术能力。

### 7.2 容器

| Token | 值 | 用途 |
|---|---|---|
| `--c-narrow` | 720px | 速算器 / 表单（行长 65–75 字符最优） |
| `--c-default` | 1024px | 首页 / 工具页 / 计算页 / 网格 |
| `--c-prose` | 760px | SEO 正文阅读 |

**网格列数跟「容器还剩多少宽度」走，不跟视口走**（`auto-fill minmax(260px, 1fr)`）——
视口变宽和侧栏推开是同一结果的两种原因，按视口写死会漏掉后者。

### 7.3 中文排版三条（通用设计系统不会告诉你）

| 项 | 规则 | 为什么 |
|---|---|---|
| **行高** | 正文 **1.7** | 方块字没有上下延伸部，英文惯例的 1.5 会糊成一片 |
| **段间距 > 行间距** | 段落间 ≥1.5 倍行距 | 中文没有首行缩进习惯，靠间距分组 |
| **数字等宽** | 金额 / 税率一律 `--font-numeric` | 不等宽数字在结果表里纵向对不齐 |

字号下限 **11px**（`--fs-micro`）；`text-[10px]` 只允许用于非文字装饰。

### 7.4 留白节奏

4px 基准栅格（`--sp-1` ~ `--sp-8`）。两条纪律：
- **卡间距 ≥ 卡内边距**，否则视觉粘连；
- **区块间距 > 卡间距**，用间距做分组比加分割线干净。

### 7.5 z-index 层级表

`--z-sticky(30)` / `--z-header(40)` / `--z-tabbar(45)` / `--z-fab(60)` / `--z-overlay(90)` /
`--z-drawer(95)` / `--z-modal(100)` / `--z-toast(200)` / `--z-emergency(9999)`。

**冻结清单**（有意保留的字面值，改前必须同步改门禁注释与测试）：

```
┌──────────────────────────┐
│ ← 返回    工具名          │   紧凑顶栏（含返回）
├──────────────────────────┤
│ 税前月薪                  │   输入框组，容器 --c-narrow

├──────────────────────────┤
│ [ 计算 ]                  │   唯一主行动，全宽、≥44px
├──────────────────────────┤
│ 结果区（见 §9）            │
└──────────────────────────┘
```

**输入细节**：`inputmode="decimal"`、就地校验（**不用 alert / 错误弹窗**）、输入框 16px、触摸区 ≥44px。

**⚠️ 量级校验（软提示，绝不阻断）**：现有校验只管「格式」，缺「合理性怀疑」：

| 例子 | 处置 |
|---|---|
| 月薪填 100 万 | 可能是笔误也可能是高管 → **只旁注提示，不阻断** |
| 专项附加 > 月收入 | 几乎必错 → 提示 |
| 任职月数 > 12 | 一定错 → 提示 |

理由：税务场景个体差异真实存在，**任何「不让提交」的强校验都可能把真实输入挡在外面**。我们要的是让用户确认一次，不是替他决定对错。

### 页型 G — SEO 落地页（20 个内容页 + 1 个目录页）

这是全站**唯一一种独立 HTML 页型**（不复用 App 的 SPA 壳），七条原则（改动时必须遵守）：

| # | 原则 |
|---|---|
| 1 | **页面自己有用** —— 每页自带能跑的最小计算器，不是只有 CTA |
| 2 | **口径同源，不复制** —— 税率表读同一份脚本（`tax-constants.js` 出厂值 + `tax-rates-sync.js` 从 `/api/config/tax-rates` 覆盖的热改值），后台改了页面跟着变 |
| 3 | **计算逻辑可证明等价** —— 与内核在临界点 ±1 元、档内采样、极值上**逐点对拍** |
| 4 | **正文静态可抓取** —— 规则/税率表/临界点表/FAQ 全是 HTML 正文，JS 只负责把输入变成结果 |
| 5 | **首屏零 CDN** —— 手写 `seo/landing.css`（约 4KB），不引 Tailwind / 图标字体，脚本 `defer`；共享语义色取自 `tokens.css` |
| 6 | **一页一词** —— 页面之间互不重复，避免站内自相残杀 |
| 7 | **可归因** —— 进 App 的链接带 `?source=seo_<page>`，服务端白名单同步登记 |

**统一排版模板（`--c-prose` 760px 阅读宽）**：

```
① H1 ─ 只含一个意图词
② 一句话定义 ─ 这一页解决什么问题（2 行内）
③ 速算器 ─ 自带可跑的最小计算器（原则 1）
④ 规则讲解 ─ 政策依据 + 文号（原则 4，静态 HTML）
⑤ 静态税率表 ─ 页面「呈现」数字但不「拥有」数字（详见下方）
⑥ 临界点 / 示例表 ─ 真实例子，必须覆盖至少三种结论方向
⑦ FAQ ─ 带 FAQPage 结构化数据
⑧ CTA ─ 「打开完整计算器」 `?source=seo_<page>`（≥2 处）
⑨ 免责声明 ─ 正文一次 + 页脚重复一次
⑩ 页脚 ─ 首页 + 工具总目录 + 1–3 个兄弟页互链
```

> ⚠️ **「静态表格」的对账纪律**：为了可抓取，正文里必然有一份静态税率表。
> 正确做法不是「禁止页面出现数字」，而是**逐档对账** —— `verify:local` 把页面正文的数字与常量文件逐一对照，
> 常量改了页面没改就失败。**页面可以呈现数字，但不能拥有数字。**

### 页型 H — 运维 / 工具页（2 个）

| 页 | 用途 | 规则 |

## 9. 结果页统一模板（全站最关键的一屏）

### 9.1 八段顺序（不许调整）

```
① 金额 Hero                            ← 最大，手机必须第一屏可见
② 结论：应退 / 应补 / 不退不补          ← 必须带文字，不许只靠颜色
③ 一句话理由                            ← 「为什么会这样」
────────────────────────────────
④ 推导链（默认折叠）                    ← 沿一列逐级核对到政策依据
⑤ 易错口径 pitfalls（**不折叠**）        ← 信任来源 + 传播素材
⑥ 明细（默认折叠，**记住展开状态**）
────────────────────────────────
⑦ 下一步：nextTools 互链 / 保存 / 导出
⑧ **免责声明**（当前缺失，见 §2.4）
```

### 9.2 ④ 与 ⑤ 的分工

| | 回答什么 | 为什么不可互相替代 |
|---|---|---|
| `pitfalls` | 「哪些坑容易算错」 | 提升「我信你是专业的」，也是传播素材 |
| **推导链** | 「这个数一级一级怎么来的」 | 这才是「我能核对」，是桌面可信度最实的一块 |

```
月薪 15,000
 − 五险一金 1,500
 − 基本减除 5,000
 − 专项附加 1,000
 = 应纳税所得额  7,500      ← 争议高发点，必须可见
 × 适用税率 3%（速算扣除 0）
 = 应纳税额 225
```

**两类人都不牺牲**：大多数人只要 ①②（一个能截图发出去的结论）；
要核对的人要 ①②③④⑤⑥（明细、口径、可导出、可打印）。
所以：**明细折叠，但展开后必须完整且可导出**；`pitfalls` 不折叠。

** ♿ 无障碍硬约束**：退/补**禁止只靠红绿区分**，必须同时有「应退 / 应补」文字（约 8% 男性红绿色觉障碍）。

### 9.3 商业化引导：必须看起来是「帮助」

| ❌ 广告位形态 | ✅ 有用的下一步 |
|---|---|
| 「需要专业服务？联系我们」 | 「你的专项附加扣除可能没填全，可补约 ¥1,200」 |
| 悬浮 banner / 弹窗 | 结果页内嵌**情境卡**，与结果同源 |
| 所有场景同一张卡 | 按计算类型分流（`BLOCKED_TYPES`） |

三条纪律：
1. **必须携带信息价值** —— 用户即使不点，也学到了东西；
2. **谈薪人群（`reverse`）永不出服务引导** —— 要传播不要线索（硬约束）；
3. **必须可关且记住** —— 反复弹同一个东西 = 广告。

## 11. 运行时环境：微信 + PWA（不是观感，是可用性）

> ⚠️ **现状：全仓库无 `display-mode` 查询、无微信 UA 检测 —— 适配为零。**
> 用户不是在浏览器标签页里用我们的产品，他们是在**具体的容器**里用。

### 11.1 微信内置浏览器（传播主场 = 获客 + 留资全程在此）

| 约束 | 后果 | 应对 |
|---|---|---|
| Android X5 底部工具栏 | 视口被挤掉 44–50px，**相当于凭空多一层底栏** | 微信环境再叠一层 inset，固定底栏抬高 |
| **`download` 属性被拦截** | 导出 PDF/CSV 大概率失败 | 见下方三条出路 |
| 字体栈回退 | `-apple-system` 在安卓微信落到系统中文字体，**行高与排版会变** | 中文必须显式指定字号 + 行高令牌，不依赖系统字体度量 |
| 外链只能同窗跳转 | 政策依据外链 → 用户离开即流失 | 政策依据做**页内展开** |

**移动端交付的三条出路**（这会改变「可交付」能力的排期判断）：
1. **结果长图** —— 复用 `export/capture.js`，含结论 + 推导链 + 政策依据，长按即可保存；
2. **复制为纯文本** —— HR 场景极实用，可直接粘进 Excel / 微信对话；
3. **「在浏览器打开」提示** —— **仅在检测到导出确实失败时**才提示，不常驻。

> **纪律：不常驻任何环境提示。** 常驻的「请在浏览器中打开」是把自己的能力缺陷转嫁给用户，且它挂在每一屏上、对所有人都没用。

### 11.2 PWA 独立窗口（最有价值的那批用户在的形态）

装机用户是留存最高的，但他们**失去了浏览器给的兜底**：

| 失去什么 | 必须自己补什么 |
|---|---|
| 地址栏与刷新 | **不允许出现死胡同**：任何页面都要能回到起点，否则用户只能杀进程 |
| **系统返回键 / 手势** | History 必须与**视觉层级**一致；否则「返回」会跳错页，甚至在向导中途直接退出应用 —— 这是分步向导的**直接前置依赖** |
| 外链跳出容器 | 同微信：政策依据页内展开 |

必须做的两条：
1. `@media (display-mode: standalone)`：提供**应用内返回 / 首页出口**，并补贴安全区；
2. 向导 History 策略：`history.pushState`，**绝不允许系统返回 = 退出应用**（用户会理解成「这软件崩了」）。

## 12. 后期开发注意事项

### 12.1 资源筛子（所有需求先过这一关）

> 三个问题：**能带来关键词吗？能带来线索吗？能解锁收款吗？**
> 三个都不能 → 排队或砍。（哪怕技术上很优雅。）

按此标准：阶段15A 是获客弹药，SEO 落地页是获客弹药，15B 是弹药 + B 端前置；
而纯架构优化与体验打磨，在拿到第一批成交之前都应靠后。

### 12.2 三条单一真源（新增代码不许绕过）

| 关注点 | 单一真源 | 位置 |
|---|---|---|
| 页面切换 | `showPage()` | `auth-ui.js:2412` |
| 导航状态 | `syncNav()` | `toolbox-ui.js:540`（旧别名 `updateTabBar` 保留兼容） |
| 设计取值 | `tokens.css` | 与 `tailwind.config.js` **同值镜像** |

**不许 `?.` 静默吞错**：`toolbox-ui.js` 对缺失依赖走 `console.warn`。
前车之鉴：`auth-ui.js` 的死选择器靠 `?.` 抹错多年未被发现。

### 12.3 Tailwind 是构建期产物（最容易踩的一颗雷）

站点的显隐几乎全靠 Tailwind 工具类（`.hidden` / `.flex`）。自 1.38.0 起产物 `src/css/tailwind.css` 随源码入仓，
这换掉了「CDN 抖动」的老风险，却换来一个**更容易真发生**的：**改了类名没跑 `npm run build:css`、或新产物忘了提交**。

此时 `.hidden` 会**静默失效** —— 类名还挂在 DOM 上、控制台零报错，但登录页盖住整个应用，
用户看到的是「登录没反应 / 永远停在登录页」。

> 💥 **这颗雷在 2026-09-17 已经爆过一次（真实事故，不是假设）**：
> v1.41.0 Phase 2 往 `tailwind.src.css` 加了 `result-conclusion` / `result-reason` / `result-disclaimer` 三个类，
> **产物一直没重建** —— 类名挂在 DOM 上、控制台零报错，而这三个类在页面上**完全没有样式**。
> v1.41.1 补 `build:css` 后才真正生效，并加了 `tests/ui-result-compliance.test.js` 的
> 「`@apply` 自定义类必须真的进了产物」断言守住它。

**纪律**：
1. 动了任何 Tailwind 类名 → **必须 `npm run build:css` 并把产物一起提交**；
2. `tokens.css` 末段有 display 类兜底（不使用 `!important`，以免压制 `md:flex` 一类响应式变体）；
3. 顺序不可调整：`.hidden` 必须排在所有 display 类之后。

### 12.4 缺视觉回归 → 小步迭代纪律

截至今日项目**无截图对比能力**。凡涉及「观感」的部分（分享图、打印、断点形态）目前只能人工核对。

因此：
- 所有 UI 改动**拆小步、每步可独立回滚**；
- 每一步都用**断言**把契约钉住（而不是「人眼看过了」）；
- 这也是手机任务页顶栏那 56px 暂时不动的原因：收益是锦上添花，回退动的是登录路径，性价比不对等。

**建议补的第一条**：端到端「计算页必须可返回」断言 —— 补齐后才动那 56px。

### 12.5 新页面的准入清单（一个都不能少）

新增 SEO 落地页时：
1. `sitemap.xml` 收录（**新页必须同时进 sitemap，否则门禁红**）；
2. `robots.txt` 允许的公开路径；
3. `canonical` 指向自身；
4. `FAQPage` 结构化数据 + 政策依据文号；
5. 静态税率表与常量文件**逐档一致**的守护断言（`verify:local`）；
6. CTA 带 `?source=seo_<page>` 且**服务端 `SOURCES` 白名单同步登记**；
7. 轻量计算与内核**逐点对拍**的单测；
8. 加载 `tokens.css`（漏一个页面就是裸色，而 `landing.css` 自己看不出来 —— 只能从页面侧钉）。

新增 App 视图时：
1. `.page` 容器 + 唯一 id；
2. 视需要进 `syncNav()` 的 `TAB_PAGES` 白名单；
3. 固定层取 `--z-*` 令牌；
4. 跑通 PWA standalone 的返回路径（不死胡同）。

### 12.6 需要补齐的合规缺口

- **20 个速算器屏幕缺免责声明**（导出与分享图都有，屏幕上没有）。补齐文案统一为：
  「本测算结果仅供参考，不构成税务建议；实际纳税请以税务部门核算为准。」
- **退/补不只靠颜色**、**键盘可达（Tab + Esc 关闭浮层）** —— 两条是**会真实阻断使用**的，优先于其他无障碍项；
- 金额建议用 `<output>` 或带 `aria-live`。

### 12.7 全税种完整测算的强制顺序（不许跳步）

**这是本站的核心功能**（§4.2：按税种类别，2026-09-18 施工前只覆盖 **1/6**；
vat / cit / social / fee / 附加税印花税交付后为 **6/6** = 全部 6 类）。**税种类别已齐**；
17B 反向迁移（验收口径：页面式归零）**已于 v1.46.0 → v1.50.0 收官** —— 剩下的是 `iit` 场景补齐（17D）：
**劳务报酬预扣预缴已随 17D-1 / v1.52.0、年终奖择优已随 17D-2 / v1.53.0、股权激励已随 17D-3 / v1.54.0、
离职补偿已随 17D-4 / v1.55.0、提前退休内退已随 17D-5 / v1.56.0、外籍津补贴免税已随 17D-6 / v1.57.0
落地** —— 个税 **10/16 场景，17D 的目标全部达成**；17D-7（v1.63.0）年度汇算清缴、17D-8（v1.64.0）
专项附加扣除继续把它推到 **12/16**。
目标：**6 类税种/费种，每类一套 `status:'deep'` 完整测算**。

不抽 solver 就直接铺第 5 个税种，必然重演 `tax-calculator.js` 2569 行、反向求解手写 6 套的技术破产。

| 步 | 内容 | 状态 |

| ① **提炼通用 solver** | 6 套手写求解 → `solver.js` 的 `solveMonotone()` / `expandUpperBound()`（97 行，零税务口径，现有 4 个流程行为不变） | ✅ **v1.41.0 已交付** |

> 也不触碰 `tax-calculator.js`（直接复用既有 Quick 纯函数）。向导的分区与排版规格见 [`deep-wizard-ui-spec.md`](deep-wizard-ui-spec.md)。

> **硬依赖顺序**：`surtax` / `stamp` 的计税依据是**实际缴纳的增值税** → 必须排在 `vat` deep 之后，不许并行。
> `iit` 的场景补齐（劳务报酬 / 年终奖 / 股权激励等）可与第 ②③ 步同批，因为它们已有 `spec` 可参照。

## 13. 验收口径

| 维度 | 口径 |
|---|---|
| **北极星** | `lead_submit / calc_done` **不降**（改版唯一验收标准） |
| **核心功能覆盖** | App 内完整测算（`status:'deep'`）覆盖的**税种类别数** —— 以 `tax-registry.js` 的 `category` 计（6 类：iit / vat / cit / surtax+stamp / social / fee）。**目标 6/6，现状 1/6**（§4.2）。新增税种以该数字 +1 为验收，**不许出现「只有速算器、没有完整测算」的税种** |
| **五步漏斗** | visit / calc_done / save / share / lead_click 不断崖 |
| **工程门禁** | `verify:local` 全绿；`npx jest` 全绿（含 `BLOCKED_TYPES` 断言） |
| **固定层预算** | 手机顶层页 ≤16%；任务页 ≤18% |
| **无障碍** | 正文对比度 ≥4.5:1；触摸区 ≥44px；退/补不只靠颜色 |
| **设备矩阵** | 360 / 390 / 768 / 1024 / 1280 / 1920 六档 + 横屏 + 字号 200% 各过一轮 |
| **运行时环境** | 微信（安卓 + iOS）完成一次完整计算并可交付；PWA standalone 无死胡同、返回不退出应用 |
| **对账能力** | 任取一个工具，用户能沿推导链逐级核对到政策依据 |
| **分享图** | 与改版后主站视觉一致，`?source=share` 归因仍可用 |
| **打印** | 深色模式下不出现「白纸白字」；表头每页重复 |
| **变现链路** | 留资 → ProCode → 兑换 → 精装报告全链路可走通；免费版导出能力**无倒退** |

> **已知缺口**：项目**缺视觉回归**。上表中凡涉及「观感」的目前只能人工核对，这也是 §12.4 小步纪律存在的原因。
