# 阶段19 · UI 重构与留存设计方案

> 目标：把 EuriskoTax 从「41 个计算器的集合」升级为「**一个人的税务工作台**」——
> 让首次访问者 3 秒内知道该干什么，让算完的人有理由明天再来，让高价值人群自然走到顾问面前。
>
> 本文分四部分：① 现有核心功能全景 ② 竞品精读与自我诊断 ③ 新设计方案 ④ 分阶段落地路线。
> 现状基线：v1.76.0 ｜ 20 速算器 + 21 深度测算 ｜ 94 测试套件 / 门禁 259 项 / 线上指纹 37 项。

---

## 0. 一句话结论

> **我们最大的资产是「全税种 + 本地隐私计算 + 政策依据」，但现在的 UI 把它呈现成了「一堆按钮」。**
> 重设计的本质不是换配色，而是给产品装一条**主线**：
> `我是谁 → 我今年这件事 → 算 → 存成资产 → 到点回来 → 需要时找人`。

### 1.3 商业架构要点（UI 必须服务它）

- **铁律**：计税能力永不锁，锁的是云端增值（同步 / 方案库 2→10 / 精装报告）。
- **北极星**：`lead_submit / calc_done`（分母不是 visit）。漏斗 `visit → calc_done → share/save → lead_click`。
- **客群分层**：个体户·个独 ★★★（强引导留资）｜小微企业主 ★★★｜财务HR ★★★（B 端第二曲线）｜汇算纳税人 ★★☆｜**打工人 ★☆☆（谈薪场景硬约束：只出分享图，不出服务引导）**。
- **获客**：21 个 SEO 落地页 + 分享图裂变 + 社媒冷启；**站内零购买语义**，一律「留资 → 线下发码」。
- **现状**：0 用户 0 收入未推广，收入瓶颈 = 线索质量 × 顾问承接能力。

## 2. 竞品精读与自我诊断

### 2.1 竞品矩阵：取其精华，弃其糟粕

| 竞品 | 精华（要抄） | 糟粕（不抄） |
|---|---|---|
| **TurboTax TaxCaster** | ① 一屏一问，进度条常驻 ② **估算结果始终可见**（填的过程中数字实时变） ③ 把"报税"这件焦虑的事做成陪伴式引导 ④ 结束页立刻给"下一步" | 过度营销、强推付费升级打断流程 |
| **NerdWallet Tax Calculator** | ① **左输入 / 右结果双栏实时联动** ② 结论先行、推导折叠 ③ 结果页带图表可视化 ④ "还能怎么少交"的提示卡 | 广告密度高、参数一次性暴露太多 |
| **国内个税工具站**（365工具网 / 工具派 / 100Tools / 小波财税） | ① 一屏表单即时出结果 ② 年终奖「单独 vs 合并」择优对比（我们也有） ③ 五险一金城市预设 | ① **纯工具无留存**：算完即走，无历史/无账号/无回访 ② 等权罗列一堆计算器，无身份引导 ③ 结果页无下一步 ④ 无政策依据 → 不敢信 |
| **支付宝 / 微信内个税小工具** | 轻、即时、嵌在场景里 | 只覆盖月薪个税，无深度 |
| **Excel 派代账/财务** | 可留存、可对比、可导出 | 门槛高、不会算、政策过期不自知 |

**结论**：竞品把「算」做到了极致，把「留」全部放弃了。
**我们的机会 = 竞品的强项（算）+ 竞品的空白（资产沉淀 · 回访理由 · 可信度 · 人的服务）。**

### 2.2 自我诊断：5 个留存断点

| # | 断点 | 现象 | 后果 |
|---|---|---|---|
| **B1** | **首页无主线** | 9 个区块纵向平铺、等权无焦点；首屏「你好 👋 + 今日税感 + 搜索框」，用户不知道先干嘛 |  bounce 高，工具站通病 |
| **B2** | **41 入口等权罗列** | 工具页 5 组平铺，卡片长得都一样；`index.html:529` 文案还写着「24 个」（已过期） | 选择过载 → 最大优势（全税种最全）变成认知负担 |
| **B3** | **结果是终点，不是起点** | 结果页给完数字就到免责声明；保存/导出/分享藏在折叠里 | 算完即走，无资产沉淀 |
| **B4** | **回访引擎空转** | 税务日历是静态列表，与「我的测算」不通；没有「距你上次测算 92 天 / 距申报截止 17 天」 | 唯一天然的回访钩子没用上 |
| **B5** | **权益钩子埋太深** | 升级入口仅 `#topbar-plan-badge` 与 `#profile-nav-upgrade` 两处；云同步/方案库的价值用户在关键时刻感知不到 | 转化漏斗断在最后一步 |

**补充 UX 债**：
- 速算器结果无可视化（只有数字表），桌面右侧大片留白未利用。
- 「最近计算」是一次性流水，没有「方案」心智（存了也不知道能对比什么）。
- 深色模式有，但页面层次全靠 `#ffffff / #f9fafb` 两档，卡片与背景几乎同色 → 视觉平、无纵深。

## 2.5 两个极端用户的完整使用旅程（后续所有设计的依据）

> 本节回答一个问题：**一个完全不懂税务的人，和一个财务人员，分别是怎么用这个软件的？**
> 先把两条旅程走通，再反推产品效果、使用流程与 UI。后面 §3 的所有设计都从这里推导。

### 2.5.1 用户 A：完全不懂税务的人（"小白"）

**他为什么来 —— 触发他的永远是生活事件，不是税种**

| 触发事件 | 他脑子里的问题（原话） | 对应的税事 |
|---|---|---|
| 这个月工资到账 | "怎么扣了这么多？是不是扣错了？" | 月薪个税 |
| 发了年终奖 | "我能拿到手多少？" | 年终奖个税 |
| 拿到 offer / 谈薪 | "税前 2 万，实际到手多少？" | 税后倒算 |
| 刷到"个税退税" | "我能退吗？能退多少？" | 年度汇算 |
| 生了孩子 / 在租房 / 父母老了 | "听说能少交点，怎么弄？" | 专项附加扣除 |
| 开了个小店 | "我一年要交多少？" | 经营所得 |
| 要卖房 | "卖了这个房子要交多少税？" | 跨税种组合 |
| 被裁员拿补偿 | "这笔钱要交税吗？" | 离职补偿 |

> **关键**：他的词汇是「工资 / 到手 / 年终奖 / 房贷 / 孩子上学」，
> **不是**「综合所得 / 分类所得 / 应纳税所得额」。当前 UI 用后者当入口，第一道门就把他挡在外面。

**他不知道什么（这才是真正的障碍，不是计算本身）**

1. 他不知道「专项附加扣除」是什么 —— 但他知道"我在租房""我妈 60 了"。
2. 他不知道自己的社保基数、公积金比例。
3. 他不知道该选 41 个入口里的哪一个。
4. 他不知道自己填的数对不对 —— 全程没有"校验感"。
5. 他不知道这个结果能不能信（怕算错、怕被坑、怕信息泄露）。

**他的心理**：怕麻烦（填超过 5 项就想走）· 怕错（算错要补税）· 怕泄露（工资、单位、身份证都是敏感信息）· **要结论，不要公式**。

**理想旅程（6 步）**

```
① 我看到一件跟我有关的事（"发了年终奖"）
② 我用大白话回答 3–5 个问题（月薪多少 · 年终奖多少 · 有没有房贷/孩子）
③ 我立刻看到「到手 ¥XX,XXX」+「这样最划算」
④ 我明白为什么（一句人话；想看细节再展开）
⑤ 我知道还能做什么（补填扣除能省 ¥1,200）
⑥ 我可以存着 / 发给家人 / 问真人
```

**当前产品在这条路上的断点**

| # | 断点 | 说明 |
|---|---|---|
| A1 | 首页给的是**功能入口**，不是**事件入口** | 用户必须先学会税务分类，才知道点哪里 |
| A2 | 术语直给 | 「综合所得 / 分类所得 / 经营所得」是税法分类，不是用户语言 |
| A3 | 41 入口 = 选择过载 | 他只想算一个数 |
| A4 | **无默认值策略** | "参保城市""社保基数"他真的不知道 → 卡死在这里就走了 |
| A5 | 可信度没被表达 | 「数据不出你的浏览器」是**碾压竞品的优势**，却写在「关于我们」里，而不是他第一次要填工资的那一刻 |
| A6 | 算完没有下一步 | 结果是终点 |

### 2.5.2 用户 B：财务人员（中小企业财务 / HR / 代账会计）

**他是谁**：一个人管几十到几百人的工资、几家公司、多个税种的申报。**税对他不是疑问，是重复的活。**

**他的工作流是周期性的**

| 周期 | 做什么 |
|---|---|
| 每月 | 算工资个税 → 做工资条 → 发员工 → 申报 |
| 每季 | 增值税 / 企业所得税预缴 |
| 每年 | 汇算清缴 · 残保金 · 年报 |
| 不定期 | 老板问"这笔业务要交多少税"· 员工问"我为什么扣这么多"· 招聘时算用工成本 |

**他的痛点（和 A 完全不在一个维度）**

1. **要快** —— 同一个场景每周每月反复算，不能每次重填 20 个字段。
2. **要能对上账** —— 算错要背锅，必须能看到逐项明细和公式，能手工复核。
3. **要能交差** —— 要给老板看、给员工看、给税局看，**需要产出物**，不是一个网页上的数字。
4. **怕政策过期**（最大的隐性焦虑）—— "我用的税率是最新吗？这个优惠还在吗？"
5. **要留痕** —— 下个月、明年、被查时，要能还原"当时用的什么口径"。
6. **要能解释给非专业人士** —— 员工问"为什么我扣这么多"，他要一张能发给人看的图。
7. **算的是别人的税** —— 不是一个人的税，是一群人的税。

**理想旅程（6 步）**

```
① 直接进"我这个场景"（他知道要什么，不需要引导）
② 填全参数（或从上次 / 模板带出来）
③ 拿到四件套：预算表 + 逐项明细 + 计算公式 + 政策依据（含生效/到期日）
④ 导出成能发出去的东西（PDF / Word / 表 / 给员工看的说明）
⑤ 存进"我的台账"，下个月一键复用
⑥ 政策变动或到期时被告知
```

**当前产品在这条路上的断点**

| # | 断点 | 说明 |
|---|---|---|
| B1 | **无批量 / 多员工** | `employer-cost` 只有一句"多人再乘人数"的手工提示 → 工资表场景断在这里 |
| B2 | 无参数模板复用 | 有历史、有方案，但没有"月度台账 / 复制上月"心智 |
| B3 | **政策时效零产品化** | `tax-registry.js` 里 `effectiveFrom` / `expiresOn` / `statusOf` / `expiringWithin` **全都已经有**，但 UI 上没渲染 —— 现成的资产在睡大觉 |
| B4 | 结果不标政策版本 | 用户不知道这次算用的是哪一年的政策 |
| B5 | 导出 ≠ 可交付物 | 现在导出的是"计算结果"，不是"发给员工的工资条说明 / 给老板的税负报告" |
| B6 | 无周期提醒 | 税务日历是静态列表，没和"我的岗位/我的公司/我的申报周期"绑定 |

### 2.5.3 对比矩阵（后面所有 UI 决策都查这张表）

| 维度 | 用户 A（小白） | 用户 B（财务） |
|---|---|---|
| 需求触发 | **生活事件**（偶然） | **工作周期**（必然） |
| 算谁的税 | 自己的 | **别人的**（老板 / 员工 / 企业） |
| 术语 | 不懂，也不要懂 | 精通 |
| 参数 | 越少越好，要默认值 | 越多越好，全部可调 |
| 结果 | **一个结论 + 一句人话** | **明细 + 公式 + 依据 + 产出物** |
| 核心焦虑 | 对不对？会不会被坑？ | 会不会错？政策过期没？ |
| 用完要什么 | 存着 / 分享 / 问人 | 导出 / 存档 / 复用 / 交差 |
| 留存靠什么 | **记住我的情况**（下次别让我重填）+ 下次事件提醒 | **台账 / 模板 + 周期提醒 + 政策预警** |
| 商业价值 | ★☆☆（打工人，硬约束不打扰） | ★★★（ICP，要引导留资） |

> **最本质的一句**：
> 对 A，税是**一次性的疑问** → 产品要给他**确定性**。
> 对 B，税是**重复性的工作** → 产品要给他**效率和证据**。

### 2.5.4 共同点（决定产品底座，不能为两类人做两套）

A 和 B 都要「可信」，只是形式不同：

- A 要**敢信** —— 凭什么信你？（数据不出浏览器 + 有依据 + 说人话）
- B 要**能证明** —— 凭什么交差？（文号 + 有效期 + 可复核）

→ 所以 **本地计算 + 政策依据库（`basis` 文号 / `effectiveFrom` / `expiresOn`）+ 推导链** 是同时服务两类人的核心资产，
必须在 UI 上**显性化**，区别只在呈现深度：A 折叠成一句话，B 全展开。

### 2.5.5 由此确定的产品效果

**一句话定位**：把**生活事件**翻译成税，把税翻译成**人话**和**证据**。

**产品效果三条（验收标准）**

1. 小白进来 **30 秒**内得到一个他听得懂的结论。
2. 财务进来 **3 分钟**内得到一份能发出去的东西。
3. 两类人都**敢把结果拿去做决定**。

**各自的成功定义**

| 用户 A | 用户 B |
|---|---|
| ① 知道该用哪个（不用先学税务） | ① 不重复填（模板 / 复制上月） |
| ② 填完不需要查任何资料 | ② 结果能对上账（明细 + 公式） |
| ③ 看得懂结果 | ③ 有文号、有日期，可交代 |
| ④ 知道下一步（还能省多少） | ④ 政策变了/快到期了，他知道 |

### 2.5.6 由此确定的使用流程（两条主线 + 一个共用底座）

```
              ┌────────── 共用底座（单一真源，不许分叉）──────────┐
              │  计税引擎 tax-calculator · 政策库 tax-registry    │
              │  结果八段模板 · 导出 · 历史/方案存储              │
              └──────────────┬─────────────────┬────────────────┘
                             │                 │
        主线 A（事件式）      │                 │    主线 B（周期式）
        ┌────────────────────┘                 └────────────────────┐
        │                                                           │
  生活事件入口                                              场景/税种直入
        ↓                                                           ↓
  大白话提问 3–5 个                                    填全（模板/历史带入）
        ↓                                                           ↓
  即时结论 + 「这样最划算」                        结果四件套：预算表·明细·公式·依据(含到期日)
        ↓                                                           ↓
  一句人话解释（细节可展开）                              导出为可交付物
        ↓                                                           ↓
  下一步：还能省多少 / 去补填                           存进台账 → 下月一键复用
        ↓                                                           ↓
  存为「我的情况」（下次不重填）                      政策到期/申报节点提醒
```

两条主线**共用同一套计算、同一套结果模板**，差异只在四处：**入口形态 · 字段密度 · 结果展开深度 · 产出物**。
—— 这正是 §3.9「简明 / 完整」双视图存在的理由：它不是"新手/专业"的身份标签，而是**两条主线的不同呈现深度**。

### 2.5.7 由此确定的 UI 设计六条结论

1. **首页双入口，但不要让用户回答"你是谁"**
   上半屏「**我遇到了什么事**」（事件卡：发了年终奖 / 换工作 / 要卖房 / 我开了店 / 我要发工资）；
   下半屏「**按税种场景直接查**」（搜索 + 分组，服务 B）。
   用户不需要选身份，他只需要**点一件跟他有关的事** —— 这比任何"模式开关"都自然。

2. **术语分层：用户语言在上，税言在下**
   入口用事件语言，结果用结论语言，只有点开"详情"才出现「应纳税所得额」「财税〔2018〕164 号」。

3. **默认值策略是 A 路径的生死线**
   每个他不知道的字段都要给「大多数人是多少」的默认值 + 一句「不知道就先按这个，结果差不多」。

4. **结果页双深度**（= §3.9 双视图）
   A：Hero + 结论 + 一句人话；B：默认展开明细 + 推导链 + 政策依据（含生效/到期日）。

5. **财务专属三件套（数据已就绪，成本极低）**
   - 政策有效期标注：结果里直接渲染 `expiresOn` →「本项优惠 2027-12-31 到期」
   - 政策到期预警：`expiringWithin` → 我的页「你关注的 3 项政策将在 12 个月内到期」
   - 月度台账：历史记录升级为按场景归档的台账 +「复制上月」
   - （批量算工资表 = 新增能力，成本最高，排最后）

6. **可信度要在最痛的那一刻说，不要写在"关于我们"里**
   「你的数据不会离开这台设备」这句话，应该出现在**他第一次要输入工资数字的输入框旁边**，而不是关于页。

### 2.5.8 其余身份人群逐类分析（补充）

> 上两节只覆盖了「打工人」和「企业财务」。但产品实际面向的人群远不止两类，且**遗漏的那部分商业价值更高**。
> 先给分类方法，再逐类分析。

**分类方法：两层 persona 正交**

| 层 | 是什么 | 决定什么 | 例子 |
|---|---|---|---|
| **常态 persona**（职业 / 身份） | 你长期是谁 | **默认视图**（默认展开哪些字段、什么深度、什么产出物） | 打工人 · 自由职业 · 老板 · 财务 · 代账 · HR · 外籍 |
| **事件 persona**（人生事件） | 你这次遇到了什么 | **这次进来干什么**（走哪条主线、用哪个入口） | 卖房 · 拿期权 · 被裁 · 生孩子 · 第一次工作 |

> 关键洞察：**任何人都会在某个时刻变成"卖房的人""拿期权的人"**。
> 事件 persona 与职业身份无关 —— 一个财务总监卖房时，他的需求和一个小白卖房时是一样的。
> 这正好印证 §2.5.7 的结论：**首页上层放事件卡（覆盖所有人的"这次"），下层放身份/税种索引（服务"我的常态"）**。

---

#### C. 老板 / 小微企业主 / 个体户 ★★★

- **他是决策者，不是执行者。** 他不关心申报流程，他关心「哪个方案省钱」「合规吗」「风险多大」。
- **他的税**：经营所得 · 增值税（小规模）· 企税 · 自己的工资个税 · 用工成本。
- **痛点**：
  1. 分不清「核定征收」还是「查账征收」（项目里已有这个易错口径，说明做过）
  2. **临界点**：月销售额 10 万 / 季 30 万免征额 —— 差 1 块钱多交几千，**这是他最痛的决策点**
  3. 「我该给自己发多少工资最划算」（工资 vs 分红的取舍）
  4. 公司钱和个人钱分不清
- **他要的**：**方案对比**（A 方案 vs B 方案）+ **临界点预警**（"再开 ¥5,000 就超 30 万了"）+ 风险提示
- **当前断点**：工具是「算一个数」，不是「比两个方案」；临界点零预警；无"发多少工资最划算"的筹划
- **为什么重要**：**付费意愿最高的群体**，且背后是一整个企业客户

#### D. 代账会计 / 财税顾问 ★★★（价值被严重低估）

- **和企业财务的关键区别**：**多主体**（管 20 家公司的账）+ **给客户交差**（不是给老板）+ **政策必须最新**（靠专业吃饭，用错政策会丢客户）。
- **痛点**：① 在多个主体间反复切换、反复填同样的参数 ② 要给客户看得懂的报告 ③ 政策变动必须第一时间知道
- **他要的**：**主体切换器** + 批量/模板 + **可交付给客户的报告**
- **当前断点**：无多主体、无批量、导出物不是"给客户看"的形态
- **为什么重要**：**渠道型用户** —— 一个代账背后是几十家企业客户，是**获客杠杆**，不是单个用户

#### E. HR / 薪酬 ★★

- **和财务的区别**：他关心的是**人的成本**和**员工感受**，不是税种本身。
- **场景**：offer 谈判（税前/税后倒算）· 用工总成本 · 社保公积金 · 工资条解释
- **痛点**：① "候选人要税前 30 万，我成本是多少" ② **员工总来问"为什么这个月扣这么多"**（累计预扣法导致下半年税额递增，这是 HR 每月的重复劳动）③ 社保基数调整的影响
- **他要的**：**能直接发给员工的说明材料**（这是刚需，每月重复）
- **当前断点**：无「给员工看」的产出物模板；无批量工资表
- **为什么重要**：和财务同源，能带来企业客户

#### F. 自由职业者 / 灵活就业 / 副业者 ★★

- **和打工人的关键区别**：**他没有单位替他算**。打工人有雇主代扣，他必须自己搞明白、自己申报。
- **他最大的困惑**（这是比小白更严重的翻译层缺失）：
  1. **"我这笔钱是劳务报酬还是经营所得？"** —— 差别巨大：劳务 20–40% 预扣 vs 经营所得 5–35% 且**能扣成本**。选错税种，多交几万。
  2. 平台已经代扣了，汇算能退多少？
  3. 自己交的社保能扣吗？
  4. **要不要注册个体户？**（开票 vs 劳务费）
- **他要的**：**先判定身份**（我是哪种所得），再算；以及"注册个体户划算吗"的对比
- **当前断点**：工具按税种组织（劳务报酬 / 经营所得各一个），但**他根本不知道自己是哪种** —— 和小白 A1 是同一类断点
- **为什么重要**：人数增长最快的群体，且问题 4 天然导向 C（老板），是**身份跃迁的转化路径**

#### G. 房产交易者 ★★☆（事件 persona）

- **特征**：低频、高额、一次性、决策极敏感（涉及几十万到几百万）。
- **痛点**：① 「满五唯一」到底免不免 ② **极度不信任中介给的数，需要自己核对** ③ 买卖双方各自承担哪些税
- **他要的**：**可信 + 可逐项核对** + **完整清单**（不止个税，还有增值税、契税、附加）
- **当前断点**：**跨税种组合**能力没有产品化（现在是一个一个税种单独算）
- **为什么重要**：一次性，但**分享率最高** —— 他要发给配偶/家人/中介核对 → **天然裂变**

#### H. 股东 / 高管 / 高净值 ★★★（事件 persona）

- **场景**：股权转让 · 股权激励（期权/限制性股票）· 股息红利 · 大额年终奖
- **痛点**：① 金额大，**错不起** ② **政策到期**：股权激励、年终奖单独计税政策均 `expiresOn: 2027-12-31`（数据已在库里！）③ **筹划需求**：什么时候行权/兑现最划算
- **他要的**：**筹划**（时间维度对比）+ 政策有效期 + 极高的可信度
- **当前断点**：只算当期，不算"什么时候做最划算"；政策到期未提示
- **为什么重要**：**客单价最高**，且天然导向「找专家」→ **留资转化最优场景**

#### I. 外籍 / 港澳台 / 无住所个人 ★★

- **场景**：183 天居民身份判定 · 境内境外所得分摊 · 外籍津补贴 vs 专项附加扣除二选一
- **痛点**：**几乎没人能算对，市面上没有工具**
- **当前状态**：项目里已有专属政策（无住所个人、外籍津补贴 `expiresOn: 2027-12-31`）—— **竞品空白区**
- **为什么重要**：人少，但 **零竞争 + 高单价 + 外企 HR 是天然渠道** → SEO 差异化利器

#### J. 离职 / 内退 / 提前退休 ★☆（事件 persona）

- 一次性补偿、内退、提前退休三种算法完全不同（项目里都有）
- 痛点：拿到一笔钱不知道要交多少，且网上说法互相矛盾
- 价值：单次，但**情绪浓度高**（刚被裁）→ 转化窗口极短但很强

#### K. 学生 / 职场新人 ★☆

- A 的变体，但**更不懂**：连"五险一金"是什么都不知道
- 需要更强的默认值 + 科普（"为什么第一个月扣这么少/多"）
- 价值：当下低，但是**全生命周期的起点**（他会一路变成 F、G、H）

### 2.5.10 由此新增的 UI 结论（对 §2.5.7 的补充）

7. **双轴导航（最重要的结论）**：
   首页上层 = **事件卡**（"卖了房""拿了期权""被裁了""第一次工作"）→ 覆盖所有人的"这次"；
   首页下层 = **身份/税种索引**（老板 · 财务 · 代账 · HR · 自由职业 · 外籍）→ 服务"我的常态"。
   两层正交，**不需要用户先回答"我是谁"**。

8. **主体切换器**（服务 D，顺带服务 B/C）：
   顶部「当前主体：XX 公司 ▾」，一套参数按主体归档。**这是代账的命门**，也是多公司财务的刚需。

9. **方案对比**（服务 C，决策者的核心诉求）：
   不是"算一个数"，是**"比两个方案"** —— 核定 vs 查账、工资 vs 分红、单独计税 vs 并入综合所得。
   左右对照 + 差额高亮 + 结论句。

10. **临界点预警**（服务 C，成本极低、价值极高）：
    "再开票 ¥5,000 就超过季度 30 万免征额，预计多缴 ¥X" —— 免征额数据已在 `tax-registry`。

11. **身份判定前置**（服务 F，和 A1 同源的翻译层缺失）：
    进计算器**之前**先问 2 个问题判定"你这笔是劳务报酬还是经营所得"，再进对应工具。

12. **产出物按接收方分角色**（服务 B/D/E）：
    同一份结果，三种导出模板 —— **给员工看**（HR）/ **给客户看**（代账）/ **给老板看**（财务）。
    现在只有"导出 PDF/Word"，是**计算结果**，不是**可交付物**。

13. **高客单价事件导向专家**（服务 G/H）：
    房产、股权这类"错不起"的事件，结果页天然是留资最优位置 —— 但要**先给足可信度再引导**（政策文号 + 推导 + 限额提示），而不是一上来就弹窗。

### 2.5.11 对 §3 方案的修正（整合前次三条）

1. §3.3 首页「按身份挑工具」→ 升级为「**事件卡（上层）+ 身份/税种索引（下层）**」双轴导航，身份卡降为次级分组。
2. §3.5 结果页新增一段「**政策依据（含有效期）**」—— 对 A 折叠为一行小字，对 B/D 默认展开并带到期日。
3. §3.8 留存机制新增：⑧ **政策到期预警**（服务 B/D/H）、⑨ **主体/台账归档**（服务 B/D）、⑩ **临界点提醒**（服务 C）。
4. §3 新增设计项：**双轴导航首页**（§3.3）、**主体切换器**（§3.3 区块② / §3.10 E1）、**方案对比视图**（§3.5 结果页分支）、**分角色导出模板**（§3.10.7）。
5. **新增 §3.10「效率层」**（后续开发，阶段 19-8 ~ 19-11）：主体 E1 → 模板 E2 → 台账 E3 → 快捷提效 E5 → 批量 E4，服务于 B/C/D/E 的"重复性工作"而非一次性疑问。

## 3. 新设计方案

### 3.1 设计主轴：Mission-driven 工作台

> **旧心智**：我有一堆计算器，你自己挑。
> **新心智**：我知道你是谁、你现在该办哪件事、上次算到哪了。

```
首屏 Mission Hero（1 个主行动，动态）
      ↓
身份/场景收敛（不用看完 41 个）
      ↓
算（速算器一屏 / 深度向导分步，结果始终可见）
      ↓
结果 = 结论 + 省钱提示 + 四件可做的事（存/比/享/问）
      ↓
存成「我的方案」→ 绑定申报节点 → 到点回来
      ↓
需要人工核对 → 情境顾问卡（仅高价值 ICP）
```

### 3.2 信息架构（IA）重构

| 层 | 旧 | 新 |
|---|---|---|
| Tab | 首页 / 工具 / 我的 | **不变**（肌肉记忆，不动） |
| 首页 | 9 区块平铺 | **3 段式**：Mission Hero → 我的税务资产 → 发现（降权） |
| 工具页 | 5 组等权平铺 | **推荐(动态) → 按身份 → 全部（默认折叠，搜索优先）** |
| 结果页 | 单列纵向 | **桌面双栏**（左输入 sticky、右结果），手机保持单列 + 结果吸底 |
| 我的 | 横幅 + 4 卡 + 发射台 | **权益进度条 → 资产概览 → 功能（按场景分组）** |

### 3.3 首页：双轴导航（事件轴 × 身份轴）

> 依据 §2.5.8：常态 persona（你长期是谁）× 事件 persona（你这次遇到什么）**正交**。
> 首页因此给出**两条并列的路径**，且**不需要用户先回答"我是谁"** —— 他只需要点一件跟他有关的事。

#### 3.3.1 区块顺序（新）

```
① 公告条（可关）
② 主体切换器（顶栏右侧，仅当已建主体时显示）        ← §3.10 E1
③ Mission Hero（首屏唯一焦点，动态三态）
④ 【上轴】我遇到了什么事 —— 事件卡组（横向滑动 / 网格）
⑤ 我的税务资产（4 卡，仅回访用户可见）
⑥ 【下轴】我的常态 —— 身份卡组（6 张）
⑦ 常用（动态 6）+「查看全部 41 个 ›」
⑧ 呼吸卡（税感 + 贴士）→ 关于本站
```

**排序理由**：Hero（你现在该办的事）→ **事件轴**（我要做什么·行动）→ 资产（我已有的·回顾）→ **身份轴**（我是谁·导航）→ 兜底（全部工具）。
行动在前、导航在后，符合 §3.1 的 Mission-driven 主轴。

#### 3.3.2 ③ Mission Hero（首屏唯一焦点，动态三态）

| 用户状态 | Hero 内容 | 主 CTA |
|---|---|---|
| 新客（无历史） | 「**你今年要交多少税？**」副文案：「41 个场景，全在你手机里算完，数据不出本机」 | 「开始测算」→ 滚到事件轴（**不再是身份三选**） |
| 有历史 | 「上次测算：**经营所得 应纳 ¥12,340**」+「3 天前 · 2026 年度」 | 「继续」/「换个方案对比」 |
| 临近申报节点 | 「**距经营所得汇算截止还有 17 天**」+ 关联的上次结果 | 「现在更新测算」 |

- 视觉：Hero 是全站唯一使用**品牌渐变 + 大留白**的区域，高度 ≤ 一屏的 45%。
- 原则：**首屏只有 1 个主按钮**。搜索框降级为次级（右上角图标或 Hero 下方细条）。
- **变更说明**：原 CTA 落到「身份三选」，现在落到**事件轴** —— 因为身份不是人人都说得清（自由职业者不知道自己算"上班族"还是"个体户"），但**每个人都认得自己遇到了什么事**（依据 §2.5.8 F）。

#### 3.3.3 ④ 上轴：我遇到了什么事（事件卡）

9 张事件卡，**用生活语言，不用税言**。每张直接落到具体工具：

| 事件卡文案 | 落到 | 服务谁 |
|---|---|---|
| 发了年终奖 | `bonus-tax` 速算 → `bonus-tax-deep` | A |

| 我要卖房 / 买房 | `property-transfer`（跨税种） | **G** |
| 拿了期权 / 要转股权 | `equity-deep` | **H** |
| 被裁 / 离职拿了补偿 | `severance-deep` | **J** |
| 第一次工作 / 看工资条 | `salary-tax` | **K** |
| 生娃 / 租房 / 父母养老 | `special-deduction` | A |
| 开了店 / 接了私活 | 先判定（劳务报酬 or 经营所得）→ `withholding` / `business` | **F / C** |

**交互与文案规则**：
- 卡片 = 「一句大白话」+「一行小字说明」+ 一个箭头，**不出现税种名、不出现术语**。

首屏露出 1.5 张暗示可滑；桌面 `grid auto-fill minmax(220px,1fr)`。
—— 事件卡是首页转化主力，**任何断点都不折叠它**。

### 3.5 结果页：留存的主战场

**桌面（≥1024px）双栏**：

```
┌──────────────┬────────────────────────────┐
│ 输入（sticky） │  结果（实时联动）           │
│ 改一个数字     │  ┌ Hero 金额 + 结论文字 ┐   │
│ 右边立刻变     │  │  ¥12,340  应补       │   │
│              │  └──────────────────────┘   │
│              │  ▸ 还能少交 ¥1,200（省钱卡）  │
│              │  ▸ 推导链（折叠）            │
│              │  ▸ 明细（折叠 + 图表）        │
│              │  ▸ 易错口径（不折叠）         │
│              │  ─────────────────────      │
│              │  [存为方案] [对比] [分享] [导出]│  ← 横向行动条
│              │  ▸ 需要人工核对？找顾问（情境卡）│
└──────────────┴────────────────────────────┘
```

**手机**：单列，但**结果 Hero 吸底**（滚动时底部常驻一条「¥12,340 应补 ▸ 详情」），避免"算完还要往回找数字"。

四个新增设计点：

1. **省钱卡（最强留存钩子）**
   结果旁一张高优先级卡，用**确定性文案**告诉用户还能优化：
   - 年终奖：`单独计税比合并少缴 ¥3,180（已为你选优）`
   - 专项附加扣除：`未填「住房租金」，补填可少缴 ¥1,200`
   - 经营所得：`费用扣除未用满，还可用 ¥8,400`
   原则：**只报确定的、能给依据的**，绝不猜测（政策依据库已有，可复用 `tax-registry`）。

2. **行动条（Action Bar）**
   把「保存 / 对比 / 分享 / 导出」从折叠区提到结果下方一行四按钮（图标 + 短文案），
   这是 `calc_done → save/share` 的转化面，**必须常驻可见**。

3. **情境顾问卡（服务引导，非弹窗）**
   仅对 ICP 白名单场景（经营所得 / 年度汇算 / 综合所得 / 分类所得）在结果末尾内联一张卡：
   > 「测算已出，扣除项是否需要人工核对？我们的顾问可以帮你过一遍 · [留个联系方式]」
   - **不弹窗、可关闭、可跳过**；谈薪场景保持硬约束 `BLOCKED_TYPES` 不出现。
   - 相比现在的弹窗式触点，内联卡的体验更柔、归因更准（`lead-context` 已有情境取数能力）。

4. **结果可视化**
   引入 Chart.js 轻量图表（已在依赖里，`final-report.js` 已用）：
   - 速算器结果：横向条形「收入构成 → 扣除 → 应税 → 税额」四段瀑布（手机折叠）。
   - 深度测算：沿用现有明细表 + 一个构成饼/条。

> ⚠️ **八段模板顺序不许调序**（`ui-design-spec.md` 硬约束）：金额 Hero → 结论（必须带文字）→ 理由 → 推导链 → 易错口径 → 明细 → 下一步 → 免责。
> 新增的省钱卡插在「理由」之后，行动条插在「下一步」位置，**不破坏既有顺序**。

| **跨税种组合** | 1 | `property-transfer` 卖房要交多少税（增值税 + 个税 + 契税 + 附加，一屏出总额） |

> 即：**个税的完整测算早已不止 4 个**，是 15 个；其他税种各 1 个完整测算，共 6 个。
> 用户认知还停留在「综合所得 / 经营所得 / 分类所得 / 反向倒算」四个，说明**首页没有把这 15 个的关系讲清楚** —— 这正是 §3.4 工具页降载要解决的问题（按税种重新组织 + 标注"属于个税"）。

**20 个速算器（quick）按场景组**

| 组 | 个数 | 入口 |
|---|---|---|
| 工资与到手 | 5 | 月薪个税、税后工资倒算、年终奖个税、专项附加扣除、年度汇算清缴 |
| 一次性收入与特殊所得 | 5 | 劳务报酬个税、股权激励个税、离职补偿金、提前退休/内退、外籍津补贴免税 |
| 税优与养老 | 3 | 个人养老金、税优健康险、企业年金 |
| 社保与用工 | 3 | 社保公积金、企业用工成本、残保金与工会经费 |
| 企业与经营 | 4 | 增值税、企业所得税、附加税与印花税、个体户经营所得 |

**速算器 ↔ 完整测算的配对关系（重要，UI 要显性化）**

- **14 组同名配对**：`vat / corporate-income-tax / surtax-stamp / social-base / disability-fund / annual-settlement / special-deduction / bonus-tax / withholding / equity / severance / early-retirement / expat / private-pension` —— 速算器「只想知道一个数」，完整测算「按年填全、出预算表」。
- **7 个只有完整测算、没有速算器**：`forward 综合所得`、`business 经营所得`、`classification 分类所得`、`reverse 反向倒算`、`donation 公益捐赠`、`property-transfer 卖房`、`non-resident 非居民`。
- **1 个只有速算器**：`net-salary 税后工资倒算`、`employer-cost 用工成本`、`health-insurance / annuity`、`business-income 个体户经营所得`（其完整测算版是 `business`）。

> **设计含义**：速算器与完整测算不是两套产品，是**同一件事的两种深度**。
> UI 应该在速算器结果页放一句「想要按年填全的完整版 ›」，在完整测算入口标「≈ 3 分钟 · 出预算表」—— 现在这层关系完全没表达。

#### 3.9.2 对「新手 / 专业」模式的评估：方向对，形态要改

**赞成的部分**：产品确实需要一个"信息密度"开关。41 个入口 + 每个工具 5–20 个字段，对只想算月薪的用户是过载的。

**反对"登录后强制二选一 + 全局互斥模式"的五个理由**：

| # | 问题 | 说明 |
|---|---|---|
| 1 | **自评悖论** | 熟练度是**按税种而异**的，不是按人而异：企业主算增值税很专业，算个税汇算可能一头雾水；上班族算月薪很熟，一遇到经营所得就懵。一个全局开关必然一半场景错配。 |
| 2 | **身份羞辱** | 没人愿意点「新手小白」。命名导致大量用户硬选"专业"，然后在专业模式里被 20 个字段劝退 —— 保护机制反向生效。 |
| 3 | **多一道门就掉一波人** | 北极星是 `calc_done`，且**免登录是核心优势**（游客可直接算）。登录后强制选择 = 在漏斗上再切一刀。 |
| 4 | **全局互斥把「渐进披露」做反了** | 用户在简明模式里想调一个高级参数，必须退出去切模式再回来 —— 正确的解法是**就地展开**，不是全局切换。 |
| 5 | **维护成本翻倍** | 两套入口 + 两套结果模板 + 两套文案 = 41×2 组合，回归面积翻倍，且本项目**没有视觉回归**（§4 前置动作）。 |

#### 3.9.3 改造后的方案：视图密度偏好（可就地切换）

**命名改为「简明 / 完整」** —— 描述**内容密度**，不描述人的水平。副文案：「简明：只填必填项，直接出结论 ｜ 完整：可调全部参数，看逐项推导」。

**模式只影响 3 件事（边界必须写死）**：
1. **输入字段可见性** —— 简明只显示 `level: 'basic'` 字段，其余收进「⚙ 更多参数（可选）」折叠块（**永远可见可展开**，不切模式也能临时用）。
2. **结果展开深度** —— 简明：Hero + 结论 + 一句话理由 +「看完整推导 ▸」；完整：推导链与明细默认展开。
3. **工具页入口密度** —— 简明：推荐 6 + 身份卡，其余收进「全部 41 个 ▸」；完整：默认展开全部（搜索置顶）。

**模式绝不影响 4 件事（防止变成两个产品）**：
- ❌ 计算口径（同一输入必须算出同一个数 —— 单一真源是 `tax-calculator.js`）
- ❌ 可用工具范围（41 个永远都能进）
- ❌ 保存 / 导出 / 分享 / 对比能力
- ❌ 价格与权益

**默认与切换**：
- 默认**简明**，**游客也可用**，登录不是前提（保住免登录优势）。
- 每个计算页右上角一个 `简明 / 完整` pill 开关，**就地切换、即时生效、记住偏好**。
- 「我的 → 偏好设置」保留入口（满足"在我的里切换"的诉求），另加自动升级提示。

**自动升级提示（留存钩子，替代强制选择）**：
算满 3 次后在结果页轻提示一次：「你已算过 3 次 · 切换到**完整模式**可以自己调社保基数、逐项扣除，算得更准」〔切换〕〔不用了〕。
—— 让用户在**有上下文的时刻**做选择，而不是注册时盲选。

#### 3.9.4 逐视图表现

| 位置 | 简明视图 | 完整视图 |
|---|---|---|
| **首页** | Mission Hero + 我的资产 + 身份卡 + 常用 6 | 同上 + 「全部 41 个」入口前置 + 税种分组直显 |
| **工具页** | 搜索 + 身份 chip + 推荐 6 + 折叠分组 | 搜索（自动聚焦）+ 身份 chip + 全部分组默认展开 |

#### 3.9.5 字段分级示例（三档典型）

| 工具 | `basic`（简明可见） | `advanced`（收进"更多参数"） |
|---|---|---|
| **月薪个税** `salary-tax` | 税前月薪、五险一金（默认比例，可开关）、专项附加扣除总额 | 社保基数、公积金比例、年终奖、多处任职、年中跳槽月份、专项附加扣除逐项、商业健康险、递延型养老 |
| **增值税** `vat-deep` | 销售额（含税/不含税）、纳税人类型（小规模/一般）、税率（默认） | 进项税额、征收率、简易计税选择、附加税费率、减免税项目、留抵退税 |

分级原则：**basic = 不填就算不出来 或 80% 用户会填的**；其余一律 advanced。宁可少放。

#### 3.9.6 实现机制（复用阶段17 的 spec 架构，不新增体系）

```
tool-registry.js

新增 src/js/ui/mode-pref.js

  存储：localStorage['euriskoPrefMode']（游客）；登录后随档案同步（后端偏好字段，待定）

渲染器改动（两处，均为过滤而非重写）
  toolbox-ui.js      → visibleFields(fields) 按 mode 过滤；advanced 组渲染为折叠块
  deep-wizard-ui.js  → stepsOf(tool) 按 mode 过滤；被折叠的步骤用默认值参与计算
```

**三条守护测试（必加）**：
1. **口径对拍**：同一组输入在两种视图下，`compute` 结果**逐项相等**（`toBeCloseTo(x,6)`，不用 `toEqual`）。
2. **默认值一致**：简明视图隐藏字段的默认值 = 完整视图的默认值（防两套默认值）。

#### 3.9.7 商业价值：视图模式是白捡的高意图信号

选**完整视图**（或手动展开过"更多参数"）的用户，极可能是财务 / HR / 企业主 —— 正好是 ICP ★★★。
建议把 `mode` 与 `advancedFieldsTouched` 写进 `lead-context` 的情境与线索表，作为**线索质量分层**依据：同样的手机号，"完整视图 + 调过社保基数" 的线索优先级应高于 "简明视图 + 只填了月薪"。这比任何猜测都准，且零采集成本。

> 约束不变：谈薪场景仍受 `BLOCKED_TYPES` 硬约束，完整视图也不例外（视图不是解锁服务引导的钥匙）。

### 3.10 效率层：让财务「把活干完」，而不只是「算出个数」

> 依据 §2.5.2 / §2.5.8：对 B（财务）、C（老板）、D（代账）、E（HR）而言，税是**重复性的工作**。
> 他们缺的不是"会算"，是**不重复填、能批量、能复用、能交差**。
> 本节把「批量处理 / 多员工管理 / 模板复用 / 其他提效能力」收敛为一个**效率层**，作为 §3 之后的后续开发规划。

#### 3.10.1 先划清三个容易混的概念（心智模型）

| 概念 | 存的是什么 | 用来干什么 | 现状 |
|---|---|---|---|
| **方案 Scenario** | **结果快照**（算出来的数） | **对比**（A 方案 vs B 方案） | ✅ 已有 |
| **模板 Template** | **输入快照**（填进去的参数） | **复用**（下次一键带出） | ❌ 缺 |
| **台账 Ledger** | **按周期归档的方案序列** | **追踪 + 复制上月 + 留痕** | ❌ 缺（现在只有流水账式的「历史」） |

> 一句话：**方案是"算出来的"，模板是"填进去的"，台账是"按月攒起来的"**。
> 三者都要挂在**主体**上才有意义 —— 所以主体（E1）是效率层的地基。

#### 3.10.2 E1 · 主体管理（Entity）—— 一切效率的地基

**概念**：主体 = 一个纳税实体（公司 / 个体户 / 个人）。模板、台账、批量任务**全部挂在主体下**。

- 字段：名称 · 类型（企业/个体户/个人）· 纳税人类型（小规模/一般纳税人）· 征收方式（查账/核定）· 城市（决定社保基数）· 默认社保公积金比例
- **向后兼容**：个人用户**不强制建主体**。「无主体」模式下历史/方案仍按现在的方式存 —— 游客和 A 类用户**完全不受影响**。
- UI：顶栏右侧「当前主体：XX 公司 ▾」（§3.3.1 区块 ②），仅在已建主体时显示。
- **这是 D（代账）的命门**，也顺带服务 B（一人管多家公司）和 C。

#### 3.10.3 E2 · 参数模板（Template）—— 解决「每次重填 20 个字段」

- 模板 = 某个工具的**一套已填参数**，可挂主体也可全局。
- 三个动作：**「从模板填充」**（进工具时一键带出）· **「存为模板」**（结果页行动条）· **「复制上月」**（台账内）。
- 与 §3.9 的字段分级联动：模板存的是**全部字段**（含 advanced），填充时按当前视图过滤显示 —— 简明视图下模板的高级参数照样参与计算。
- **权益刻度**：免费 2 个模板 · Pro 无限。

#### 3.10.4 E3 · 月度台账（Ledger）—— 把「历史」升级成「工作台」

现有「历史记录」是流水账，升级为**按 主体 × 场景 × 期间 归档的表格**：

```
期间      场景        应纳税额    状态          操作
2026-03   增值税       ¥4,320    已导出        [查看][复制上月]
2026-03   工资个税     ¥12,340   已算          [查看][导出][批量]
2026-02   增值税       ¥3,980    已申报        [查看]
```

- 核心操作：**「复制上月」** → 一键带出上月参数，只改变动项（B/E 每月都在做的事）。
- **状态字段**（草稿 / 已算 / 已导出 / 已申报，用户手动标记）—— 状态本身就是**留存钩子**：未申报的条目会在首页待办卡出现。
- 与 §3.8 留存机制 ①（申报倒计时）打通：台账里"未申报"的条目 × 税务日历 → 自动生成待办。

#### 3.10.5 E4 · 批量计算（Batch）—— 工程量最大，最后做

**场景 1（最高频）：工资表批量算个税**
- 粘贴/导入名单（姓名 · 税前工资 · 专项附加扣除 …）→ 自动识别列 → 预览 → 一次算 N 人 → 导出表。
- 输出：每人一行（应发 / 社保 / 专项扣除 / 应纳税额 / 实发）+ 合计行。
- ⚠️ **合规卖点**：批量场景下"数据不出浏览器"这条**依然成立且更有说服力**（整份工资表都不上传）。这句话要写在批量页顶部。

**场景 2：多主体同场景**（D 代账：20 家公司各算一遍增值税）—— 依赖 E1。

- 权益刻度：免费 **5 行/次** · Pro 无限。这是**最强的付费钩子**（比"方案数"更能打动财务）。
- **依赖**：E1（主体）+ E2（模板，批量时用模板作为每行默认值）+ E4 前先有 E3 承载结果。

#### 3.10.6 E5 · 快捷提效（低成本、高感知，可穿插先行）

| # | 能力 | 说明 | 成本 |
|---|---|---|---|
| 1 | **复制上月** | 见 E3 | 低 |
| 2 | **参数记忆** | 同一工具记住上次输入，进来自动带出（不建模板也生效） | 极低 |
| 3 | **键盘优先** | Enter 下一步 · Tab 顺序正确 · 数字键盘（财务打字快） | 低 |
| 4 | **结果一键复制** | 复制明文数额 / **复制为表格**（直接粘进 Excel） | 极低 |
| 5 | **批量导出** | 勾选多条历史 → 一次导出一个 Excel/PDF | 中 |
| 6 | **URL 携带参数** | 把填好的参数生成链接 → 发同事 / 存书签（**零后端成本 + 天然传播**） | 低 |
| 7 | **常用置顶** | 工具页「我的常用」可手动固定 | 极低 |
| 8 | **对比上次** | 结果页常驻「与上次差 ¥X」（现在有方案对比，但没和台账打通） | 低 |

> E5 是**性价比最高的一组**：单条成本都在 1 天内，但对 B/D/E 的日常体感提升最大。建议先做 1/2/4/6/7。

#### 3.10.7 与现有能力的映射（避免重复造轮子）

| 现有 | 演进 | 说明 |
|---|---|---|
| 历史记录 | → **台账**（E3） | 扩展，不重写；无主体时退回现有行为 |
| 方案 scenario | **保留** | 继续承担"对比"，不并入台账 |
| 云同步 | 扩展到主体/模板/台账 | 同步通道已有，扩字段 |
| 导出 PDF/Word | + **分角色模板**（给员工 / 给客户 / 给老板，§2.5.10 第 12 条） | 同一份结果，三种包装 |
| 税务档案 | 升级为**主体档案**（E1 的超集） | 个人档案是主体的特例 |
| 税务日历 | × 台账状态 → 待办 | 打通 §3.8 ① |

#### 3.10.8 依赖顺序与优先级

```
E1 主体 ──→ E2 模板 ──→ E3 台账 ──→ E5 快捷 ──→ E4 批量
 (地基)      (复用)      (追踪)     (穿插先行)    (工程量最大，最后)
```

- **E4 必须最后**：它依赖 E1 挂主体、E2 提供默认参数、E3 承接结果。
- **E5 可随时穿插**：不依赖任何一项，成本极低，建议与 19-x 各阶段并行铺。

#### 3.10.9 权益刻度（效率层是天然的付费墙，比现在更硬）

| 能力 | 免费 | Pro |
|---|---|---|
| 主体数 | 1 | 无限 |
| 参数模板 | 2 | 无限 |
| 台账归档 | 近 3 个月 | 无限 |
| **批量行数** | **5 行/次** | **无限** |
| 批量导出 | ❌ | ✅ |
| 分角色导出模板 | 1 种 | 3 种 |

> 现有 Pro 权益靠"方案数 + 云同步 + 精装报告"驱动，对财务不够硬。
> **主体数 / 批量行数**是财务真实工作流里的刻度，转化率预期显著高于方案数。

#### 3.10.10 实现机制（复用现有存储与同步通道，不新增体系）

```
新增
  src/js/data/entity-store.js        主体 CRUD + 当前主体（E1）
  src/js/data/template-store.js      模板存取（E2）
  src/js/data/ledger-store.js        台账（E3，基于 history 扩展，不重写）
  src/js/ui/entity-switcher-ui.js    顶栏主体切换器
  src/js/ui/batch-ui.js              批量粘贴 → 预览 → 计算 → 导出（E4）

复用
  存储：沿用 scenario/history 的 localStorage 范式 + 既有云同步通道
  计算：批量 N 行 = 循环调用 tax-calculator.js（**绝不另写批量引擎**）
  导出：复用现有 PDF/Word 导出 + 新增分角色模板
```

**五条守护测试（必加）**：

1. **无主体兼容**：未建主体时，历史/方案/导出行为与改动前**完全一致**（保护 A 类用户与游客）。
2. **模板对拍**：用模板填充后算出的结果 = 手工填同样参数算出的结果（逐项相等）。
3. **批量对拍（最关键）**：批量 N 行中每一行的结果 = 该行单独计算的结果（防两套计算口径）。
4. **复制上月正确性**：复制后仅改动项变化，其余字段与上月一致。
5. **导出一致性**：导出文件里的数字 = 页面显示的数字。

### 阶段 19-10 · 效率层 · 台账（E3）✅ 已交付（v1.93.0）
- `ledger-store.js`：按 主体 × 场景 × 期间 归档（**基于现有 history 扩展，不重写**）。
- 「复制上月」+ 状态标记（草稿 / 已算 / 已导出 / 已申报）。

- **验收**：守护测试 4 全绿；历史数据平滑迁移（老用户不丢记录）。

**交付结果（v1.93.0）**
- 新增 `src/js/data/ledger-store.js`；界面沿用 19-9 的 `entity-ui.js`（工作台组第三张卡「我的台账」→ 台账弹窗）。
- **"基于现有 history 扩展，不重写"落在代码上是这么一层**：历史是本体，台账是它之上的索引，
  索引只存历史自身查不出来的三样东西 —— 期间（默认从 `date` 推，**只有用户显式改过**才写覆盖值）/
  主体（`attach` 默认取当前主体）/ 状态（已算 / 已导出 / 已申报）。这么分工的收益碰上线才知道：
  索引读坏了期间能从 `date` 重建、主体与状态丢了只是少一层标注 —— **历史一条不少、一个数都没改**。
  也正因为如此，本版**没有一次性迁移脚本**（那种脚本没有回归网跑它，半年后没人敢删也没人敢信）：
  索引吃亏就自动重建，老记录照样出现在对应的月份里。
- 新的归档点只有两处（速算器 `saveToHistory` + `tax-calculator.js` 的 `saveToHistory`）：**保存即入账**。
  这是**有意偏离本计划原文**的一处 —— 原话是"结果页行动条改为「存为模板 · 加入台账」"，
  但 v1.92.0 刚把行动条上那颗只负责回工具页的第四颗按钮撤掉，再加回来就是自打脸。
  归档该跟着保存发生；改期间 / 状态 / 归属去台账弹窗改。
  `data-management.deleteHistoryRecord` 同时连线：**历史删了台账那行跟着走**（否则就是一排幽灵行）。
- 界面：按月分组的行 + 每行的期间 / 状态就地改；**只有真有上一期账的行才出现「复制上月」**
  （给没有的行摆一颗点了没反应的按钮，是拿 UI 骗人）。
- 权益只影响**看几个月**（免费近 3 个月 / 专业版不限），更老的一条都不删 ——
  门槛设在视野上而不是数据上：删掉的数据用户没法自己变回来。
- **验收**：`tests/ledger.test.js` 14 条全绿（索引里不存任何测算内容 / 历史删了行跟着消失 /
  索引读坏了历史一条不少 / 存储不可用不能把保存搞挂 / attach 不覆盖期间 / 跨年月轴不错位 /
  默认挂当前主体、没主体也照样归档 / 删主体不删台账 / 免费看近 3 个月但一条不删 /
  复制上月取同工具同主体上一期最新那条且不串主体 / 换账号看不到别人的台账 / 分组「未按期」垫底）。
- **未做（留后续）**：**首页「台账待办」小卡**（plan 原文"台账未申报项 × 税务日历 → 首页待办卡"那一环）——
  它得先答清"什么算待办"（`status` 本来是用户自己标的），现在做等于替用户判定，会把记账变成瞎催；
  往**申报台**再走一步（申报表 / 回执 / 对接税局）同样是另一个产品，`status` 只是给自己看的进度。

### 阶段 19-11 · 效率层 · 批量（E4，工程量最大，必须最后）✅ 已交付（v1.94.0）
- `batch-ui.js`：粘贴名单 → 自动识别列 → 预览 → 批量计算 → 导出表（先做**工资表批量算个税**，再做多主体同场景）。

- 权益：免费 5 行/次 · Pro 无限。
- **验收**：**守护测试 3（批量 N 行 = 单行逐个算，逐项相等）必须全绿** —— 这是防两套口径的最后一道闸。

**交付结果（v1.94.0）**
- 新增 `src/js/ui/batch-ui.js`；页面 `profile-batch-page` 由个人中心「工作台」组第四张卡进入（**不动主 Tab**）。
- **"防两套口径"在代码里就是一句话**：每一行都走 `tool.compute(values)`，与速算器逐个手填同一个入口。
  守护测试 3 对**每一个**速算器做对拍（不是挑两个代表）：批量第 i 行的主结果与每一条明细的
  label / value / kind 三项，都等于把同一份参数单独喂给 `compute` 的结果。
- **只做速算器**（注册表里非 deep 的 20 个）：完整测算（deep）是分步向导、字段之间有依赖
  （前一步选了什么，后一步才有哪一列），按列喂进去会缺字段 —— 那不是"批量算不准"，
  是把"填到哪一步了"这个语境整个丢了。多主体同场景（plan 第二小步）仍**未做**。
- **列识别有退路也有说法**：表头带单位 / 空格 / 括号都认（"税前月薪（元）"）；一个字都认不出
  才退到"按字段顺序对号入座"，并在界面上明说 —— 认错了不会有任何提示，这是最危险的一档。
  未识别的列（姓名 / 工号）**原样带出**：对不上人的表没法用。
- **脏数据分两种**：这一格空着 = 这项没有（0，照算）；写了却读不懂（"面议"、手滑多打一个字）
  = 标出来，不算成 0（算成 0 就成了"这个人不用交税"，一份表里有这么一行没人会回头查）。
- **权益在整批上**：免费 5 行/次，超了**一行都不算**（不是截前 5 行）—— 半份工资表看起来
  跟完整的一份一模一样，发出去就是事故。升级入口仍只有顶栏与个人中心两处，不新造第三处。
- **数据不出本机**写在页面顶部（`.batch-note`）而不是脚注：HR 交的是全员工资，她先要知道的是安不安全。
  批量结果不写计算历史 —— 200 行灌进历史，历史就不再是"我算过什么"；要留痕就导出那张表。
- **验收**：`tests/batch.test.js` 20 条全绿（守护 3 全工具对拍 / 列识别四种形态 / select 写标签或值 /
  ¥ 千分位全角负号百分号 / 空=0 与写错=标出来 / 缺列用 spec 默认值不归零 / 免费 6 行一行不算 /
  专业版不限 / 姓名列原样带出 / TSV 裸数字且列数对齐 / 坏行留空不填 0 / 引号包裹的 "12,000" 不切错列 /
  界面接线下拉·预览·计算·导出条显隐）。
- **真机已补验**（agent-browser 挂死当晚改走 playwright-cli）：本地会话 + mock `/api/auth/profile` 让
  `loadProfile` 走通 → 13 张卡渲染 → 点工作台第四张卡进批量页 → 粘贴脏表（¥ / 千分位 / "面议"）→ 计算 →
  结果表正确（王五结果列 "—" 留空而非 0，李四 `¥9,000` 正确解析）→ 返回；浅/深排版逐屏目测正常，
  导出与复制按钮无报错。**截图基线不用重拍**：profile 基线是"无后端"形态（无后端时卡片 grid
  本来就不渲染，19-1 以来的口径），新卡片不改变基线画面。

## 5. 风险与约束清单

| 风险 | 说明 | 对策 |
|---|---|---|
| 无视觉回归 | 改样式看不出坏 | 19-0 先建截图基线 |
| Tailwind 构建产物 | 改类名忘 `build:css` → 线上静默降级 | 每个阶段结束必跑并提交 `src/css/tailwind.css` |
| 结果页改动牵动留资/分享取数 | `#dw-result-primary` / `data-dw-row` / `data-tool-id` 是三个锚点 | 19-4 期间**冻结这三个属性名**，加测试钉住 |
| `index.html` 171KB 单文件 | 改动冲突多 | 按区块精确替换，不重写整文件 |
| 首页膨胀 | 已有 9 区块，容易再加 | 规范写死"首屏 ≤3 区块" |
| 谈薪场景硬约束 | 不得出服务引导 | `BLOCKED_TYPES` 保持，19-4 后回归验证 |
| 升级入口收敛 | 只允许 2 处 | 19-6 后核对 |
| 深色模式 | 每加一个表面色都要给深色值 | 令牌新增必须成对 |
| 双视图退化成两个产品 | 分级后两种视图算法/默认值分叉 | 三条对拍守护测试钉住；分级**只动 UI 不动 compute** |

## 6. 不做的事（避免过度设计）

- ❌ 不换主色系（收益低、风险高）
- ❌ 不引入前端框架（现有原生 + Tailwind 产物体系稳定，重构成本 >> 收益）
- ❌ 不做首页信息流/社区（与"工具+顾问"定位无关）
- ❌ 不做强制注册墙（免登录是核心优势，北极星分母是 calc_done）
- ❌ 不做弹窗式营销（改内联情境卡）
- ❌ 不动结果页八段模板顺序
