## §0 一页纸：三个纯数据文件

| 文件 | 内容 | 规模 | 依赖 |
|---|---|---|---|
| `src/js/data/tax-taxonomy.js` | **税种字典**：5 税类 / 18 税种 / 4 项费 / 2 项机制 | ~180 行 | 无 |
| `src/js/data/person-taxonomy.js` | **个人字典**：3 组 / 9 格所得形态 / 职业别名 / 24 事件 | ~150 行 | 无 |
| `src/js/data/tool-taxonomy.js` | **挂载点表**：41 个入口 → 挂在哪（主挂 + 次挂） | ~60 行 | 读 `tool-registry.js` |

三条依赖方向（不许反向）：

```
tax-taxonomy   （税种是什么）     ← B 企业侧的分类真源
person-taxonomy（自己的钱属哪格） ← A 我自己侧的分类真源
tool-registry  （工具有哪些、怎么算）  ← 现状，本轮不改结构
tool-taxonomy  （工具挂在哪）      ← 唯一同时引用上面三者的文件
```

**为什么挂载点要独立成文件**：`tool-registry.js` 已 6500+ 行且承担渲染与计算适配，再塞分类信息会让它变成第二个分类真源。独立出来后，注册表**零改动**，分类可独立演进与校验。

## §1 现状衔接点（本轮不改的东西）

`tool-registry.js` 现有条目字段（以 `salary-tax` 为例）：

```js
{ id: 'salary-tax', name: '月薪个税', subtitle: '…',
  group: 'salary', icon: 'fa-money', status: 'native', seoPath: '…', hot: true,
  policyKey: 'comprehensive', nextTools: ['bonus-tax', 'annual-settlement', 'social-base'],
  fields: [...], pitfalls: [...], compute: function (v) {…} }
```

| 现有字段 | 本轮处置 |
|---|---|
| `id` | 保留，是挂载点表的外键 |
| `group`（现有 5 组） | **保留但降级**为「渲染次序提示」，不再是分类真源（分类改由 `tool-taxonomy` 给出） |
| `status` / `compute` / `fields` / `pitfalls` | **完全不动** |
| `policyKey` | 不动（政策时效判定仍由 `tax-registry.statusOf` 负责） |
| `nextTools` | 不动（仍指向工具 id，与分类无关） |
| `hot` | 不动（人工维护的高发名单） |

> 一句话：**本轮只加三个新文件，注册表一行不改。** 这是风险可控的原因。

引入位置：`index.html` 在 `src/js/data/tool-registry.js`（第 2195 行）**之后**追加三行，因为挂载点表的断言需要读注册表。

## §2 `tax-taxonomy.js` 规格

### 2.1 四类对象（务必分清，这是统计口径的前提）

| 对象 | 数量 | `kind` | 说明 |
|---|---|---|---|
| **税种** | **18** | `'tax'` | 中国现行法定税种，封闭集合 |
| **费** | 4 | `'fee'` | 社保公积金、残保金、工会经费、文化事业建设费 —— 不是税但必办 |
| **机制** | 2 | `'mechanism'` | 出口退税、研发费加计扣除 —— **不是税种**，是计算机制/政策 |
| 税类 | 5 | — | 按征税对象的一级分组 |

> ⚠️ **一处口径修正**：此前文档把“出口退税”算进 18 税种里，导致流转税组数到 5。出口退税与研究费加计扣除都不是税种，应标 `kind: 'mechanism'` 单独统计。修正后 18 税种严格等于法定税种数。

### 2.2 `CATEGORIES`（5 个税类）

### 2.3 `TAXES`（18 税种 + 4 费 + 2 机制）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | ✅ | 英文短码，**全表唯一**，工具与事件通过它引用 |
| `name` | string | ✅ | 法定名称 |
| `kind` | enum | ✅ | `tax` / `fee` / `mechanism` |
| `category` | string | ✅（mechanism 可空） | 指向 `CATEGORIES.id` |
| `frequency` | enum | ✅ | `month` / `quarter` / `year` / `onetime` / `withVat`（随增值税） |
| `scope` | enum | ✅ | `all`（普适）/ `conditional`（有条件）/ `industry`（特定行业） |
| `entities` | string[] | ✅ | `company` / `individual` / `person` |
| `law` | string | ✅ | 现行法律依据名称（**不存条文内容**，只存名称与生效日） |
| `effectiveFrom` | string | ✅ | 生效日 `YYYY-MM-DD` |
| `hasTool` | boolean | 派生 | **不存**，由 `tool-taxonomy` 反查（避免两处维护） |
| `note` | string | — | 口径提示 |

### 2.5 完整性约束

1. `id` 全表唯一，且**只能**取自上表（新增税种需先改本规格文档）
2. `kind='tax'` 恰好 **18** 条，`kind='fee'` 恰好 4 条
3. `category` 非空的必须存在于 `CATEGORIES`；`kind='mechanism'` 的 `category` 必须为 `null`
4. `frequency='withVat'` 只允许 `city-tax`（附加税费随增值税，是这个枚举存在的唯一理由）
5. **禁止在 `TAXES` 里存税率、公式、起征点** —— 那些在 `*-quick.js` 与 `tax-rates` 里，这里只存"是谁、归哪类、多久报一次、依据哪部法"
6. `hasTool` 不落库，由 `tool-taxonomy` 反查

### 3.1 `INCOME_GROUPS`（3 组）


### 3.2 `INCOME_FORMS`（9 格，分类骨架）

| 字段 | 类型 | 说明 |
|---|---|---|

| `rateBasis` | enum | `annual-progressive` / `five-level` / `flat-20` / `exempt` |

| id | 名称 | group | withheldBy | 汇算 | rateBasis | 判定问句 |
|---|---|---|---|---|---|---|
| F1 | 工资薪金 | comprehensive | employer | ✅ | annual-progressive | 单位按月发给你、还给你交社保？ |
| F2 | 劳务报酬 | comprehensive | payer | ✅ | annual-progressive | 给别人干活，按次 / 按项目结算，没人给你交社保？ |
| F3 | 稿酬 | comprehensive | payer | ✅ | annual-progressive | 写稿、出书、开专栏？ |
| F4 | 特许权使用费 | comprehensive | payer | ✅ | annual-progressive | 把版权 / 专利 / 肖像给别人用？ |
| F5 | 经营所得 | business | self | ❌ | five-level | 自己有摊 / 店 / 工作室 / 合伙份额，自负盈亏？ |
| F6 | 利息、股息、红利 | schedular | payer | ❌ | flat-20 | 钱生钱（分红、利息、理财）？ |
| F7 | 财产租赁 | schedular | self | ❌ | flat-20 | 把房 / 车 / 东西租出去了？ |

### 3.4 `EVENTS`（24 个事件，用户语言的真正入口）

1. `INCOME_FORMS` 恰好 9 条，`group` 只有三个值

7. **禁止**在个人字典里出现职业之外的分类维度（如「性别」「年龄段」）—— 它们不改变算法

## §4 `tool-taxonomy.js` 规格（挂载点）

```js
MOUNTS = [
    // id            主挂载点（唯一）                     次挂载点（可多个，不计数）
    { id: 'salary-tax',  branch: 'A', primary: 'F1/E1',  secondary: ['B/C2'],           taxCode: 'iit' },
    { id: 'vat',         branch: 'B', primary: 'B/C1',   secondary: ['A/F5'],           taxCode: 'vat' },
    { id: 'surtax-stamp',branch: 'B', primary: 'B/C1',   secondary: ['B/C3', 'A/F5'],   taxCode: 'city-tax',
      mixed: '附加税费与印花税混装，待拆' },
    ... 共 41 条
];
```

| 字段 | 说明 |
|---|---|
| `id` | 外键 → `tool-registry.id` |
| `branch` | `A` / `B`，**主挂载点**所在分支（决定计数归属） |
| `primary` | 主挂载点路径，形如 `F1/E1`（A 侧）或 `B/C1`（B 侧） |
| `secondary` | 次挂载点数组，**不重复计数** |
| `taxCode` | 指向税种字典；混装工具填**主税种**，次税种写进 `mixed` |
| `mixed` | 可选，混装说明（§3 的 4 个「建议拆」+ `classification` 的补齐说明） |

### 4.1 5 个已知混装/待处理工具的记法

| 工具 | `primary` | `mixed` |
|---|---|---|
| `surtax-stamp` (+deep) | `B/C1`（附加税费） | 印花税归 `B/C3` → **建议拆** |
| `disability-fund` (+deep) | `B/C5`（残保金） | 工会经费同体 → **建议拆** |
| `classification` | `A/F6`+`A/F9`（分类所得） | 兼 F3 / F4 → **不是拆，是补入口**（内核保留一个） |
| `property-transfer` | `A/F8`（财产转让个税） | 增值税 / 契税 / 附加靠手填 → **写组合器，不重算** |
| `employer-cost` | `B/C5`（用工成本测算） | **不是税种，是成本** → 标注 `'not-a-tax'` |

### 4.2 完整性约束（最有价值的一组断言）

1. `MOUNTS` 恰好 **41** 条，与 `tool-registry.all() + deep()` 双向一致（无孤儿、无幽灵）
2. 每条恰有一个非空 `primary`；**同一路径可以挂多个工具** —— 速算与完整测算算**同一入口**但各占一条（`salary-tax` / `net-salary` / `reverse` 都在 `F1/E1`）；「A 30 / B 11」按**工具数**计
3. `branch='A'` 恰好 **30** 条、`branch='B'` 恰好 **11** 条 → 相加 41（与总表 §0.2 验算一致）
4. `primary` 路径分五种形态，每一端都必须真实存在：`F*/E*`（格 + 事件，且事件属于该格）、纯 `F*`（classification 补入口）、`L1/*`（身份层：expat / non-resident，见总表 §1.1）、`cross/E*`（必须是 `form='cross'` 的事件）、`B/C*`（C1–C5 是总表 §2.1 编号，映射到 `CATEGORIES.id`）
5. `taxCode` 非空时必须存在于 `tax-taxonomy`；唯一允许为空的是 `employer-cost`（`mixed` 标注 `not-a-tax`）
6. 任一工具出现在两条分支时，只能有一个 `primary`，另一个进 `secondary`
