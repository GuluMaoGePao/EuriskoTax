## §0 一页纸：三条互不相同、且不能合并的轴

| 轴 | 回答的问题 | 值 | 由谁决定 | 存在哪 | 进不进算式 |
|---|---|---|---|---|---|
| **用户立场** | 谁在算 / 替谁算 | 我自己 / 企业 | 用户首访弹窗 | `euriskoPrefIdentity` | ❌ 只决定推荐排序 |
| **纳税主体** | 这笔税算在谁头上 | 个人（自然人）/ 个体工商户 / 企业 | 工商登记事实 | `euriskoEntities` | ✅ 决定减免适用 |
| **工具属性** | 这是什么税 | 5 组税种 | 工具本身 | `GROUPS`（注册表） | — |

**结论：三条轴正交，任何两条都不能合并。** 上一版把「用户立场」独立出来（刻意不叫 `person` / `company`，那两个字符串已被纳税主体占用），就是因为这两条轴一旦合并，只有导航职责的东西会混进算式。

## §1 三条轴的定义

### 1.1 用户立场（v2.0.0 引入）

| 立场 | 定义（`tool-registry.js:6413-6415`） |
|---|---|
| `self` 我自己 | 给自己算 —— 工资、劳务、经营所得、自己持有的股权 |
| `enterprise` 企业 | 替公司或客户算 —— 企税、增值税、发票、用工成本 |

- **唯一功能**：决定工具页默认推荐哪一组
- **不参与任何算式**
- ⚠️ **立场不按所有权判**：老板算自己公司的企业所得税 → 立场是「企业」；同一个人算从这家公司拿的分红 → 立场是「我自己」。同一人、同一公司、两笔税，落两个立场。

### 1.2 纳税主体

`entity-store.js:38-42` 的三值：

| 值 | 标签 | 民法典位置 |
|---|---|---|
| `person` | 个人 | **自然人** |
| `individual` | 个体工商户 | 民法典第二章第四节（**归在自然人章节下**，不是非法人组织） |
| `company` | 企业 | **法人**（有限责任公司等） |

主体档案共五字段：名称 / 类型 / 纳税人类型（小规模 · 一般）/ 征收方式（查账 · 核定）/ 城市。**这五项都参与算式。**

**已知缺口**：合伙企业的合伙人、个人独资企业的投资人（民法典「**非法人组织**」）与农村承包经营户，三值体系里没有位置，现在被硬塞进 `individual`。

### 1.3 工具属性（现有 5 组，覆盖全部 43 个入口）

> ⚠️ 本节是**现状测绘**。这 5 组将被 §4 的分类体系整体替换 —— 它们混了四种维度（场景 / 政策 / 主体 / 频次）。保留此节是为了记录「改造前长什么样」。

| 分组 | 速算 | 完整测算 | 合计 |
|---|---|---|---|
| 工资与到手 | 5 | 6 | 11 |
| 一次性收入与特殊所得 | 5 | 8 | 13 |
| 税优与养老 | 3 | 1 | 4 |
| 社保与用工 | 3 | 2 | 5 |
| 企业与经营 | 4 | 4 | 8 |

## §2 「我自己」不等于自然人（43 个入口逐一标注）

**标注口径**：按「这笔税的法定纳税主体」给 43 个入口分类。这是为量化做的**人工标注**，不是产品里已有的字段，可复核。

| 纳税主体 | 入口数 |
|---|---|
| 自然人 | 28 |
| 经营者（个体户 / 小微，为单位缴的税） | 8 |
| 单位（法人） | 3 |
| 单位 + 人（社保公积金两边各缴一半） | 2 |

### 2.1 错位 A：「我自己」17 个里，只有 12 个是自然人内容

| 「我自己」的工具按纳税主体拆 | 数量 | 清单 |
|---|---|---|
| 自然人 | 12 | 月薪个税 / 税后倒算 / 年终奖 / 专项附加 / 汇算 / 劳务报酬 / 股权激励 / 离职补偿 / 提前退休 / 外籍 / 个人养老金 / 企业年金 |
| **经营者** | 4 | 个体户经营所得 / 增值税 / 附加印花 / 残保金 |
| **单位 + 人** | 1 | 社保公积金 |

来源很集中：**「个体户 / 小店」（`owner`）这张卡的 5 个工具里，一个纯自然人税目都没有**；「自由职业」卡里也混了 `business-income`。

> 这也是阶段21 得出「5 组不能按身份二分」的结构性原因：`社保与用工` / `企业与经营` 两组会被自己侧大量点到。

### 2.2 错位 B：自然人内容 28 个入口，只有 12 个被身份覆盖，漏了 16 个

```
health-insurance, forward, classification, donation, reverse, property-transfer, non-resident,
withholding-deep, bonus-tax-deep, equity-deep, severance-deep, early-retirement-deep,
expat-deep, annual-settlement-deep, special-deduction-deep, private-pension-deep
```

规律：全是**完整测算** + 1 个税优健康险。根因是 `SCENARIOS[].tools` 当年只填了速算工具。

具体后果：上班族选了「我自己 · 上班族」，**年终奖个税速算**有身份加成，同一个工具的**年终奖择优（完整版）**一点加成都没有。

### 2.3 四个打破直觉的例子

| 立场 | 纳税主体 | 场景 |
|---|---|---|
| 我自己 | 自然人 | 上班族算自己工资个税 ← 符合直觉 |
| **我自己** | **个体工商户 / 单位** | 老板算自己小店的增值税、附加印花、残保金 |
| **企业** | **自然人** | HR 代员工算工资个税（**扣缴义务人替纳税人算账**） |
| 企业 | 企业（法人） | 财务算企业所得税 ← 符合直觉 |

**四个格子都非空 → 这两条轴无法压缩成一条。**

## §3 要不要让「我自己」用户再选一次「自然人 / 个体工商户」？

**建议：不要。** 三条理由 + 一个更好的替代。

### 理由一：二级场景卡已经隐含了这层信息

| 二级卡 | 典型行为 | 默认纳税主体 |
|---|---|---|
| 上班族 | 领工资、算年终奖、看汇算退税 | 自然人 |
| 高管 / 股东 / 临近退休 | 股权激励、离职补偿、退休与年金 | 自然人 |
| 自由职业 / 兼职 | 劳务报酬预扣、自己缴社保 | 自然人（也可能是个体工商户） |
| 个体户 / 小店 | 经营所得、开票缴税、核定还是查账 | **个体工商户** |

选了「个体户 / 小店」，答案已经是个体工商户了。再问一遍是重复信息。

### 理由二：加一层选择要付三种代价

多一次点击 + 一个返回态 + 一个「第 2 步点了算不算数」的歧义。这与阶段21 论证过并否决的「两步弹窗」是**同一个取舍**——当时结论是：6 张卡本就一屏放得下，两步换来的收益抵不上的状态机的成本。

### 理由三：需要精确到主体的地方，已有更精确的载体

能不能享六税两费减半、核定还是查账、小规模还是一般纳税人——这些判定依赖 `entity-store` 的**五字段档案**，比「自然人 / 个体工商户」二选一精确得多，而且**已经存在**。用一道二选一去覆盖它，是把高精度的东西降级。

### 替代方案（数据层补齐，零 UI 成本）

把「二级卡 → 纳税主体的**默认倾向**」写进注册表：

```js
// 二级卡的默认纳税主体（v2.1.0）。注意：这是**倾向值**，不是事实——
// 最终以用户在 entity-store 建的主体档案为准，用户建档后可覆盖。
SCENARIO_ENTITY_KINDS = {
    employee:  'person',      // 自然人
    executive: 'person',      // 自然人
    freelance: 'person',      // 自然人为主（也可能是 individual）
    owner:     'individual',  // 个体工商户
    finance:   'company',
    hr:        'company'
};
```

好处：不改 UI、不加点击；将来做「按主体推荐」或「为什么我不能享这个减免」时有数据支撑。

## §4 分类体系（v2：先分类，后对应）

> **本节替换掉本文件初稿的「C4 组内三段」方案**（原因见 4.0）。
> 顺序是：先按税法定分类（4.1 / 4.3），再谈工具怎么挂（4.5 / 4.6）。**允许现有 43 个入口被删改**。

### 4.0 为什么推翻初稿

初稿是在「现有 43 个入口 + 现有 5 组」之上加一层视角切换。两轮讨论后判定不够：

1. **现有 5 组维度不统一**：「工资与到手」是场景、「税优与养老」是政策、「企业与经营」是主体、「一次性收入」是频次 —— 一个目录混了四种维度，所以两侧都不好用
2. **现有入口可能是错的**：`surtax-stamp` 把印花税和附加税费揉成一个工具、`classification` 是兜底格、`health-insurance` 没有归属。在错的集合上分类，只能把错误整理得更整齐
3. **54% 的身份盲区**（§2.2）根因不是「没标」，而是**没有一套分类体系可以标**

所以改为自顶向下：**先建分类，再把工具挂上去。**

---

### 4.1 企业侧：按征税对象五分类（专业口径）

两类用户的认知起点不同，决定了分类方式不同：

| | 知道自己要算什么税吗 | 他要什么 |
|---|---|---|
| **企业侧** | ✅ 知道（财务 / 代账 / 老板） | 按**专业税种**快速定位 |
| **自己侧** | ❌ 不知道 | 只知道「我是谁、我遇到了什么事」→ **要被引导** |

现行 **18 个税种**按征税对象分为五类，企业会碰到的是下面这些（`scope`：普适 / 条件 / 特定行业）：

| 一级（税类） | 二级（税种） | 适用面 | 申报节奏 | 现有工具 |
|---|---|---|---|---|
| **① 流转税** | 增值税 | 普适 | 月 / 季 | ✅ `vat` · `vat-deep` |
| | 城建税 + 教育费附加 + 地方教育附加 | 普适（随增值税） | 月 / 季 | ⚠️ 混在 `surtax-stamp` |
| | 消费税 | 特定行业（15 税目） | 月 / 季 | ❌ 只作为附加税的计税依据被输入 |
| | 关税 / 出口退税 | 进出口 | 按次 | ❌ |
| **② 所得税** | 企业所得税 | 普适 | 季预缴 + 年汇算 | ✅ `corporate-income-tax` · `-deep` |
| | 个人所得税（**代扣代缴**） | 有雇员即普适 | 月 | ✅ 多个个税工具（但缺「代扣申报汇总」） |
| **③ 财产与行为税** | 印花税 | 普适 | 季 / 按次 | ⚠️ 混在 `surtax-stamp` |
| | 房产税 | 有房产 | 年（分期） | ❌ |
| | 城镇土地使用税 | 有土地 | 年（分期） | ❌ |
| | 契税 | 取得不动产时 | 登记前 | ❌ |
| | 车船税 | 有车船 | 年（保险代收） | ❌ |
| | 车辆购置税 | 购车时 | 60 日内 | ❌ |
| **④ 特定目的与资源环境税** | 土地增值税 | 转让不动产 | 项目预征 + 清算 | ❌ |
| | 耕地占用税 | 占用耕地 | 30 日内 | ❌ |
| | 资源税 | 采矿 / 取水 | 月 / 季 | ❌ |
| | 环境保护税 | 直接排污 | 季 | ❌ |
| | 烟叶税 / 船舶吨税 | 极窄 | — | ❌ |
| **⑤ 费与用工** | 社保 + 公积金 | 普适 | 月 | ✅ `social-base` · `-deep` |
| | 残疾人就业保障金 | 普适 | 年 | ✅ `disability-fund` · `-deep` |
| | 工会经费 | 普适 | 月 / 季 | ⚠️ 与残保金合并在一个工具里 |
| | 文化事业建设费 | 广告 / 娱乐业 | 月 / 季 | ❌ |

**覆盖率一眼可见：18 个税种里只有 4 个（增值税、企业所得税、个税代扣、社保/残保金）有真正的计算器**，另有两个是「混装」（`surtax-stamp` 同时算附加税与印花税）。

### 4.2 三处必须偏离学术分类

| # | 偏离 | 理由 |
|---|---|---|
| 1 | **附加税费不单独成类，挂在增值税旁边** | 税法上城建税属「特定目的税」，但它永远依附于增值税与消费税。放进第 ④ 组，财务会在「流转税」里找不到它。行业里也叫「增值税及附加」 |
| 2 | **个税代扣双入口** | 它属第 ② 所得税，但由 HR 的用工事务触发 → 第 ② 与第 ⑤ 各放一个入口（一处是正门、一处是跳转），不重复计数 |
| 3 | **第 ④ 组默认折叠** | 资源税 / 环保税 / 烟叶税 / 船舶吨税对 95% 企业是零。展开是为了完整性，不是为了常用 |

### 4.3 我自己侧：三层结构

**先回答一个前置问题：要分「自然人 / 其他主体」吗？——不用，「我自己」恒等于自然人。**

| 身份 | 法律地位 | 所得税落在谁头上 |
|---|---|---|
| 个体工商户 | 民法典归**自然人**章节（第二章第四节），不是独立主体 | 户主（自然人）缴经营所得个税 |
| 个人独资企业 | 非法人组织 | **穿透**到投资人（自然人） |
| 合伙企业 | 非法人组织 | **穿透**到各合伙人（自然人） |

非法人组织**不缴企业所得税**，所得税全部穿透到自然人。所以「我自己」这一侧看到的永远是自然人，真正要分的是三层别的东西：

| 层 | 回答什么 | 值 | 变化频率 | 作用 |
|---|---|---|---|---|
| **L1 税务身份** | 「税法上你归哪套规则」 | 居民个人 / 非居民个人 | 几乎不变 | **只改算法参数**，不改推荐 |
| **L2 职业角色** | 「你在靠什么挣钱」 | 见下表 8 类 | 几年一变 | **决定推荐包** |
| **L3 事件** | 「你这笔钱是怎么来的」 | 20+ | 每次都变 | **真正的工具入口** |

> ⚠️ **本节已被 `阶段22-分类总表-思维导图与工具映射.md` §1.2 替换**（2026-10-28）：
> L2 职业角色 8 类 → **L2 所得形态 9 格 / 3 组**（个税法第二条给定的**封闭集合**），职业降级为 `ROLE_ALIASES` **别名层**（加一行数据＝加一个职业）。
> 原因：职业是**开放集合**（律师 / 医生 / 骑手 / 主播……列不完），且同一职业横跨多套算法（律师＝工资薪金 + 劳务报酬 + 稿酬 + **经营所得**（律所合伙人））。
> **下表保留**作过程记录，实施以总表 §1.2 为准。

**L2 职业角色（8 类）→ 推荐包**（历史版本，已由 9 格所得形态替代）

| 角色 | 典型动线 | 推荐工具（现有） | 缺口 |
|---|---|---|---|
| 上班族（雇员） | 领工资、年终奖、年底汇算 | `salary-tax` `net-salary` `bonus-tax` `special-deduction` `annual-settlement` + 同名 deep | — |
| 自由职业 / 兼职 | 接私活、被预扣、自己缴社保 | `withholding` `annual-settlement` `social-base` `private-pension` | 稿酬 / 特许权无专器 |
| 个体经营者 | 开小店、报增值税、经营所得 | `business-income` `vat` `surtax-stamp` `social-base` `disability-fund` | 核定 vs 查账无引导 |
| 股东 / 高管 / 持股员工 | 股权激励、行权、离职补偿 | `equity` `severance` `early-retirement` `annuity` | 分红、转让股权无专器 |
| 退休与年金领取者 | 领养老金、企业年金 | `annuity` `private-pension` `early-retirement` | 退休再任职无专器 |
| 灵活就业 | 自缴社保、无单位代扣 | `social-base` `private-pension` | 缴费基数选择无引导 |
| 外籍 / 跨境 | 津补贴、税收协定、离境 | `expat` `non-resident` | 协定待遇无专器 |
| 待业 / 学生 / 实习 | 实习报酬、偶然所得 | — | **整块空白** |

**L3 事件（20+，真正的入口）**

```
发了工资 · 发了年终奖 · 年底汇算 · 离职了 · 拿到股权 · 行权 · 卖房 · 买房
租房 · 把房租出去 · 接了私活 · 讲课出书 · 炒股理财 · 存款利息 · 开小店
直播带货 · 中奖了 · 捐款 · 出国 · 领养老金
```

**关键：L3 才是入口。** 用户不知道「财产租赁所得」是什么，但一定知道「我把房子租出去了」。表层是事件，底层是税种 —— 这就是「引导」。

### 4.4 引导逻辑（怎么推荐）

```
L1 税务身份（居民/非居民） ──── 只改参数，不改推荐集合
        │
L2 职业角色 ──── 决定「推荐包」= 该角色常用的工具集合（上表）
        │
L3 事件 ──── 直达单个工具，并把该事件的坑前置（如「卖房满五唯一」）
```

三条规则：

1. **L2 只决定「先给谁」**，不决定「谁能出现」——职业包之外的工具始终可达（全局搜索 / 「看全部」）
2. **L3 优先于 L2**：用户点「卖房了」，不该被他的职业身份拦住
3. **L1 默认居民**，只在结果页给「我是非居民」的切换（99% 的人这一层没有变化，不该进首访流程）

### 4.5 现有 43 个入口的处置原则（不预先决定）

分类定完后重新挂靠，原则：

| 原则 | 说明 |
|---|---|
| 一个工具挂**一个主税种** | 现有 `surtax-stamp` 同时挂「附加税」和「印花税」→ 应拆或标主/次 |
| 兜底格不是分类 | `classification`（分类所得通用格）应挂在具体所得项下，或降级为工具而非入口 |
| 无归属的必须解释 | `health-insurance`（税优健康险）→ 明确挂「个人所得税 · 税优」 |
| **允许删、允许合并、允许新增** | 「43 个入口」不再是硬约束，改成**由分类体系统计得出**的数字 |

明显可疑、需要重做的 5 个：`surtax-stamp`（混装）、`classification`（兜底）、`health-insurance`（无归属）、`employer-cost`（不是税种，是成本测算）、`business-income`（是税目还是经营主体？两者混在一起）。

## §5 核查结论：`property-transfer` 不是「跨税种组合」

`docs/development/阶段19-UI重构与留存设计方案.md:751` 把它登记为：

> **跨税种组合** | 1 | `property-transfer` 卖房要交多少税（增值税 + 个税 + 契税 + 附加，一屏出总额）

**核查结果：这个规划形态从未落地。**

| 证据 | 内容 |
|---|---|
| 字段 | 18 个字段全部是财产转让所得的个税（收入 / 原值 / 凭证 / 自用年限 / 是否唯一 / 换购）；**没有任何**契税、增值税、土增税的输入项 |
| 副标题 | 「满五唯一免在哪、核定 1% 能不能选、换购能退多少」——全是**个税**口径 |
| 内核注释 | `property-transfer-quick.js:31`：「增值税及附加**由调用方传入**（口径在 `surtax-stamp-quick` / `vat-quick`，**不在这里复制一遍**）」 |
| git | `a3c6422`（17D-11/12/13/17E，v1.67.0~v1.70.0）一次性落地 312 行内核 + 320 行测试，**就是单税种** |
| git 后续 | 只有结构改动（v1.142.0 入口统一 / v1.101.0 字段分级 / v1.103.0 政策时效）；`git log --all --grep 跨税种` **无命中** |

**结论两层**：
1. 是**规划未落地**，不是「实现了又被砍」
2. 不做是有意原则而非遗漏 —— 仓库禁止同一条口径在多处复制。将来要补，正确姿势是**写一个组合器去调用现有内核**（`vat-quick` / `surtax-stamp-quick`），而不是在 `property-transfer-quick` 里重算一遍

## §6 顺带发现：个人常见的非个税种，产品一个都不算

扫描 43 个入口的关键词覆盖：

| 个人会遇到的税 | 有没有工具算 |
|---|---|
| 个人所得税 | ✅ 14 个入口 |

| **房产税**（出租住房 4%） | ❌ |
| 城镇土地使用税 | ❌ |
| **车辆购置税**（买车 10%） | ❌ |
| **车船税**（有车按年） | ❌ |

买房的契税、买车的购置税都是典型的**个人大额支出**，搜索意图强、传播性强，目前没有产品承接。
