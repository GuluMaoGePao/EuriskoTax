## §0 完整思维导图（展开到工具级）

**两条分支的设计原则不同，这是整个总表的前提：**

| | A 我自己 | B 企业 |
|---|---|---|
| 用户状态 | 不知道自己要算什么税 | 知道自己要算什么税 |
| 给他什么 | **引导**（身份 → 角色 → 事件） | **目录**（税类 → 税种 → 场景） |
| 一级分类依据 | 人生动线 | 征税对象（税法） |
| 跨分支 | 允许：个体经营者要算增值税，财务也要算自己的个税 | 同左 |

> 关于「我自己」为什么只有自然人：个体工商户归民法典**自然人**章节，个人独资 / 合伙的所得税**穿透**到投资人、合伙人（自然人）。所以 A 分支下不再分主体类型，只分角色与事件。

## §1 A 我自己

### 1.1 L1 税务身份（算法层，不进首访）

| 值 | 判定 | 影响 | 工具 |
|---|---|---|---|
| 居民个人 | 有住所，或无住所而一个纳税年度内在境内居住累计满 183 天 | 综合所得年度汇算 | 默认 |
| 非居民个人 | 不满足上条 | 按月/次分项计税，捐赠扣除率不同 | `non-resident` ✅ |

**规则**：默认居民，只在结果页提供「我是非居民」切换（99% 的用户这一层没有变化）。

### 1.2 L2 所得形态：9 格 / 3 组（分类骨架＝个税法第二条）

> **本节替换了初版的「L2 职业角色 9 类」。** 原因：职业是**开放集合**，每出现一个新业态就要加一张卡（律师 → 医生 → 骑手 → 主播……），而且同一个职业横跨多套算法。改用**所得形态**后，分类变成法律给定的**封闭集合**，职业降级为别名索引。

#### 1.2.0 为什么不用「职业」当分类轴

| | 职业 | 所得形态 |
|---|---|---|
| 数量 | 开放（列不完） | **封闭，9 个，税法给定** |
| 完备性 | 永远会有新职业 | **穷尽**：个人收入不可能落在这 9 格之外 |
| 与算法的对应 | 一对多（一个职业跨多套算法） | **一对一**（每格一套算法） |
| 加一个的代价 | 加一张卡 + 一套推荐逻辑 + 一套测试 | **加一行别名数据** |

证据（同一个职业跨多个格子，不同职业落在同一个格子）：

| 职业 | 落到的格子 |
|---|---|
| **律师** | **F1 工资薪金**（授薪律师）/ **F2 劳务报酬**（外聘讲课）/ **F3 稿酬**（出书）/ **F5 经营所得**（律所合伙人，先分后税） |
| 医生 | F1（受雇）/ F2（多点执业）/ F5（开诊所） |
| 主播 · 自媒体 · 电商 | F1（签约底薪）/ F2（打赏、坑位费）/ F5（有工作室） |
| 网约车 · 骑手 | F2 或 F5（**各地口径不一**，恰恰说明需要定性引导而不是给结论） |
| 保险代理人 · 中介 | F2（佣金，展业成本可扣）/ F5（注册了个体户） |

**多对多的关系在数学上就否定了「职业做分类轴」的可能性** —— 它只能做索引。

| | F7 | 财产租赁 | 把房 / 车 / 东西租出去了？ | — | ❌ **三项全缺**（个税 + 房产税 4% + 增值税）P0 |
| | F8 | 财产转让 | 卖掉了房 / 股 / 车？ | `property-transfer` ⚠️ | ⚠️ **只算个税**，其余靠手填；❌ 转让股权无专器 |
| | F9 | 偶然所得 | 中奖、白得的？ | `classification` ⚠️ | ❌ 无专器 |

> **一个意外收获**：`classification` 此前在总表里被记作「兜底格 → 建议拆」。按 9 格重排后发现，它其实正好覆盖法定的**「分类所得」**一组（F6 红利 + F9 偶然），另外还兼职了 F3/F4 两个综合所得项。它不是设计缺陷，而是当年**无意做出了「分类所得」的入口**——缺的只是把一枚格子 UI 做出来。§3 的口径由「建议拆」改为「按 9 格补入口」。

#### 1.2.2 二分没有消失，只是换成了「这笔钱有人替你处理吗」

| | 落在哪些格 | 他要什么 | 产品形态 |
|---|---|---|---|
| **有人代扣** | 以 F1 为主 | 到手多少、能不能退税 | 直接给计算器 |
| **要自己处理** | F2–F9 | **先定性**（这笔钱属哪一格），再给工具 | 定性引导在前 |

**「特殊职业人群」不是一个分类，而是一个症状：没人给他代扣代缴。** 所以第二侧的人要的是同一个东西 —— 定性引导。这比按职业枚举准确，也不会随职业增加而膨胀。

## §5 维护约定

1. **一个工具一个主挂载点**，跨分支可以有次挂载点；计数以主挂载点为准，不重复
2. **状态只有三种**：✅ 现有 / ⚠️ 现有但混装或不精确 / ❌ 待做
3. **入口数由分类体系统计得出**，不再硬编码「41 个」——拆 `classification`、拆 `surtax-stamp` 后这个数字会变
4. **两条分支共用同一套税种字典**（`tax-taxonomy.js`）：A 分支的事件映射到 `taxCode`，B 分支的税种直接是 `taxCode`。这样 A / B 可以互相跳转（个体经营者 → 增值税 → 落在 B / C1）
5. **普法卡不是工具**：存款利息免税、养老金免税这类，做成知识卡而不是计算器
6. **新职业只加别名行，不加分类节点**：出现新业态（某个新平台从业者）时，只允许往 `ROLE_ALIASES`（§1.2.3）加一行，指向已有的 F1–F9 组合；**不得**在 L2 所得形态下新增格子，也**不得**为此新建一层分类。理由见 §1.2.0（职业是开放集合，所得形态是法律给定的封闭集合）
7. **事件层（L3）必须能回答「属哪一格」**：新增事件时要在 §1.3 的「所得形态」列填值；填不出值说明这个事件可能不是一笔收入（如买房→契税），应归入「跨格子事项」

### 注 1：`property-transfer` 为什么只有个税

内核注释 `property-transfer-quick.js:31` 明确：「增值税及附加由调用方传入（口径在 `surtax-stamp-quick` / `vat-quick`，**不在这里复制一遍**）」。所以现在它只算财产转让所得个税，其余税种要用户在别的工具算完后手填进「转让过程中缴纳的税金」字段。

将来补齐的正确姿势：**写一个组合器调用现有内核**，而不是在 `property-transfer-quick` 里重算——这与仓库「同一条口径不许复制」的原则一致，也与上面 P0 的「个人出租组合」是同一个做法。

**M5（v2.1.0）已经按这个姿势交了第一份**：`property-rental-quick.js` 里没有一条税率，价税分离调
`EuriskoVatQuick.priceSplitOf`、附加与租赁合同印花税调 `EuriskoSurtaxQuick`，四个独属于出租的参数
（增值税减按 1.5%、房产税 4%、个税 10%、修缮费 800 元/月）落在 `tax-constants.js` 的 `rentalRules`，
且 5% 与 10 万免征线、财产租赁 20%、六税两费减半比例全部是**引用**上游常量 —— 改上游而这里没跟着变，
`tests/property-rental-deep.test.js` 的「口径同源」那一段会红。卖房组合补齐时直接抄这个结构。
